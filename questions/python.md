### Python

1. Какие типы данных существуют в Python?
   <details>
   <summary>Ответ</summary>

   * **Числа**: `int` (произвольной точности), `float`, `complex`, `Decimal` и
     `Fraction` из стандартной библиотеки.
   * **Логический**: `bool` (подтип `int`).
   * **Последовательности**: `str`, `bytes`, `bytearray`, `list`, `tuple`,
     `range`.
   * **Множества**: `set`, `frozenset`.
   * **Отображения**: `dict`.
   * **Прочее**: `None`, функции и классы (они тоже объекты), `Ellipsis`.

   Ключевое деление — на изменяемые (`list`, `dict`, `set`, `bytearray`) и
   неизменяемые (`int`, `float`, `str`, `tuple`, `frozenset`, `bytes`). От него
   зависят и поведение при передаче в функцию, и возможность быть ключом
   словаря.

   </details>

1. Области видимости в Python. Как работают?
   <details>
   <summary>Ответ</summary>

   Правило LEGB: сначала ищем в локальной области (Local), затем в объемлющих
   функциях (Enclosing), затем в модуле (Global) и наконец во встроенных именах
   (Built-in).

   ```python
   x = 'global'

   def outer():
       x = 'enclosing'
       def inner():
           print(x)       # 'enclosing' — берётся из объемлющей функции
       inner()
   ```

   Присваивание внутри функции по умолчанию создаёт локальную переменную —
   именно поэтому попытка изменить внешнюю даёт `UnboundLocalError`. Чтобы
   писать во внешнюю область, нужны `global` (модуль) или `nonlocal` (объемлющая
   функция).

   Важные детали: у `if`, `for` и `while` своей области видимости нет
   (переменная цикла остаётся жить после него), а у comprehension'ов — есть; у
   классов область видимости особая: тело класса не участвует в поиске имён для
   методов.

   </details>

1. Методы работы со списками, какие существуют?
   <details>
   <summary>Ответ</summary>

   ```python
   lst.append(x)      # добавить в конец
   lst.extend(it)     # добавить все элементы итерируемого
   lst.insert(i, x)   # вставить по индексу (O(n))
   lst.remove(x)      # удалить первое вхождение по значению
   lst.pop([i])       # снять и вернуть (по умолчанию последний)
   lst.clear()
   lst.index(x)       # найти индекс, иначе ValueError
   lst.count(x)
   lst.sort(key=..., reverse=True)   # на месте
   lst.reverse()      # на месте
   lst.copy()         # поверхностная копия, как lst[:]
   ```

   Рядом полезные встроенные функции, которые возвращают новое значение, а не
   меняют список: `sorted`, `reversed`, `len`, `sum`, `min`, `max`, `enumerate`,
   `zip`, плюс срезы (`lst[1:5:2]`) и list comprehension.

   Оговорки: `sort()` возвращает `None` (частая ошибка `lst = lst.sort()`),
   удаление из середины и `insert(0, x)` — это `O(n)` (для очереди берут
   `collections.deque`), а `copy()` копирует только верхний уровень.

   </details>

1. Как устроены хеш-мапы в Python?
   <details>
   <summary>Ответ</summary>

   `dict` — хэш-таблица. Для ключа вычисляется `hash()`, по нему выбирается
   слот; коллизии разрешаются открытой адресацией (пробированием), а не
   цепочками. При заполнении примерно на 2/3 таблица увеличивается и все
   элементы перераспределяются.

   С Python 3.6 используется «compact dict»: отдельно хранится плотный массив
   записей `(hash, key, value)`, а таблица содержит лишь индексы в него. Отсюда
   два следствия: словарь занимает меньше памяти и **сохраняет порядок вставки**
   (с 3.7 это часть спецификации языка).

   Сложность: вставка, поиск и удаление — `O(1)` в среднем, `O(n)` в худшем
   случае. Ключ обязан быть хэшируемым: `__hash__` и `__eq__` должны быть
   согласованы, а объект — неизменяемым по этим полям, иначе запись потеряется.
   `set` устроен так же, но хранит только ключи.

   </details>

1. В чем разница между операторами `is` и `==`?
   <details>
   <summary>Ответ</summary>

   `is` сравнивает идентичность — это один и тот же объект в памяти (`id(a) ==
   id(b)`). `==` сравнивает значения и вызывает `__eq__`.

   ```python
   a = [1, 2]; b = [1, 2]
   a == b    # True  — значения равны
   a is b    # False — разные объекты

   x = 256; y = 256; x is y      # True  — маленькие int кэшируются
   x = 257; y = 257; x is y      # False (в интерактивном режиме)
   ```

   Практика: `is` применяют только к синглтонам — `None`, `True`, `False` (`if x
   is None`), и в `Enum`. Сравнивать через `is` числа и строки нельзя:
   кэширование малых чисел и интернирование строк — деталь реализации CPython,
   на которую нельзя полагаться.

   </details>

1. Какие циклы существуют в Python?
   <details>
   <summary>Ответ</summary>

   Два: `for` (обход итерируемого объекта) и `while` (по условию). Отдельного
   `do..while` нет, его имитируют `while True` с `break`.

   ```python
   for i, item in enumerate(items, start=1):
       if not item.valid:
           continue
       if item.stop:
           break
   else:
       print('прошли без break')   # блок else у циклов
   ```

   Особенности Python: `for` работает через протокол итератора
   (`__iter__`/`__next__`), а не по индексу — поэтому `range(len(x))` считается
   антипаттерном; у обоих циклов есть `else`, срабатывающий, если не было
   `break`; вместо ручных циклов часто выразительнее comprehension, `itertools`,
   `sum`/`any`/`all`.

   </details>

1. Что такое контекстный менеджер? Для чего он используется?
   <details>
   <summary>Ответ</summary>

   Объект, реализующий протокол `__enter__`/`__exit__`, который гарантирует
   освобождение ресурса при выходе из блока `with` — в том числе при исключении.

   ```python
   with open('data.csv', encoding='utf-8') as f:   # файл закроется всегда
       process(f)

   from contextlib import contextmanager

   @contextmanager
   def transaction(conn):
       tx = conn.begin()
       try:
           yield tx
           tx.commit()
       except Exception:
           tx.rollback()
           raise
   ```

   Для чего используется: файлы и сетевые соединения, транзакции базы,
   блокировки (`threading.Lock`), временная подмена окружения и настроек, замер
   времени, `pytest.raises`, временные каталоги. По сути это структурированная
   замена `try/finally`.

   Полезно упомянуть: `contextlib.contextmanager` для написания через генератор,
   `ExitStack` для динамического набора менеджеров, `__aenter__`/ `__aexit__` и
   `async with` для асинхронного кода.

   </details>

1. Что такое магические методы в Python? Как они работают?
   <details>
   <summary>Ответ</summary>

   Методы с двойным подчёркиванием (dunder), которые Python вызывает в ответ на
   синтаксис и встроенные операции. Именно они делают протоколы языка
   расширяемыми.

   ```python
   class Money:
       def __init__(self, cents): self.cents = cents
       def __repr__(self): return f'Money({self.cents})'
       def __eq__(self, other): return self.cents == other.cents
       def __hash__(self): return hash(self.cents)
       def __add__(self, other): return Money(self.cents + other.cents)
       def __lt__(self, other): return self.cents < other.cents
   ```

   Группы: создание и уничтожение (`__new__`, `__init__`, `__del__`),
   представление (`__repr__`, `__str__`, `__format__`), сравнение (`__eq__`,
   `__lt__`, `__hash__`), арифметика (`__add__`, `__mul__`), контейнеры
   (`__len__`, `__getitem__`, `__contains__`, `__iter__`), вызов (`__call__`),
   контекст (`__enter__`/`__exit__`), доступ к атрибутам (`__getattr__`,
   `__setattr__`, `__get__` у дескрипторов), асинхронность (`__await__`,
   `__aiter__`).

   Как работают: `a + b` — это `type(a).__add__(a, b)`, `len(x)` —
   `type(x).__len__(x)`. Поиск идёт по типу, а не по экземпляру.

   </details>

1. В чем разница между приватными и защищенными методами?
   <details>
   <summary>Ответ</summary>

   В Python нет настоящих модификаторов доступа, есть соглашения:

   * `_name` — «защищённый»: техническая договорённость «не трогать снаружи».
     Ничего не запрещает, но такие имена не попадают в `from module import *`.
   * `__name` — «приватный»: срабатывает name mangling, имя превращается в
     `_ClassName__name`. Это не защита, а способ избежать случайного
     переопределения в наследниках.

   ```python
   class A:
       def __init__(self):
           self._protected = 1
           self.__private = 2

   a = A()
   a._protected        # 1 — доступно
   a.__private         # AttributeError
   a._A__private       # 2 — доступ есть, просто имя другое
   ```

   Практика: по умолчанию используют одно подчёркивание, двойное — редко и
   осознанно (обычно в библиотеках и базовых классах, чтобы наследники не
   затёрли внутреннее поле). Основной механизм инкапсуляции в Python —
   договорённость и документация, а не запрет.

   </details>

1. Различия между `staticmethod` и `classmethod`.
   <details>
   <summary>Ответ</summary>

   `classmethod` получает первым аргументом класс (`cls`), `staticmethod` — не
   получает ничего и является просто функцией в пространстве имён класса.

   ```python
   class User:
       table = 'users'

       @classmethod
       def from_row(cls, row):       # альтернативный конструктор
           return cls(**row)         # cls учитывает наследника

       @staticmethod
       def normalize_email(email):   # утилита, ничего не знает о классе
           return email.strip().lower()
   ```

   Когда что: `classmethod` — фабрики и альтернативные конструкторы, работа с
   атрибутами класса, полиморфизм при наследовании (`cls` будет наследником).
   `staticmethod` — вспомогательная функция, логически связанная с классом, но
   не использующая ни экземпляр, ни класс.

   </details>

1. Что такое GIL? Как он влияет на многозадачность в Python?
   <details>
   <summary>Ответ</summary>

   GIL (Global Interpreter Lock) — глобальная блокировка интерпретатора CPython:
   одновременно байт-код исполняет только один поток.

   Что это значит на практике:

   * **CPU-bound задачи не ускоряются потоками** — потоки лишь делят одно ядро.
     Для них нужен `multiprocessing`, `concurrent.futures.ProcessPoolExecutor`,
     вынос вычислений в C/Rust-расширения (numpy сам отпускает GIL) или другой
     рантайм.
   * **I/O-bound задачи ускоряются** — при ожидании сети и диска GIL
     отпускается, поэтому потоки и `asyncio` здесь работают хорошо.

   ```text
   CPU-bound: процессы (ProcessPool), C-расширения
   I/O-bound: threads или asyncio
   ```

   Полезно добавить: GIL — деталь реализации CPython, в Jython и PyPy-STM его
   нет; в Python 3.12 появились подинтерпретаторы, а в 3.13 — экспериментальный
   free-threaded режим (`--disable-gil`), то есть направление на устранение GIL
   уже есть.

   </details>

1. Что может быть ключом словаря, а что не может? Почему?
   <details>
   <summary>Ответ</summary>

   Ключом может быть любой **хэшируемый** объект: у него есть `__hash__`, а
   `__eq__` согласован с хэшем, и значение хэша не меняется за время жизни.

   Можно: `int`, `float`, `str`, `bytes`, `tuple` из хэшируемых, `frozenset`,
   `None`, `bool`, объекты классов (по умолчанию хэшируются по `id`), `Enum`,
   `datetime`.

   Нельзя: `list`, `dict`, `set`, `bytearray` и `tuple`, внутри которого есть
   изменяемый объект.

   ```python
   d = {(1, 2): 'ok'}      # хорошо
   d = {[1, 2]: 'нет'}     # TypeError: unhashable type: 'list'
   ```

   Почему так: словарь размещает ключ по значению хэша. Если ключ изменить после
   вставки, хэш изменится, и запись окажется «потерянной» — найти её по новому
   значению будет невозможно. Поэтому изменяемые типы намеренно сделаны
   нехэшируемыми. Отсюда же правило: если переопределяешь `__eq__`, определи и
   `__hash__` (иначе класс станет нехэшируемым).

   </details>

1. Как устроено наследование в Python? Как работает множественное наследование?
   <details>
   <summary>Ответ</summary>

   Класс наследует атрибуты и методы родителей, поиск идёт по MRO (Method
   Resolution Order) — линеаризации иерархии по алгоритму C3. Множественное
   наследование разрешено.

   ```python
   class A:
       def greet(self): return 'A'

   class B(A):
       def greet(self): return 'B' + super().greet()

   class C(A):
       def greet(self): return 'C' + super().greet()

   class D(B, C): pass

   D.__mro__      # D, B, C, A, object
   D().greet()    # 'BCA' — super() идёт по MRO, а не «к родителю»
   ```

   Ключевая мысль: `super()` вызывает **следующий класс в MRO**, а не
   конкретного родителя, — именно так «ромбовидная проблема» решается без
   двойного вызова `A`. Это же требует кооперативности: все классы в цепочке
   должны вызывать `super().__init__(**kwargs)`.

   Практика: множественное наследование в основном используется для миксинов
   (узкая примесь поведения без своего состояния), и часто композиция
   предпочтительнее. Если MRO построить нельзя, Python выдаст `TypeError` при
   объявлении класса.

   </details>

1. Что такое ленивые вычисления в Python?
   <details>
   <summary>Ответ</summary>

   Вычисление значения не заранее, а в момент, когда оно реально понадобилось.
   Так экономят память и время: можно работать с бесконечными или очень большими
   последовательностями.

   ```python
   squares = (x * x for x in range(10**9))   # генераторное выражение
   next(squares)                             # считает по одному

   def read_lines(path):
       with open(path, encoding='utf-8') as f:
           for line in f:                    # файл не читается целиком
               yield line.rstrip()

   from itertools import count, islice
   list(islice(count(), 5))                  # [0, 1, 2, 3, 4]
   ```

   Где встречается в языке: генераторы и `yield`, генераторные выражения,
   `range`, `map`/`filter`/`zip` и `dict.items()` в Python 3, модуль
   `itertools`, `functools.cached_property`, ленивые QuerySet в Django (запрос
   уходит в базу только при обращении к данным), логические операторы `and`/`or`
   с коротким замыканием.

   Обратная сторона: ленивый объект одноразовый, у него нет `len`, ошибки
   всплывают позже (в момент потребления), и по QuerySet легко случайно сделать
   N+1 запросов.

   </details>

1. В чем разница между Flask и FastAPI?
   <details>
   <summary>Ответ</summary>

   * **Flask** — минималистичный синхронный WSGI-фреймворк, появился раньше,
     огромная экосистема расширений (Flask-SQLAlchemy, Flask-Login). Валидация,
     сериализация и документация — отдельными библиотеками (marshmallow,
     pydantic, flasgger).
   * **FastAPI** — асинхронный ASGI-фреймворк на Starlette и Pydantic. Из
     коробки: валидация и сериализация по аннотациям типов, автоматическая
     OpenAPI-документация (`/docs`), внедрение зависимостей, поддержка WebSocket
     и фоновых задач.

   ```python
   # Flask
   @app.post('/users')
   def create():
       data = request.get_json()          # валидируешь сам

   # FastAPI
   @app.post('/users')
   async def create(user: UserIn) -> UserOut:   # валидация и схема автоматом
       ...
   ```

   Когда что: FastAPI — для новых API, особенно с большим количеством
   асинхронных внешних вызовов. Flask — когда нужен простой синхронный сервис,
   серверный рендеринг шаблонов или уже есть команда и экосистема вокруг него.
   Оговорка про FastAPI: синхронная блокирующая функция в async-обработчике
   блокирует event loop, поэтому её нужно выносить в `run_in_threadpool` или
   делать обработчик обычным `def`.

   </details>

1. Что такое сериализация? Где и зачем она используется?
   <details>
   <summary>Ответ</summary>

   Преобразование объекта в поток байтов или текст, который можно сохранить или
   передать, и обратное преобразование (десериализация).

   ```python
   import json, pickle

   json.dumps({'id': 1})        # '{"id": 1}' — текст, межъязыковой формат
   pickle.dumps(obj)            # байты, только Python, зато любые объекты
   ```

   Где используется: ответы API (JSON), кэш и очереди (Redis, Celery), хранение
   состояния, обмен между сервисами (JSON, Protobuf, Avro, MessagePack), файлы
   конфигурации (YAML, TOML), формы и модели (pydantic, marshmallow,
   DRF-сериализаторы).

   Что важно сказать: `pickle` нельзя применять к недоверенным данным — его
   десериализация выполняет код (уязвимость RCE), для внешнего обмена берут JSON
   или Protobuf. Плюс типовые проблемы: `datetime`, `Decimal` и `UUID` не
   сериализуются в JSON по умолчанию, у больших чисел теряется точность, а
   версионирование схемы нужно продумывать заранее.

   </details>

### Базы данных

1. Какие бывают типы баз данных? В чем их отличия?
   <details>
   <summary>Ответ</summary>

   * **Реляционные** (PostgreSQL, MySQL, SQLite): таблицы, строгая схема, SQL,
     JOIN, ACID-транзакции. Выбор по умолчанию для связанных данных.
   * **Документные** (MongoDB): документы JSON/BSON, гибкая схема, данные
     денормализуют. Удобно для разнородных документов и быстрого старта.
   * **Ключ-значение** (Redis, DynamoDB): очень быстрый доступ по ключу. Кэш,
     сессии, счётчики, очереди.
   * **Колоночные** (ClickHouse, Cassandra): аналитика по огромным объёмам,
     агрегаты по нескольким колонкам вместо чтения всей строки.
   * **Графовые** (Neo4j): связи как first-class сущность, обход графа. Соцсети,
     рекомендации, антифрод.
   * **Временных рядов** (TimescaleDB, InfluxDB): метрики, события, агрегации по
     времени.
   * **Поисковые** (Elasticsearch): полнотекстовый поиск с релевантностью.

   Главное отличие — модель данных и то, какие гарантии обменены на
   масштабирование и скорость. Практика: реляционная как основная база, а
   специализированные — под конкретную задачу.

   </details>

1. В чем разница между `JOIN` и `UNION`?
   <details>
   <summary>Ответ</summary>

   `JOIN` соединяет таблицы **по горизонтали** — добавляет колонки, объединяя
   строки по условию. `UNION` склеивает результаты **по вертикали** — добавляет
   строки, наборы колонок должны совпадать.

   ```text
   JOIN:   users(id, name) + orders(user_id, total) -> id, name, total
   UNION:  select id from clients_ru
           union
           select id from clients_kz          -> один столбец, строки обеих таблиц
   ```

   Иначе говоря: `JOIN` отвечает на вопрос «что связано с чем», `UNION` — «дай
   всё из нескольких источников в одном списке».

   </details>

1. В чем различия между `UNION` и `UNION ALL`?
   <details>
   <summary>Ответ</summary>

   `UNION` убирает дубликаты строк, `UNION ALL` возвращает всё как есть.

   Разница в цене: чтобы отбросить дубли, базе нужно отсортировать или
   захэшировать весь результат — это дополнительная работа и память. Поэтому
   `UNION ALL` быстрее, и его берут по умолчанию, если известно, что пересечений
   нет (или дубликаты допустимы).

   ```sql
   select id from a union all select id from b;   -- быстрее
   select id from a union     select id from b;   -- + дедупликация
   ```

   </details>

1. Какие требования предъявляются к оператору `UNION`?
   <details>
   <summary>Ответ</summary>

   * Одинаковое **число столбцов** во всех запросах.
   * **Совместимые типы** столбцов по позициям (база приводит их к общему типу
     или выдаёт ошибку).
   * Имена столбцов результата берутся из **первого** запроса.
   * `ORDER BY` допустим только один — в самом конце, он относится ко всему
     объединению (внутри частей — только с `LIMIT` и обычно в подзапросе).

   ```sql
   select id, name, 'ru' as src from clients_ru
   union all
   select id, name, 'kz'        from clients_kz
   order by name
   limit 100;
   ```

   Порядок столбцов важен: соответствие идёт по позиции, а не по имени, —
   классическая ошибка, когда во втором запросе колонки перепутаны местами и
   типы случайно совпали.

   </details>

1. В чем разница между `HAVING` и `WHERE`?
   <details>
   <summary>Ответ</summary>

   `WHERE` фильтрует строки **до** группировки, `HAVING` — группы **после**
   агрегации. Поэтому в `WHERE` нельзя использовать агрегатные функции, а в
   `HAVING` можно.

   ```sql
   select user_id, count(*) as cnt
   from orders
   where created_at >= '2026-01-01'   -- отбор строк до группировки
   group by user_id
   having count(*) > 5;               -- отбор групп по агрегату
   ```

   Порядок выполнения: `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` →
   `ORDER BY` → `LIMIT`.

   Практический вывод: условия, которые можно проверить до группировки, всегда
   ставят в `WHERE` — он отсекает строки раньше и может использовать индекс, а
   `HAVING` работает уже по промежуточному результату.

   </details>

1. Что такое индексы в базах данных? Какие плюсы и минусы у их использования?
   <details>
   <summary>Ответ</summary>

   Индекс — отдельная структура (обычно B-tree) с упорядоченными значениями
   столбца и ссылками на строки. Работает как алфавитный указатель: поиск за
   `O(log n)` вместо полного прохода.

   **Плюсы**: ускоряют `WHERE`, `JOIN` по ключам, `ORDER BY`, `GROUP BY`,
   обеспечивают `UNIQUE` и первичные ключи, позволяют читать данные прямо из
   индекса (index-only scan).

   **Минусы**: занимают место, замедляют `INSERT`/`UPDATE`/`DELETE` (индексы
   надо поддерживать), требуют актуальной статистики, могут не использоваться
   (`LIKE '%x'`, функция над столбцом без функционального индекса, низкая
   селективность), а лишние индексы просто вредят.

   Что полезно добавить: составной индекс `(a, b)` работает для условий по `a` и
   по `a, b`, но не по одному `b` (правило левого префикса); внешние ключи в
   PostgreSQL сами индекс не создают; проверять использование индекса надо через
   `EXPLAIN ANALYZE`, а не по интуиции.

   </details>

1. Что такое SQL-инъекции? Как их предотвратить?
   <details>
   <summary>Ответ</summary>

   Уязвимость, когда пользовательские данные попадают в текст SQL-запроса и
   меняют его смысл: можно прочитать чужие данные, обойти авторизацию, изменить
   или удалить записи.

   ```python
   cur.execute(f"select * from users where email = '{email}'")   # уязвимо
   # email = ' or 1=1 --

   cur.execute('select * from users where email = %s', (email,))  # правильно
   ```

   Защита:

   * **параметризованные запросы** — основной способ (`%s`/`:name` в psycopg и
     SQLAlchemy, `?` в sqlite3); никогда не собирать SQL f-строками и
     конкатенацией;
   * ORM (Django ORM, SQLAlchemy) — но осторожно с `raw`, `extra`, `text()` и
     `RawSQL`;
   * то, что нельзя параметризовать (имя таблицы, колонки, направление
     сортировки), проверять по **белому списку**;
   * минимальные права пользователя базы, отдельные учётки на чтение и запись;
   * валидация типов на входе (pydantic) и логирование подозрительных запросов
     как дополнение, но не замена параметризации.

   </details>

1. Что такое транзакции? Как они работают?
   <details>
   <summary>Ответ</summary>

   Транзакция — группа операций, выполняемых как одно целое: либо все, либо ни
   одна. Свойства описывает ACID: атомарность, согласованность, изолированность,
   долговечность.

   ```python
   with connection.atomic():          # Django
       order.save()
       Payment.objects.create(order=order, amount=order.total)
   # исключение внутри блока -> откат обеих операций
   ```

   Как работают внутри: изменения пишутся в журнал упреждающей записи (WAL) — за
   счёт него обеспечивается долговечность и восстановление после сбоя;
   параллельные транзакции изолируются блокировками или версионностью (MVCC в
   PostgreSQL, где читатели не блокируют писателей). Уровни изоляции — read
   committed (по умолчанию в PostgreSQL), repeatable read, serializable —
   определяют, какие аномалии возможны: грязное и неповторяемое чтение, фантомы.

   Практические оговорки: держать транзакцию короткой (долгая мешает `VACUUM` и
   держит блокировки), не делать внутри неё внешних HTTP-вызовов, помнить, что
   при `COMMIT` может прийти конфликт сериализации — его надо повторить.

   </details>

1. Какие ORM знаешь и какие использовал? Какие плюсы и минусы можешь выделить?
   <details>
   <summary>Ответ</summary>

   Django ORM, SQLAlchemy (Core и ORM), Tortoise ORM и Peewee для асинхронных и
   небольших проектов, SQLModel (pydantic + SQLAlchemy).

   * **Django ORM** — очень быстро писать, миграции из коробки, админка; минусы
     — жёстко привязан к Django, сложные запросы выражать неудобно.
   * **SQLAlchemy** — мощнее и гибче, полный контроль над SQL, поддержка
     асинхронности, Alembic для миграций; минусы — выше порог входа и больше
     кода.

   Общие минусы ORM: N+1 запросы (лечится `select_related`/ `prefetch_related` и
   `joinedload`), непрозрачный генерируемый SQL, протекающая абстракция на
   сложных выборках, потеря производительности на массовых операциях (нужны
   `bulk_create`, `update()` и сырой SQL).

   Хороший ответ включает пример: где ORM хватало, а где пришлось спуститься к
   SQL и почему.

   </details>

1. Если соединяем несколько таблиц БД с помощью `INNER JOIN`, есть ли разница в оптимизации, в каком порядке соединяем таблицы?
   <details>
   <summary>Ответ</summary>

   Для результата — нет: `INNER JOIN` коммутативен и ассоциативен. Для плана
   порядок соединений критичен, но выбирает его планировщик по статистике, а не
   по тому, как написан запрос.

   Оговорки, которые стоит назвать: при большом числе таблиц PostgreSQL
   перестаёт перебирать все варианты (`join_collapse_limit`,
   `from_collapse_limit`, дальше генетический оптимизатор), и тогда порядок в
   запросе начинает влиять; с `LEFT JOIN` порядок меняет и результат, поэтому
   переставлять их планировщик не вправе.

   Если план плохой — смотреть `EXPLAIN (ANALYZE, BUFFERS)`, сравнивать оценку
   строк с фактической, обновлять статистику (`ANALYZE`) и проверять индексы, а
   не переписывать порядок таблиц наугад.

   </details>

### Сети

1. Какие бывают протоколы передачи данных?
   <details>
   <summary>Ответ</summary>

   По уровням модели TCP/IP:

   ```text
   прикладной:    HTTP/HTTPS, HTTP/2, HTTP/3, WebSocket, gRPC, DNS,
                  SMTP/IMAP/POP3, FTP/SFTP, SSH, MQTT, AMQP
   транспортный:  TCP, UDP, QUIC
   сетевой:       IP, ICMP
   канальный:     Ethernet, Wi-Fi, ARP
   ```

   Для бэкенда чаще всего важны: HTTP/HTTPS для API, WebSocket для двусторонней
   связи, gRPC для межсервисных вызовов, AMQP/Kafka-протокол для очередей, SMTP
   для писем, TCP как транспорт под всем этим и UDP для DNS и QUIC.

   </details>

1. В чем разница между HTTP и HTTPS?
   <details>
   <summary>Ответ</summary>

   HTTPS — тот же HTTP, но внутри TLS-соединения: трафик шифруется, проверяется
   целостность, а сертификат подтверждает подлинность домена. Порт 443 вместо
   80.

   Что это даёт: пароли, токены и cookie нельзя прочитать на пути, содержимое
   нельзя подменить (внедрить скрипт или рекламу), нельзя выдать себя за наш
   сайт. Соединение начинается с TLS-рукопожатия: согласование шифров, проверка
   сертификата, обмен ключами. Домен (SNI) виден, а путь, заголовки и тело —
   нет.

   </details>

1. В чем разница между UDP и TCP?
   <details>
   <summary>Ответ</summary>

   TCP — с установлением соединения (рукопожатие SYN → SYN/ACK → ACK),
   гарантирует доставку и порядок, переспрашивает потерянное, управляет
   перегрузкой. Медленнее, зато надёжно: HTTP, базы, почта.

   UDP — без соединения, отдельные датаграммы: доставка и порядок не
   гарантированы, зато минимум накладных расходов и задержки. Голос и видео,
   игры, DNS, QUIC/HTTP-3 (надёжность там реализована уже поверх UDP).

   ```text
   TCP: соединение, подтверждения, повторы, порядок  -> надёжность
   UDP: отправил и всё                               -> скорость
   ```

   </details>

1. Какие методы HTTP существуют? Как они различаются?
   <details>
   <summary>Ответ</summary>

   `GET` (чтение), `POST` (создание и любые действия с побочными эффектами),
   `PUT` (полная замена), `PATCH` (частичное обновление), `DELETE`, `HEAD` (как
   `GET`, но без тела), `OPTIONS` (какие методы поддерживаются, в том числе CORS
   preflight), реже `TRACE` и `CONNECT`.

   Различаются по двум свойствам:

   ```text
   безопасные (не меняют состояние):     GET, HEAD, OPTIONS
   идемпотентные (повтор безвреден):     GET, HEAD, PUT, DELETE, OPTIONS
   не идемпотентные:                     POST, PATCH
   ```

   Практические следствия: `GET` кэшируется и не должен ничего менять,
   идемпотентный запрос можно безопасно повторить при таймауте, а для повторов
   `POST` вводят ключ идемпотентности. Тело обычно есть у `POST`, `PUT`,
   `PATCH`.

   </details>

1. Что такое JWT токен?
   <details>
   <summary>Ответ</summary>

   JSON Web Token — самодостаточный токен из трёх частей, разделённых точкой:
   заголовок, полезная нагрузка и подпись, каждая в base64url.

   ```text
   eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsImV4cCI6MTcwMH0.<подпись>
      header (alg)          payload (sub, exp, iss, aud)     signature
   ```

   Сервер проверяет подпись своим ключом и доверяет содержимому, не обращаясь к
   базе, — отсюда удобство для API и микросервисов.

   Что важно сказать: payload не зашифрован, а всего лишь закодирован — секреты
   туда кладут нельзя; токен нельзя отозвать до истечения, поэтому `exp` делают
   коротким и добавляют refresh-токен; алгоритм надо фиксировать на сервере
   (иначе атака подменой на `none` или на `HS256` с публичным ключом); проверять
   нужно `exp`, `iss`, `aud`. Для межсервисной проверки используют асимметричные
   `RS256`/`ES256`: подписывает приватным ключом только эмитент.

   </details>

1. Что такое REST API и как оно работает?
   <details>
   <summary>Ответ</summary>

   REST — архитектурный стиль поверх HTTP: данные представлены ресурсами с URL,
   действия выражаются HTTP-методами, результат — кодом ответа и телом (обычно
   JSON).

   ```text
   GET    /articles?page=2   список          200
   GET    /articles/42       один            200 / 404
   POST   /articles          создать         201 + Location
   PATCH  /articles/42       обновить        200
   DELETE /articles/42       удалить         204
   ```

   Принципы: клиент-серверность, stateless (сервер не хранит состояние сессии
   между запросами — контекст приходит в токене), кэшируемость, единый
   интерфейс, слоистость, опционально HATEOAS.

   Как работает на практике: клиент отправляет запрос с методом, путём,
   заголовками (`Authorization`, `Accept`) и телом; сервер маршрутизирует его в
   обработчик, валидирует, обращается к базе и возвращает статус и JSON. Плюс
   сопутствующее: пагинация, фильтры в query-параметрах, версионирование
   (`/v1/`), единый формат ошибок, OpenAPI-схема.

   </details>

### Безопасность

1. Какие виды уязвимостей знаешь?
   <details>
   <summary>Ответ</summary>

   Ориентир — OWASP Top 10:

   * **Инъекции**: SQL, команды ОС, шаблонизаторы (SSTI), а также XSS.
   * **Broken access control** — IDOR (доступ к чужому объекту по id),
     отсутствие проверки прав на ручке, обход через прямой URL.
   * **CSRF** — запрос от имени авторизованного пользователя с чужого сайта.
   * **Ошибки аутентификации и сессий**: слабые пароли, нет защиты от перебора,
     фиксация сессии, токены в URL.
   * **Криптографические ошибки**: нет TLS, пароли не через `bcrypt`/`argon2`,
     секреты в репозитории.
   * **Раскрытие данных**: `DEBUG = True` в проде, чувствительные данные в
     логах, открытые бэкапы и `.git`.
   * **SSRF** — сервер по просьбе клиента ходит во внутреннюю сеть.
   * **Небезопасная десериализация** (`pickle`, `yaml.load`) и загрузка файлов
     (path traversal, исполняемые файлы).
   * **Уязвимые зависимости** (`pip-audit`, Safety), небезопасная конфигурация,
     отсутствие логирования и мониторинга.

   </details>

1. Что такое `XSS` уязвимость? Как организовать защиту от неё?
   <details>
   <summary>Ответ</summary>

   Cross-Site Scripting — внедрение чужого JavaScript в страницу, который
   исполняется в браузере жертвы: кража cookie и токенов, действия от имени
   пользователя, подмена содержимого.

   Защита:

   * **экранирование при выводе по контексту**: шаблонизаторы Django и Jinja2
     экранируют автоматически, опасны `|safe`, `mark_safe`, `{% autoescape off
     %}`;
   * для HTML от пользователя — санитайзер с белым списком (bleach, nh3), а не
     самодельная чистка;
   * `Content-Security-Policy` как второй эшелон, cookie с `HttpOnly`, `Secure`,
     `SameSite`;
   * на фронте — `textContent` вместо `innerHTML`;
   * валидация входных данных полезна, но не заменяет экранирование на выводе.

   Отдельно стоит помнить про JSON, встраиваемый в HTML (`json_script` в
   Django), и про XSS в атрибутах и внутри `<script>` — контекст определяет
   способ экранирования.

   </details>

1. Что такое `SQLi` уязвимость? Как организовать защиту от неё?
   <details>
   <summary>Ответ</summary>

   SQL-инъекция — пользовательские данные попадают в текст запроса и меняют его
   смысл: чтение чужих данных, обход авторизации, изменение и удаление записей.

   ```python
   User.objects.raw(f"select * from users where email = '{email}'")  # уязвимо
   User.objects.filter(email=email)                                   # безопасно
   cur.execute('select * from users where email = %s', (email,))      # безопасно
   ```

   Защита: параметризованные запросы и ORM; никакой сборки SQL f-строками; белый
   список для имён таблиц, колонок и направления сортировки; минимальные права
   пользователя базы; аккуратность с `raw`, `extra`, `RawSQL`, `text()` и с
   `order_by` из пользовательского ввода; валидация типов на входе. WAF и
   логирование — дополнение, а не основной механизм.

   </details>

1. Чем HTTPS отличается от HTTP?
   <details>
   <summary>Ответ</summary>

   HTTPS работает поверх TLS: шифрование, контроль целостности и проверка
   подлинности сервера по сертификату; порт 443 вместо 80.

   В контексте Python-приложения стоит добавить практическое: TLS обычно
   терминируется на nginx или балансировщике, а приложение об этом узнаёт из
   `X-Forwarded-Proto` (в Django — `SECURE_PROXY_SSL_HEADER`); полезно включить
   `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE` и HSTS,
   а сертификаты брать в Let's Encrypt.

   </details>

## Middle

### Общие вопросы

1. В чем разница между аутентификацией, авторизацией и идентификацией?
   <details>
   <summary>Ответ</summary>

   * **Идентификация** — «кто ты?»: пользователь предъявляет идентификатор
     (логин, email, id).
   * **Аутентификация** — «докажи»: проверка пароля, кода из второго фактора,
     подписи токена. Результат — подтверждённая личность.
   * **Авторизация** — «что тебе можно»: проверка прав и ролей на конкретное
     действие с конкретным объектом.

   ```text
   идентификация -> аутентификация -> авторизация
      логин           пароль/токен      роли и права
      401 если не аутентифицирован, 403 если не хватает прав
   ```

   Модели авторизации: RBAC (по ролям), ABAC (по атрибутам), ACL, object-level
   permissions. Типовая ошибка — проверить только аутентификацию и забыть про
   права на объект (IDOR), либо проверять права только в интерфейсе, а не на
   сервере.

   </details>

1. Расскажи о принципах SOLID.
   <details>
   <summary>Ответ</summary>

   * **S** — Single Responsibility: у модуля одна причина для изменения.
   * **O** — Open/Closed: расширяем новым кодом, не переписывая существующий
     (новая реализация вместо ещё одного `if`).
   * **L** — Liskov Substitution: подтип подставляется вместо базового типа, не
     нарушая контракт (не ужесточать предусловия, не бросать новые исключения).
   * **I** — Interface Segregation: несколько узких интерфейсов лучше одного
     «толстого»; в Python это протоколы (`typing.Protocol`) и утиная типизация.
   * **D** — Dependency Inversion: зависим от абстракции, конкретную реализацию
     передаём снаружи.

   ```python
   class OrderService:                      # D: зависимость приходит извне
       def __init__(self, gateway: PaymentGateway, mailer: Mailer) -> None:
           self._gateway = gateway
           self._mailer = mailer
   ```

   Оговорка для Python: явные интерфейсы не обязательны — роль абстракции играют
   протоколы и duck typing, а DI часто выражается просто параметрами
   конструктора или функции. Хороший ответ содержит пример из своего кода.

   </details>

1. Расскажи о принципах ООП.
   <details>
   <summary>Ответ</summary>

   * **Инкапсуляция** — данные и работающий с ними код вместе, детали скрыты за
     интерфейсом (в Python — соглашение `_name`, свойства через `@property`).
   * **Наследование** — переиспользование поведения через иерархию; в Python
     возможно множественное, поиск методов идёт по MRO.
   * **Полиморфизм** — один вызов, разное поведение реализаций. В Python это
     прежде всего утиная типизация и dunder-протоколы: работает всё, что
     реализует нужные методы.
   * **Абстракция** — выделение существенного: `abc.ABC` и `typing.Protocol` для
     описания контракта.

   Полезные добавления: композиция обычно лучше наследования, а глубокие
   иерархии — плохой признак; в Python нет перегрузки методов по сигнатуре (есть
   `functools.singledispatch`); наследование от нескольких классов применяют для
   миксинов.

   </details>

1. Какие паттерны программирования знаешь? Приведи пару примеров.
   <details>
   <summary>Ответ</summary>

   Классификация GoF: порождающие (Factory Method, Builder, Singleton,
   Prototype), структурные (Adapter, Decorator, Facade, Proxy, Composite),
   поведенческие (Strategy, Observer, Command, Template Method, State, Chain of
   Responsibility, Iterator).

   Два примера, которые реально встречаются в Python:

   ```python
   # Strategy: алгоритм передаётся как объект или функция
   def checkout(order, gateway: PaymentGateway):
       return gateway.charge(order.total)

   # Decorator: обёртка, добавляющая поведение
   @lru_cache(maxsize=128)
   def get_rate(currency: str) -> Decimal:
       ...
   ```

   Особенность Python: часть паттернов вырождается в идиомы языка — Strategy это
   просто функция первого класса, Decorator — синтаксис `@`, Iterator —
   генераторы, Singleton — модуль (он и так один), Adapter — утиная типизация.
   Поэтому важно называть то, что применял, и не натягивать паттерны на всё
   подряд.

   </details>

1. Достаточно ли валидации в ORM при реализации проверки на уникальность, например, email при регистрации? Раскройте
   <details>
   <summary>Ответ</summary>

   Нет, недостаточно. Валидация в ORM — это `SELECT` перед `INSERT`, между ними
   есть окно: два параллельных запроса оба увидят «свободно» и оба вставят
   запись. При нескольких воркерах gunicorn это происходит регулярно — двойной
   клик по кнопке уже воспроизводит проблему.

   Надёжная защита — ограничение в базе:

   ```python
   class User(models.Model):
       email = models.EmailField()

       class Meta:
           constraints = [
               models.UniqueConstraint(Lower('email'), name='user_email_unique'),
           ]
   ```

   `unique=True` в Django как раз создаёт индекс в базе, а вот
   `Model.clean()`/`Form.is_valid()` — только проверку. Ошибку из базы
   (`IntegrityError`, `SQLSTATE 23505`) перехватывают и превращают в ошибку
   валидации формы. Дополнительно: нормализация email (trim, lower) и защита от
   повторной отправки формы.

   </details>

1. Какие последствия возможны при отправке email прямо в контроллере? Как можно решить эти проблемы?
   <details>
   <summary>Ответ</summary>

   Проблемы: запрос пользователя ждёт SMTP (медленно, таймауты), падение
   почтового сервиса роняет ручку, ретраев нет — письмо теряется, письмо может
   уйти при откате транзакции, тесты начинают ходить в сеть, скорость рассылки
   ничем не ограничена.

   Решение: обработчик только ставит задачу в очередь (Celery, RQ, Dramatiq,
   `django-q`), а воркер отправляет письмо с ретраями (`autoretry_for`,
   экспоненциальная задержка), dead-letter очередью и идемпотентностью.

   Важная деталь: задачу публиковать после коммита транзакции —
   `transaction.on_commit(lambda: send_mail.delay(user.id))`, иначе воркер может
   начать работу раньше, чем данные попадут в базу (или письмо уйдёт о том, чего
   в базе нет). В задачу передают id, а не объект.

   </details>

1. Как бы вы реализовали смену email на сайте, так чтобы соблюсти баланс между сложностью и безопасностью?
   <details>
   <summary>Ответ</summary>

   Схема с подтверждением по ссылке — разумный баланс:

   1. Пользователь вводит новый адрес и **свой текущий пароль** (или проходит
      повторную аутентификацию).
   2. Меняем не email, а создаём запись «запрос на смену»: новый адрес,
      одноразовый токен (случайный из `secrets`, хранится хэшем), TTL 1–24 часа.
   3. Письмо со ссылкой подтверждения — на **новый** адрес; уведомление о
      попытке смены со ссылкой «это не я» — на **старый**.
   4. По переходу проверяем токен и срок, меняем email, инвалидируем токен и
      остальные сессии, пишем событие в аудит-лог.

   Что учесть: rate limiting на запросы смены, уникальный индекс на email,
   письма не должны раскрывать, зарегистрирован ли адрес, сравнение токена через
   `secrets.compare_digest`. В Django для токена подойдёт
   `signing.TimestampSigner` или механика `PasswordResetTokenGenerator`.

   Чего не делать: менять email сразу по нажатию кнопки — это позволяет угнать
   аккаунт через незалоченную сессию и рассылать спам подтверждениями.

   </details>

1. Можно ли доверять email, который мы получаем по oauth от соц сетей и мержить аккаунты автоматически? Приведите примеры
   <details>
   <summary>Ответ</summary>

   Автоматически мержить нельзя. Провайдер отдаёт `email` и флаг
   `email_verified`; без подтверждённого флага адрес — просто строка, которую
   пользователь мог указать сам. Плюс бывают приватные релеи (Apple
   `@privaterelay.appleid.com`), адрес может меняться, а Gmail игнорирует точки
   и суффикс `+`.

   Примеры атак: злоумышленник регистрирует у стороннего провайдера аккаунт с
   чужим неподтверждённым email и логинится в наш сервис как жертва; или
   наоборот — регистрируется у нас на чужой адрес, а настоящий владелец позже
   приходит через OAuth и получает доступ к чужому аккаунту.

   Как правильно: мержить только при `email_verified = true` у доверенного
   провайдера, а лучше — спрашивать подтверждение у уже залогиненного
   пользователя, хранить связки в отдельной таблице `social_account (provider,
   uid)` (так делает django-allauth) и опираться на `sub` провайдера, а не на
   email.

   </details>

1. Как ограничить отправку email пользователю, который добавил письмо нашего проекта в спам? И почему это стоит делать (или не стоит)?
   <details>
   <summary>Ответ</summary>

   Отправку надо прекратить. Механика: провайдер (SES, SendGrid, Mailgun)
   присылает webhook с событиями `bounce`, `complaint` (нажали «спам»),
   `unsubscribe`; по ним адрес попадает в suppression-таблицу, и отправщик
   сверяется с ней перед каждым письмом.

   Почему это обязательно: жалобы и хардбаунсы убивают репутацию домена и IP —
   после определённого порога (у SES 0.1% жалоб) письма всех пользователей
   уходят в спам или отправку блокируют. Плюс требования CAN-SPAM, GDPR и
   152-ФЗ.

   Тонкость: разделять типы писем. Маркетинговые — блокировать полностью;
   транзакционные (сброс пароля, чек, оповещение безопасности) — при жалобе или
   хардбаунсе тоже безопаснее остановить, дав альтернативный канал в интерфейсе.

   </details>

1. Предположим что вы реализуете редакцию журнала, где редактора могут в админке править статьи. Как предотвратить ситуацию, когда два редактора могут начать одновременно редактировать одну статью и перетирать изменения друг друга?
   <details>
   <summary>Ответ</summary>

   Это задача про конкурентный доступ. Варианты по возрастанию сложности:

   **Оптимистическая блокировка** — базовое решение. У статьи есть `version`,
   при сохранении обновляем с проверкой версии:

   ```python
   updated = (Article.objects
              .filter(pk=pk, version=form_version)
              .update(body=body, version=F('version') + 1))
   if not updated:
       raise ConflictError('статью уже изменили')
   ```

   Ноль обновлённых строк означает, что кто-то сохранил раньше: показываем
   предупреждение и различия, предлагаем перезагрузить или слить изменения.
   Ничего не теряется молча.

   **Пессимистическая блокировка** — «статью редактирует Иван»: запись с
   владельцем и TTL, который продлевается, пока редактор активен; по истечении
   блокировка снимается, у админа есть принудительный сброс. Для короткой
   критической секции подойдёт `select_for_update()`, но держать её на всё время
   редактирования нельзя.

   **Совместное редактирование** (OT или CRDT — Yjs, Automerge) через WebSocket
   — настоящая одновременная работа, но существенно дороже.

   Практика: в админке журнала обычно достаточно оптимистической блокировки плюс
   мягкий индикатор «сейчас редактирует другой» через heartbeat.

   </details>

1. Каких принципов разработки нужно придерживаться, для обеспечения механизма zero downtime deployment. Как это достигается?
   <details>
   <summary>Ответ</summary>

   Zero downtime достигается тем, что старая и новая версии умеют работать
   одновременно:

   * **Обратно совместимые миграции** в несколько шагов: сначала добавить
     nullable-колонку и писать в оба места, потом перенести данные, потом
     переключить чтение и только в следующем релизе удалить старое
     (expand/contract). Никаких переименований и удалений колонок вместе с
     деплоем кода.
   * **Миграции отдельно от деплоя** и без долгих блокировок: в Django —
     `AddIndex` с `AddIndexConcurrently` и `atomic = False`, обновление данных
     батчами, отдельно от `RunPython` на всю таблицу.
   * **Приложение stateless**: сессии и кэш во внешнем хранилище, файлы в
     объектном хранилище (S3), медиа не на локальном диске.
   * **Плавное переключение трафика**: rolling update, blue-green или canary,
     readiness-проба, чтобы балансировщик не давал трафик неготовому инстансу.
   * **Graceful shutdown**: gunicorn/uvicorn по `SIGTERM` дорабатывают текущие
     запросы, Celery-воркеры — текущие задачи (`--max-tasks-per-child`, warm
     shutdown).
   * **Совместимость контрактов API и формата сообщений в очередях** в обе
     стороны: старый воркер может получить новую задачу и наоборот.
   * Плюс фичефлаги для незавершённой функциональности и план отката, не
     требующий обратной миграции данных.

   </details>

1. Что может произойти, если ваша `cron` задача, которая запускается раз в минуту, стала выполняться больше 1 минуты? Как это можно предотвратить?
   <details>
   <summary>Ответ</summary>

   Запуски начнут накладываться: появятся два и более параллельных экземпляра.
   Последствия — двойная обработка одних и тех же записей, гонки и дубликаты
   (например, повторная отправка писем), блокировки в базе, лавинообразный рост
   числа процессов и исчерпание памяти, соединений и лимитов внешних API.

   Как предотвратить:

   * **Взаимное исключение**: `flock` на файл, `pg_try_advisory_lock`, `SET NX`
     с TTL в Redis (`redis-lock`), в Celery — `celery-once` или собственный лок
     в задаче; если лок занят — просто выйти.
   * **Планировщик с гарантией одного запуска**: `concurrencyPolicy: Forbid` у
     Kubernetes CronJob, `singleton` в APScheduler.
   * **Ограничить время работы**: обработка батчами с курсором,
     `soft_time_limit`/`time_limit` в Celery, чтобы итерация укладывалась в
     интервал.
   * **Идемпотентность** обработки и алерт на длительность выполнения, чтобы
     узнать о проблеме до аварии.

   </details>

1. Если вы пишите тесты, то как вы обходите проблему того, что код который вы тестируете, делает внешние вызовы? Доп условие, говорим о том, что на CI внешние вызовы запрещены (почему так правильно?)
   <details>
   <summary>Ответ</summary>

   Внешние вызовы изолируют:

   * **Подмена зависимости**: клиент передаётся в сервис снаружи, в тесте вместо
     него фейк. Самый чистый вариант, не требует патчей.
   * **Моки и патчи**: `unittest.mock.patch`, `monkeypatch` в pytest — патчить
     надо там, где имя используется, а не где определено.
   * **Мокирование на уровне HTTP**: `responses`, `requests-mock`, `respx` для
     httpx, VCR-подход (`vcrpy`) с записанными ответами.
   * **Контрактные тесты** (Pact) плюс отдельный редкий набор реальных
     smoke-тестов вне основного CI.
   * **Testcontainers или docker compose** для того, что поднимается локально
     (PostgreSQL, Redis, RabbitMQ) — это контролируемая зависимость, а не
     внешний вызов.

   Почему запрет внешних вызовов в CI правильный: тесты должны быть
   детерминированными и быстрыми, иначе сборка падает из-за чужой недоступности
   и сети, а не из-за кода; у внешнего сервиса есть лимиты и цена; тесты не
   должны менять данные в чужих системах; в CI часто нет ни интернета, ни
   секретов. Обратная сторона — моки расходятся с реальностью, поэтому их
   дополняют контрактными тестами и мониторингом интеграций в проде.

   </details>

1. Предположим что в вашей системе реализована смена емейла. При этом этот емейл хранится еще и во внешней системе, например эквайринге, который шлет пользователю свои письма (но пользователь им напрямую не пользуется). Как бы вы реализовали синхронизацию емейла с внешней системой?
   <details>
   <summary>Ответ</summary>

   Смену email надо рассматривать как событие, которое нужно надёжно доставить
   во внешнюю систему.

   Схема: в той же транзакции, что и обновление email, пишем запись в `outbox`
   (transactional outbox). Отдельный воркер читает её и вызывает API эквайринга
   с ретраями и экспоненциальной задержкой, идемпотентным ключом запроса и
   переводом в dead-letter при исчерпании попыток. Статус синхронизации храним у
   себя (`pending`/`synced`/`failed`) и показываем в админке.

   Что ещё учесть: порядок событий (если email меняли дважды, во внешнюю систему
   должно попасть последнее значение — помогает версия записи или отправка
   текущего состояния, а не дельты), периодическая сверка (reconciliation),
   алерт на «висящие» записи, обработка ответа «такой email уже используется».

   Чего не делать: вызывать внешний API прямо в обработчике запроса — упадёт
   сеть, и данные разъедутся без следа. Простой `send_task.delay()` без outbox
   тоже теряет событие, если задача не поставилась.

   </details>

1. Как вы узнаете об ошибках, которые происходят на продакшене? От пользователей или это автоматизировано?
   <details>
   <summary>Ответ</summary>

   Автоматизировано — это ключевая часть ответа. Ошибки собирает трекер (Sentry,
   Rollbar, GlitchTip): исключение уезжает со стеком, версией релиза, окружением
   и контекстом запроса и пользователя, дальше — дедупликация, алерты в Slack

1. Как обеспечивается изоляция тестов друг от друга если они ходят в базу и меняют ее? Если в вашем фреймворке этого нет, то как вы это делаете или сделали бы?

1. Как создать генератор в Python?
   <details>
   <summary>Ответ</summary>

   Три способа:

   ```python
   def squares(n):                       # функция с yield
       for i in range(n):
           yield i * i

   gen = (i * i for i in range(n))       # генераторное выражение

   class Counter:                        # свой итератор через протокол
       def __init__(self, n): self.i, self.n = 0, n
       def __iter__(self): return self
       def __next__(self):
           if self.i >= self.n:
               raise StopIteration
           self.i += 1
           return self.i
   ```

   Что важно: генератор считает значения по одному и не держит их в памяти —
   подходит для больших файлов и потоков; он одноразовый (второй проход ничего
   не даст), `len()` к нему не применить. `yield from` делегирует другому
   генератору, `send()` позволяет передавать значения внутрь, а `async def` +
   `yield` даёт асинхронный генератор для `async for`.

   </details>

1. Как ты понимаешь ссылочную модель в Python?
   <details>
   <summary>Ответ</summary>

   В Python переменная — это имя, привязанное к объекту, а не «ячейка со
   значением». Присваивание не копирует объект, а создаёт ещё одну ссылку на
   него. Всё является объектом, включая числа и функции.

   ```python
   a = [1, 2]
   b = a          # второе имя того же списка
   b.append(3)
   a              # [1, 2, 3] — изменение видно через оба имени
   b = [9]        # переприсваивание: b теперь смотрит на другой объект, a не тронут
   ```

   Передача аргументов — «call by object reference» (call by sharing): мутация
   объекта внутри функции видна снаружи, переприсваивание параметра — нет.
   Отсюда два практических следствия: не использовать изменяемые значения по
   умолчанию (`def f(x=[])`) и помнить, что копирование бывает поверхностным
   (`copy.copy`, срез) и глубоким (`copy.deepcopy`).

   </details>

1. Если мы создадим переменную `a`, в которой будет значение `1`, и создадим переменную `b = a`, то сколько объектов и сколько ссылок будет создано?
   <details>
   <summary>Ответ</summary>

   Объект будет один, ссылок — две. `b = a` не копирует значение, а привязывает
   второе имя к тому же объекту:

   ```python
   a = 1
   b = a
   a is b            # True — один и тот же объект
   id(a) == id(b)    # True
   sys.getrefcount(a)  # больше двух: маленькие int кэшируются и на них
                       # ссылается сам интерпретатор
   ```

   Дополнение, которое стоит сказать: для небольших целых чисел (от -5 до 256)
   CPython держит пул готовых объектов, поэтому «объект один» здесь верно
   вдвойне — даже независимое `c = 1` даст ту же ссылку. Для изменяемых объектов
   ответ такой же по смыслу: один объект, две ссылки, и мутация видна через оба
   имени.

   </details>

1. Для чего нужен счетчик ссылок в Python?
   <details>
   <summary>Ответ</summary>

   Счётчик ссылок (`refcount`) — основной механизм управления памятью в CPython:
   у каждого объекта хранится число ссылок на него, и как только оно падает до
   нуля, память освобождается немедленно и вызывается `__del__`.

   ```python
   import sys
   x = object()
   sys.getrefcount(x)   # 2: сама переменная + временная ссылка в аргументе
   del x                # refcount = 0 -> объект уничтожен сразу
   ```

   Плюсы: детерминированность (ресурс освобождается сразу, а не «когда-нибудь»)
   и отсутствие длинных пауз на сборку. Минус: циклические ссылки счётчиком не
   разрешаются, поэтому в дополнение работает генерационный сборщик мусора
   (модуль `gc`), который находит недостижимые циклы. Ещё один нюанс — операции
   со счётчиком требуют защиты, и это одна из причин существования GIL.

   </details>

1. Какие типы данных изменяемые, а какие неизменяемые в Python? Почему это важно?
   <details>
   <summary>Ответ</summary>

   **Изменяемые**: `list`, `dict`, `set`, `bytearray`, экземпляры обычных
   классов. **Неизменяемые**: `int`, `float`, `bool`, `str`, `bytes`, `tuple`,
   `frozenset`, `None`, `Decimal`, `datetime`.

   Почему это важно:

   * **Поведение при передаче в функцию**: мутация изменяемого объекта видна
     снаружи, неизменяемый изменить нельзя в принципе.
   * **Ключи словаря и элементы множества** — только хэшируемые, то есть
     практически только неизменяемые.
   * **Изменяемые значения по умолчанию** — классическая ловушка:

   ```python
   def add(item, target=[]):    # список создаётся один раз при определении
       target.append(item)
       return target
   add(1); add(2)               # [1, 2] — сюрприз
   def add(item, target=None):  # правильный вариант
       target = [] if target is None else target
   ```

   * **Общее состояние и потоки**: неизменяемые объекты безопасно использовать
     из нескольких потоков.
   * Оговорка: `tuple` неизменяем сам, но может содержать изменяемые объекты — и
     тогда он нехэшируемый.

   </details>

1. Расскажи про использование моков
   <details>
   <summary>Ответ</summary>

   Мок — подставной объект вместо реальной зависимости: он записывает вызовы и
   возвращает заранее заданные значения. В Python это `unittest.mock` (`Mock`,
   `MagicMock`, `patch`) и `monkeypatch` из pytest.

   ```python
   from unittest.mock import patch

   @patch('app.services.payments.gateway.charge', return_value=Receipt(ok=True))
   def test_checkout(charge):
       checkout(order)
       charge.assert_called_once_with(order.total)
   ```

   Главные правила:

   * **патчить там, где имя используется**, а не где определено
     (`app.services.requests`, а не `requests`);
   * проверять взаимодействие (`assert_called_once_with`), а не только
     результат, — но не превращать тест в копию реализации;
   * использовать `autospec=True`/`create_autospec`, иначе мок примет любой
     вызов с любыми аргументами и тест продолжит проходить после изменения
     сигнатуры;
   * предпочитать внедрение зависимости патчам — тогда моки почти не нужны;
   * не мокать то, что тестируешь, и не мокать всё подряд: связка «моки везде»
     даёт зелёные тесты при сломанном приложении.

   Термины рядом: stub (только возвращает значения), fake (упрощённая рабочая
   реализация — например, in-memory репозиторий), spy (следит за реальным
   объектом), mock (проверяет ожидания).

   </details>

1. Какие есть способы расширить модель пользователя в Django?
   <details>
   <summary>Ответ</summary>

   Четыре способа, от самого гибкого:

   1. **`AbstractUser`** — наследуемся и добавляем поля, вся логика стандартного
      пользователя сохраняется. Самый частый выбор.
   2. **`AbstractBaseUser`** (+ `PermissionsMixin`) — полностью своя модель:
      вход по телефону вместо username, свои менеджеры и поля. Больше работы,
      максимум контроля.
   3. **Профиль отдельной моделью** с `OneToOneField(User)` — если менять саму
      модель нельзя (проект уже в проде и миграция болезненна).
   4. **Прокси-модель** — когда нужны только другие методы и `Meta`, без новых
      полей.

   ```python
   class User(AbstractUser):
       phone = models.CharField(max_length=20, blank=True)

   # settings.py
   AUTH_USER_MODEL = 'accounts.User'
   ```

   Практика: свою модель пользователя объявляют **в самом начале проекта** —
   менять `AUTH_USER_MODEL` потом крайне неприятно. В коде на неё ссылаются
   через `settings.AUTH_USER_MODEL` (в моделях) и `get_user_model()` (в
   остальном коде), а не импортом `django.contrib.auth.models.User`.

   </details>

1. Что такое класс `BaseView` и для чего он используется?
   <details>
   <summary>Ответ</summary>

   Речь про class-based views в Django: базовый класс `View`, от которого
   происходят все остальные (`TemplateView`, `ListView`, `DetailView`,
   `CreateView`, `FormView`), а в DRF — `APIView` и `GenericAPIView`.

   ```python
   class BaseView(LoginRequiredMixin, View):
       def get_context(self, **kwargs):
           return {'user': self.request.user, **kwargs}
   ```

   Для чего используется: переиспользование поведения через наследование и
   миксины вместо копирования кода во функции-представления — пагинация,

   в непрозрачную иерархию, поэтому для простой логики функциональное
   представление часто читается лучше.

1. Как бы ты описал модель проектирования Django? Какие конструкции использует Django?
   <details>
   <summary>Ответ</summary>

   Django — «batteries included» фреймворк с архитектурой **MTV** (Model —
   Template — View), которая по сути является вариантом MVC: `Model` — данные,
   `Template` — представление, `View` — контроллер (логика обработки запроса), а
   роль «view» из MVC играет сам фреймворк с его маршрутизацией.

   Ключевые конструкции: модели и миграции (ORM с ActiveRecord-подходом),
   `QuerySet` с ленивыми запросами, приложения (`apps`) как единица модульности,
   URL-роутинг, представления (функции и CBV), формы и валидация, шаблоны,
   миксины, middleware (цепочка обработки запроса), сигналы (события), менеджеры
   и `django-admin`, а также DRF для API (сериализаторы, вьюсеты, роутеры,
   permissions).

   Полезные добавления: Django следует принципам DRY и «convention over
   configuration», из коробки даёт админку, аутентификацию, CSRF-защиту и
   миграции; за это платят связанностью — сущности часто зависят от ORM. Поэтому
   в больших проектах бизнес-логику выносят в сервисный слой, а не держат в
   моделях и представлениях.

   </details>

1. Как реализовать систему избранного в интернет-магазине на Django?
   <details>
   <summary>Ответ</summary>

   Основа — связь «многие ко многим» между пользователем и товаром через явную
   промежуточную модель:

   ```python
   class Favorite(models.Model):
       user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE,
                                related_name='favorites')
       product = models.ForeignKey(Product, on_delete=models.CASCADE)
       created_at = models.DateTimeField(auto_now_add=True)

       class Meta:
           constraints = [
               models.UniqueConstraint(fields=['user', 'product'],
                                       name='favorite_unique'),
           ]
           indexes = [models.Index(fields=['user', '-created_at'])]
   ```

   Ручки: `POST /favorites` (или идемпотентный toggle), `DELETE
   /favorites/<product_id>`, `GET /favorites` со `select_related('product')` и
   пагинацией.

   Что важно проговорить: `UniqueConstraint` вместо проверки в коде (двойной
   клик), `get_or_create`/`ON CONFLICT DO NOTHING` для идемпотентности, проверка
   прав (пользователь работает только со своими записями), для анонимных
   пользователей — сессия или localStorage с переносом в базу после логина,
   счётчик избранного в списке товаров одним запросом с аннотацией, кэш при
   больших объёмах.

   </details>

1. Как устроена система авторизации в Django?
   <details>
   <summary>Ответ</summary>

   Из коробки Django даёт `django.contrib.auth`:

   * **модель пользователя** с хэшированием пароля (PBKDF2 по умолчанию, можно
     Argon2), `check_password`, валидаторы пароля;
   * **бэкенды аутентификации** (`AUTHENTICATION_BACKENDS`) — `authenticate()`
     перебирает их; можно добавить вход по email, LDAP, OAuth (allauth);
   * **сессии**: после `login()` в базе (или Redis) создаётся сессия, клиенту
     уходит `sessionid` в cookie; `AuthenticationMiddleware` подкладывает
     `request.user`;
   * **права и группы**: `Permission` (автоматически по CRUD на каждую модель),
     `Group`, проверки `user.has_perm('app.change_order')`, декораторы
     `@login_required`, `@permission_required`, миксины `LoginRequiredMixin`,
     `PermissionRequiredMixin`;
   * в DRF — свои `authentication_classes` (сессии, токены, JWT) и
     `permission_classes`, включая объектные права.

   Что стоит добавить: стандартные права работают на уровне модели, а не
   объекта, — для «редактировать только свои заказы» нужны проверки в коде или
   библиотеки (`django-guardian`, `rules`); плюс CSRF-защита для форм,
   ограничение попыток входа (`django-axes`) и 2FA отдельными пакетами.

   </details>

1. Как реализовать корзину для интернет-магазина в Django?
   <details>
   <summary>Ответ</summary>

   Два варианта хранения:

   * **Сессия** — для анонимных пользователей: словарь `{product_id: qty}` в
     `request.session`, ничего не пишем в базу. Просто и быстро, но корзина не
     переживает смену устройства.
   * **Модели в базе** — для авторизованных: `Cart` и `CartItem` с
     `UniqueConstraint(cart, product)`. Сохраняется между устройствами, можно
     считать аналитику брошенных корзин.

   Рабочая схема — гибрид: анонимная корзина в сессии, при логине переносится в
   базу (мерж по товарам).

   ```python
   class CartItem(models.Model):
       cart = models.ForeignKey(Cart, on_delete=models.CASCADE, related_name='items')
       product = models.ForeignKey(Product, on_delete=models.PROTECT)
       qty = models.PositiveIntegerField(default=1)
       price = models.DecimalField(max_digits=10, decimal_places=2)  # фиксируем
   ```

   Что важно проговорить на интервью:

   * **цену нельзя брать с клиента** — только из базы; в заказе цену фиксируют
     на момент оформления (в корзине обычно показывают актуальную);
   * количество проверять по остаткам, а списывать резерв в транзакции при
     оформлении (`select_for_update`), иначе два покупателя купят последний
     товар;
   * `on_delete=PROTECT` для товара в заказе, чтобы история не разъехалась;
   * идемпотентность «добавить в корзину» (`get_or_create` + `F('qty') + 1`);
   * расчёт итогов одним запросом с агрегацией, `select_related` против N+1;
     деньги — `Decimal`, не `float`.

   </details>

### Безопасность

1. Какие типы `XSS` уязвимости ты знаешь?
   <details>
   <summary>Ответ</summary>

   * **Stored (persistent)** — код сохраняется на сервере (комментарий, профиль,
     название товара) и исполняется у всех, кто открыл страницу. Самый опасный.
   * **Reflected** — приходит в параметрах запроса и сразу попадает в ответ:
     жертву надо заманить по ссылке.
   * **DOM-based** — сервер не при чём: фронтенд берёт данные из
     `location.hash`, `document.referrer` или ответа API и вставляет их в
     `innerHTML`.

   Ещё различают Self-XSS (пользователя убеждают вставить код в консоль) и
   mutation XSS (mXSS), где браузер при парсинге «исправляет» разметку так, что
   безопасная строка становится опасной.

   Защита во всех случаях: экранирование при выводе по контексту (шаблоны Django
   и Jinja2 делают это автоматически, опасны `|safe` и `mark_safe`), санитайзер
   с белым списком для HTML от пользователя (bleach, nh3), `textContent` вместо
   `innerHTML`, CSP и cookie с `HttpOnly`.

   </details>

1. Какие типы `SQLi` уязвимости ты знаешь?
   <details>
   <summary>Ответ</summary>

   По способу получения данных:

   * **In-band** — результат виден в ответе: error-based (данные в тексте
     ошибки) и union-based (`UNION SELECT`).
   * **Blind** — ответ данных не показывает, но зависит от условия:
     boolean-based (страница меняется) и time-based (`pg_sleep`, `SLEEP()` —
     результат видно по задержке).
   * **Out-of-band** — данные утекают по другому каналу (DNS, HTTP-запрос из
     базы).

   По месту внедрения: в `WHERE`, в `ORDER BY` и `LIMIT` (частая ошибка — эти
   места нельзя параметризовать, нужен белый список), в имени таблицы или
   колонки, second-order (данные сохранились безопасно, а инъекция срабатывает
   позже, при подстановке в другой запрос).

   Защита одна и та же: параметризованные запросы и ORM, белый список для
   нештатных мест (сортировка, имена колонок), минимальные права пользователя
   базы, аккуратность с `raw`, `extra`, `RawSQL` и `text()`.

   </details>

1. Знаком с OWASP? Какая цель у этого проекта и чем он полезен разработчикам?
   <details>
   <summary>Ответ</summary>

   OWASP (Open Worldwide Application Security Project) — некоммерческий проект,
   который делает открытые материалы и инструменты по безопасности приложений.

   Что полезно разработчику: **OWASP Top 10** (рейтинг самых распространённых
   рисков — общий язык на ревью и в требованиях), **Cheat Sheet Series**
   (короткие практические руководства: пароли, JWT, SQLi, XSS, загрузка файлов),
   **ASVS** (чеклист требований, по которому можно проверять проект),
   **Dependency-Check** и **ZAP** (сканеры), **SAMM** (зрелость процессов),
   **Juice Shop** (намеренно уязвимое приложение для тренировки).

   Цель проекта — сделать безопасность видимой и воспроизводимой: не «эксперт
   что-то знает», а понятные списки требований и проверок, встроенные в
   разработку.

   </details>

1. Расскажи про OWASP Top 10. Какие самые популярные уязвимости в этом рейтинге?
   <details>
   <summary>Ответ</summary>

   Актуальный список (редакция 2021 года):

   1. **Broken Access Control** — на первом месте: IDOR, отсутствие проверки
      прав, обход через прямой URL.
   2. **Cryptographic Failures** — нет TLS, слабые алгоритмы, пароли не через
      `bcrypt`/`argon2`, секреты в репозитории.
   3. **Injection** — SQL, команды ОС, LDAP, а также XSS (в этой редакции он
      отнесён сюда).
   4. **Insecure Design** — изъяны самой схемы: нет ограничения попыток, нет
      подтверждения смены email, доверие к данным клиента.
   5. **Security Misconfiguration** — `DEBUG = True` в проде, дефолтные пароли,
      открытая админка, `.git` в вебруте.
   6. **Vulnerable and Outdated Components** — старые зависимости (`pip-audit`,
      Dependabot).
   7. **Identification and Authentication Failures** — слабая аутентификация,
      фиксация сессии, отсутствие 2FA и защиты от перебора.
   8. **Software and Data Integrity Failures** — небезопасная десериализация
      (`pickle`, `yaml.load`), пакеты из ненадёжных источников.
   9. **Security Logging and Monitoring Failures** — инцидент не виден в логах.
   10. **SSRF** — сервер по просьбе клиента ходит во внутреннюю сеть.

   Стоит отметить, что первое место занимает контроль доступа, а не инъекции:
   типовая ошибка — проверять права только в интерфейсе и доверять `id` из
   запроса.

   </details>

### Задачи

1. Как написать скрипт для скачивания 1000 картинок? Какие подходы лучше (асинхронно, несколько потоков и т.д.)?
   <details>
   <summary>Ответ</summary>

   Скачивание — задача I/O-bound, значит потоки или `asyncio`, а не процессы
   (GIL при ожидании сети отпускается).

   ```python
   import asyncio, aiohttp

   async def fetch(session, url, sem):
       async with sem:                      # ограничиваем параллельность
           async with session.get(url, timeout=aiohttp.ClientTimeout(30)) as r:
               r.raise_for_status()
               return await r.read()

   async def main(urls):
       sem = asyncio.Semaphore(20)
       async with aiohttp.ClientSession() as session:
           tasks = [fetch(session, u, sem) for u in urls]
           return await asyncio.gather(*tasks, return_exceptions=True)
   ```

   Что сказать про подходы:

   * **`asyncio` + aiohttp/httpx** — лучший выбор при тысячах URL: один поток,
     минимум накладных расходов, легко ограничить параллельность семафором.
   * **`ThreadPoolExecutor`** (`max_workers=20`) с `requests` — почти так же
     эффективно и проще пишется, если код уже синхронный.
   * **Процессы** — только если после скачивания идёт тяжёлая обработка (ресайз,
     кодеки): скачиваем асинхронно, обрабатываем в `ProcessPoolExecutor`.

   Что обязательно упомянуть: ограничение параллельности (не 1000 запросов
   сразу), таймауты, ретраи с экспоненциальной задержкой на 5xx и таймауты,
   переиспользование сессии и пула соединений, потоковая запись на диск
   (`iter_content`/`stream`), проверка `Content-Type` и размера, санитизация
   имён файлов, идемпотентность (не скачивать уже скачанное), логирование неудач
   и вежливость к серверу (rate limit, `robots.txt`).

   </details>

1. Как бы ты оптимизировал скрипт для скачивания изображений и сделал из него микросервис?
   <details>
   <summary>Ответ</summary>

   Оптимизация: асинхронные запросы с ограничением параллельности,
   переиспользуемая сессия с пулом соединений, таймауты и ретраи с
   экспоненциальной задержкой, потоковая запись без загрузки файла целиком в
   память, дедупликация по хэшу URL или содержимого, кэш уже скачанного,
   батчирование и алгоритмический предел скорости (rate limit) на домен.

   Микросервис: HTTP-ручка только принимает задачу и сразу отвечает, работа
   уходит в очередь.

   ```text
   POST /jobs {urls: [...]} -> 202 Accepted, job_id
          |
          v
     Redis/RabbitMQ  ->  воркеры (Celery/arq)  ->  S3/MinIO
                                               ->  статус в PostgreSQL
   GET /jobs/{id} -> прогресс и ссылки на результат
   ```

   Что важно проговорить: FastAPI + `asyncio` для ручек, Celery или arq для
   воркеров, объектное хранилище вместо локального диска (иначе не
   масштабируется), идемпотентность задач и ключ дедупликации, ретраи и
   dead-letter, ограничение размера и типа файлов, метрики (Prometheus) и
   трейсинг, health-check, горизонтальное масштабирование воркеров, SSRF-защита
   (валидация URL, запрет внутренних адресов) — при скачивании по
   пользовательскому URL это обязательный пункт.

   </details>

1. Как реализовать обработку изображений в таком микросервисе?
   <details>
   <summary>Ответ</summary>

   Обработка (ресайз, конвертация, водяной знак) — CPU-bound, поэтому её выносят
   из event loop:

   ```python
   from concurrent.futures import ProcessPoolExecutor
   from PIL import Image

   def make_thumbnail(raw: bytes) -> bytes:      # синхронная CPU-работа
       img = Image.open(io.BytesIO(raw))
       img.thumbnail((512, 512))
       out = io.BytesIO(); img.save(out, format='WEBP', quality=82)
       return out.getvalue()

   # в асинхронном коде
   loop.run_in_executor(process_pool, make_thumbnail, raw)
   ```

   Схема: воркер очереди скачивает файл, обрабатывает в пуле процессов (или
   отдельный тип воркеров под обработку), результат складывает в S3, метаданные
   в базу. Пул процессов по числу ядер; для тяжёлых задач — отдельная очередь и
   отдельный деплой, чтобы не конкурировать со скачиванием.

   Что важно упомянуть: библиотеки (Pillow / Pillow-SIMD, `libvips` через pyvips
   — заметно быстрее и экономнее по памяти, ImageMagick), лимиты на размер и
   разрешение (защита от «бомб» — `Image.MAX_IMAGE_PIXELS`,
   `DecompressionBombError`), проверка реального типа файла, а не расширения,
   удаление EXIF, генерация нескольких размеров и WebP/AVIF, идемпотентность по
   хэшу исходника, таймауты на задачу, изоляция обработки недоверенных файлов, и
   вариант «отдать это на CDN с ресайзом на лету», если своя обработка не нужна.

   </details>

1. Как написать код для подсчета четных чисел в списке?
   <details>
   <summary>Ответ</summary>

   ```python
   numbers = [1, 2, 3, 4, 5, 6]

   count = sum(1 for n in numbers if n % 2 == 0)     # 3, без лишнего списка
   count = len([n for n in numbers if n % 2 == 0])   # тоже верно, но создаёт список
   ```

   Оба варианта — `O(n)` по времени; генераторное выражение не выделяет память
   под промежуточный список. Классическая ошибка — `sum(n for n in numbers if n
   % 2 == 0)`: это сумма чётных, а не их количество.

   Если спросят про большие данные или потоки — тот же генератор, но по
   итератору (файл, курсор базы) вместо списка; если про отрицательные числа —
   `n % 2 == 0` работает и для них (в Python остаток неотрицательный).

   </details>

1. Как работать с запросами, которые внезапно стали медленнее, особенно с `JOIN`?
   <details>
   <summary>Ответ</summary>

   Алгоритм: воспроизвести, снять план, найти самый дорогой узел, проверить
   статистику и индексы, посмотреть, что изменилось.

   Что смотреть в первую очередь:

   * `EXPLAIN (ANALYZE, BUFFERS)` — расхождение оценки строк с фактической
     говорит об устаревшей статистике (`ANALYZE`), Seq Scan по большой таблице с
     селективным условием — об отсутствии индекса, `Sort ... Disk` — о малом
     `work_mem`;
   * **что изменилось**: выросли данные (план, оптимальный на 10 тысячах строк,
     плох на 10 миллионах), поменялся код или ORM-запрос, добавились индексы
     или, наоборот, распухли таблицы (`VACUUM`), появились блокировки;
   * `pg_stat_statements` и slow query log — какие запросы съедают время;
   * `pg_stat_activity` и `pg_locks` — не ждём ли мы блокировку.

   Что делать с `JOIN`: порядок соединений выбирает планировщик, поэтому
   переписывать его вручную бессмысленно; полезнее — индексы на колонки
   соединения (в PostgreSQL внешний ключ индекс не создаёт), уменьшение объёма
   до соединения (фильтр в подзапросе или CTE), замена `Nested Loop` на `Hash
   Join` за счёт корректной статистики, отказ от `SELECT *`, денормализация или
   материализованное представление для тяжёлой аналитики.

   Со стороны Python: проверить N+1 (`select_related`, `prefetch_related`,
   `joinedload`), лишние запросы в цикле, отсутствие пагинации, `count()` на
   огромной таблице.

   </details>

1. Как обработать исключения при работе с файлами в Python (отсутствие файла, другие ошибки)?
   <details>
   <summary>Ответ</summary>

   Через `with` (файл закроется всегда) и перехват конкретных исключений, а не
   `except Exception`:

   ```python
   from pathlib import Path

   try:
       text = Path(path).read_text(encoding='utf-8')
   except FileNotFoundError:
       logger.warning('нет файла %s', path)
       text = ''
   except PermissionError:
       raise                      # это ошибка конфигурации, пусть падает
   except UnicodeDecodeError:
       text = Path(path).read_text(encoding='cp1251', errors='replace')
   except OSError as exc:         # общий предок IO-ошибок: диск, сеть, дескрипторы
       logger.exception('не смогли прочитать %s', exc)
       raise
   ```

   Что стоит проговорить: иерархия — `OSError` (он же `IOError`) с подклассами
   `FileNotFoundError`, `PermissionError`, `FileExistsError`,
   `IsADirectoryError`, `NotADirectoryError`, `InterruptedError`; отдельно
   `UnicodeDecodeError` и `json.JSONDecodeError` при разборе содержимого.

   Практики: не проверять существование заранее (`os.path.exists` + открытие —
   это гонка, лучше EAFP — «просто попробуй»), всегда указывать `encoding`,
   использовать `pathlib`, для атомарной записи писать во временный файл и
   делать `os.replace`, в `finally` или контекстном менеджере убирать за собой,
   логировать с трассировкой (`logger.exception`), не глотать исключение молча.

   </details>

1. Как реализовать обращение к API с ограничением по времени и количеству потоков?
   <details>
   <summary>Ответ</summary>

   Три ограничения: таймаут на запрос, предел параллельности и предел скорости
   (rate limit).

   ```python
   import asyncio, httpx

   async def worker(client, url, sem, limiter):
       async with sem:                                   # не больше N параллельно
           await limiter.acquire()                       # не больше R запросов/сек
           for attempt in range(3):                      # ретраи
               try:
                   r = await client.get(url, timeout=httpx.Timeout(5.0))
                   r.raise_for_status()
                   return r.json()
               except (httpx.TimeoutException, httpx.HTTPStatusError):
                   await asyncio.sleep(2 ** attempt)     # экспоненциальная задержка
           raise RuntimeError(f'не удалось получить {url}')

   async def main(urls):
       sem = asyncio.Semaphore(10)
       async with httpx.AsyncClient() as client:
           return await asyncio.gather(*(worker(client, u, sem, limiter)
                                         for u in urls))
   ```

   Синхронный вариант — `ThreadPoolExecutor(max_workers=10)` плюс
   `requests.Session` с `HTTPAdapter(max_retries=Retry(...))` и общий таймаут
   через `concurrent.futures.wait(timeout=...)`.

   Что важно упомянуть: таймаут задаётся раздельно на соединение и на чтение;
   общий дедлайн на всю операцию (`asyncio.timeout`); ретраи только на
   идемпотентные запросы и на `429`/`5xx`, с учётом `Retry-After`; алгоритм
   token bucket для rate limit (`aiolimiter`); circuit breaker, чтобы не
   добивать упавший сервис; ограничение параллельности на домен, а не глобально;
   логирование и метрики по времени ответа и ошибкам.

   </details>
