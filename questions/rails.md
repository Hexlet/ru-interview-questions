## Junior

### Общие вопросы

1. Почему ты решил стать бэкенд-разработчиком, чем тебя привлекает профессия?
   <details>
   <summary>Ответ</summary>

   Проверяют осознанность выбора, а не «правильный» ответ.

   Как отвечать: связать интерес с содержанием работы — данные и их целостность,
   проектирование API, интеграции, нагрузка и надёжность. Хорошо привести
   момент, когда это стало понятно: делал интернет-магазин, разбирался, почему
   страница грузится 5 секунд, писал интеграцию с платёжной системой. Про Rails
   честно: скорость разработки, сильные соглашения (convention over
   configuration), зрелая экосистема гемов, приятный язык.

   </details>

1. Приходилось писать тесты и на чем?
   <details>
   <summary>Ответ</summary>

   RSpec (стандарт де-факто в Rails-проектах) или Minitest из коробки; рядом —
   FactoryBot вместо фикстур, Faker, `shoulda-matchers`, Capybara и Selenium для
   системных тестов, VCR или WebMock для внешних HTTP, SimpleCov для покрытия.

   Что стоит рассказать: какие уровни писал — модельные (валидации, скоупы,
   бизнес-методы), сервисные, request-спеки на контроллеры и API, системные на
   критичные сценарии; как изолировал внешние вызовы (WebMock, стабы); как
   работал с базой (`use_transactional_fixtures`, `DatabaseCleaner` для
   системных тестов); запускались ли тесты в CI и как долго идут.

   </details>

1. Знаком с пирамидой тестирования? Какие виды тестирования знаешь?
   <details>
   <summary>Ответ</summary>

   Пирамида: много быстрых юнит-тестов внизу, меньше интеграционных в середине,
   совсем немного медленных e2e сверху.

   ```text
         /\      системные (Capybara) — мало, медленно, хрупко
        /  \     request/интеграционные — контроллеры, база
       /____\    модельные и юнит — быстро, много, изолированно
   ```

   Идея: чем выше, тем дороже поддержка и медленнее прогон. Антипаттерны —
   «мороженое» (много системных и почти нет юнитов) и «песочные часы» (нет
   середины).

   Виды тестирования: юнит, интеграционные, e2e и системные, регрессионные,
   дымовые (smoke), приёмочные, контрактные, нагрузочные, безопасности,
   мутационные, а также ручное исследовательское.

   </details>

1. Приходилось профилировать код?
   <details>
   <summary>Ответ</summary>

   Если да — рассказать конкретный случай по схеме «симптом → инструмент →
   находка → результат». Если нет — описать, чем профилируют Rails:

   * **запросы к базе**: логи с временем, `bullet` (ловит N + 1 и лишний eager
     loading), `rack-mini-profiler`, `EXPLAIN ANALYZE`, `pg_stat_statements`;
   * **приложение**: `ruby-prof`, `stackprof`, `benchmark-ips` для
     микробенчмарков, `memory_profiler` и `derailed_benchmarks` для памяти и
     утечек;
   * **прод**: APM (New Relic, Scout, Skylight, Datadog), метрики в Prometheus +
     Grafana, Sentry Performance.

   Типовые находки в Rails: N + 1 запросы, отсутствующие индексы, сериализация
   больших коллекций, рендер партиалов в цикле без кэша, тяжёлые колбэки в
   моделях, синхронные внешние вызовы в контроллере.

   </details>

### Ruby

1. Какие типы данных в Ruby знаешь?
   <details>
   <summary>Ответ</summary>

   `Integer`, `Float`, `Rational`, `Complex`, `BigDecimal` (для денег),
   `String`, `Symbol`, `Array`, `Hash`, `Range`, `Regexp`, `Proc`,
   `TrueClass`/`FalseClass`, `NilClass`, `Set`, `Time`/`Date`, `Struct`.

   Особенности Ruby: всё является объектом, включая числа и `nil` (`nil.class` →
   `NilClass`); ложными считаются только `false` и `nil` (ноль и пустая строка —
   истина); целые числа произвольной точности; для денег берут `BigDecimal`, а
   не `Float`; строки изменяемы (в отличие от символов), но их можно заморозить
   (`freeze`, магический комментарий `# frozen_string_literal: true`).

   </details>

1. Чем тип данных символ отличается от строк?
   <details>
   <summary>Ответ</summary>

   Символ (`:name`) — иммутабельный идентификатор, для которого в памяти
   существует **один** объект на всю программу. Строка изменяема, и каждая
   литеральная строка создаёт новый объект.

   ```ruby
   :foo.object_id == :foo.object_id      # true — один и тот же объект
   'foo'.object_id == 'foo'.object_id    # false — два разных объекта
   :foo.to_s                             # "foo"
   'foo'.to_sym                          # :foo
   ```

   Где что использовать: символы — как ключи хэшей, имена методов и атрибутов,
   флаги и состояния (`status: :active`); строки — как данные, которые
   показываются пользователю и обрабатываются.

   Практические детали: сравнение символов быстрее (сравнение по идентичности),
   они экономят память при повторении; с Ruby 2.2 символы собираются сборщиком
   мусора, поэтому исторический риск «symbol DoS» при `to_sym` от пользователя
   стал меньше, но данные всё равно не превращают в символы бесконтрольно.

   </details>

1. Что вернётся в результате сложения `10.5` и `10`?
   <details>
   <summary>Ответ</summary>

   `20.5` — объект класса `Float`. Ruby приводит целое к числу с плавающей
   точкой (coercion), и результат «шире» по типу.

   ```ruby
   (10.5 + 10).class          # Float
   10 / 3                     # 3   — целочисленное деление
   10.0 / 3                   # 3.3333333333333335
   0.1 + 0.2 == 0.3           # false — двоичная плавающая арифметика
   BigDecimal('0.1') + BigDecimal('0.2') == BigDecimal('0.3')   # true
   ```

   Полезно добавить про подводный камень: `Float` нельзя использовать для денег
   из-за погрешности — берут `BigDecimal` или целые копейки; в Rails для этого
   есть тип `decimal` в миграциях.

   </details>

1. Чем отличаются `proc` от `lambda`
   <details>
   <summary>Ответ</summary>

   Оба — объекты класса `Proc`, но с разной семантикой (`lambda?` вернёт `true`
   только у lambda):

   ```ruby
   pr = proc   { |a, b| [a, b] }
   la = lambda { |a, b| [a, b] }

   pr.call(1)          # [1, nil] — аргументы не проверяются
   la.call(1)          # ArgumentError — строгая проверка арности

   def test
     proc   { return 1 }.call   # return выходит из метода test
     lambda { return 2 }.call   # return выходит только из lambda
     3
   end
   ```

   Итого два отличия: **арность** (proc прощает лишние и недостающие аргументы,
   lambda требует точного совпадения) и **поведение `return`** (в proc
   возвращает из объемлющего метода, в lambda — только из себя; аналогично
   различаются `break` и `next`).

   Практика: lambda ведёт себя как обычный метод — её берут, когда нужна функция
   с предсказуемым поведением (в том числе `->(x) { }` и скоупы Rails); proc
   уместен для блоков и колбэков, где важна гибкость.

   </details>

1. Что такое блок? Что такое `yield`? Можно ли передавать блоки в методы? Каким образом?
   <details>
   <summary>Ответ</summary>

   Блок — кусок кода в `{ }` или `do..end`, который передаётся методу. Это не
   объект (пока не превращён в `Proc`), поэтому блок может быть только один и
   записывается особым синтаксисом.

   ```ruby
   def each_twice(items)
     items.each do |item|
       yield item          # вызов переданного блока
       yield item
     end
   end

   each_twice([1, 2]) { |x| puts x }
   ```

   Способы передать блок в метод:

   ```ruby
   def a       = yield(1)                       # неявно, через yield
   def b(&blk) = blk.call(1)                    # явно, &block -> Proc
   def c(pr)   = pr.call(1)                     # передать Proc/lambda аргументом
   def d(&blk) = [1, 2].each(&blk)              # прокинуть блок дальше
   [1, 2].map(&:to_s)                            # symbol to_proc
   ```

   Полезные детали: `block_given?` проверяет, передан ли блок; блок — это
   замыкание, он видит переменные из места объявления; `yield` без блока бросает
   `LocalJumpError`. На блоках построены все итераторы (`each`, `map`), работа с
   ресурсами (`File.open`), конфигурация (`Rails.application.configure`) и DSL.

   </details>

1. Как происходит наследование в Ruby?
   <details>
   <summary>Ответ</summary>

   Одиночное наследование классов через `<`; поиск метода идёт по цепочке
   предков (`ancestors`): сам класс → подключённые модули (в порядке, обратном
   включению) → суперкласс → его модули → … → `Object` → `Kernel` →
   `BasicObject`.

   ```ruby
   class Animal
     def speak = 'generic'
   end

   class Dog < Animal
     def speak = "woof, not #{super}"    # super вызывает метод предка
   end

   Dog.ancestors   # [Dog, Animal, Object, Kernel, BasicObject]
   ```

   Детали: `super` без скобок передаёт те же аргументы, `super()` — ни одного;
   наследуются и методы класса; `Class.new(Parent)` создаёт класс динамически;
   методы можно переопределить в любой момент (открытые классы). Практика: как и
   везде, композиция и модули часто предпочтительнее глубоких иерархий.

   </details>

1. Есть ли в Ruby множественное наследование если нет чем можно заменить?
   <details>
   <summary>Ответ</summary>

   Множественного наследования классов нет — только один суперкласс. Вместо него
   используются **модули (миксины)**: их можно подключить сколько угодно.

   ```ruby
   module Trackable
     def track!(event) = events.create!(name: event)
   end

   module Archivable
     def archive! = update!(archived_at: Time.current)
   end

   class Order < ApplicationRecord
     include Trackable
     include Archivable
   end
   ```

   Как разрешается неоднозначность: модули встают в цепочку предков в
   определённом порядке (последний подключённый — ближе к классу), поэтому
   «ромбовидной проблемы» не возникает — есть однозначный линейный порядок
   (`Order.ancestors`).

   Альтернативы модулям: композиция и делегирование (`Forwardable`, `delegate` в
   Rails), объекты-сервисы. Оговорка про модули: они удобны, но легко
   превращаются в свалку методов с неявным доступом к состоянию класса, поэтому
   для сложного поведения лучше отдельный объект.

   </details>

1. Модули что такое зачем нужны, `extend`, `include`, `prepend` - в чем отличие
   <details>
   <summary>Ответ</summary>

   Модуль — контейнер для методов и констант. Две роли: пространство имён
   (`Admin::UsersController`) и миксин (переиспользование поведения без
   наследования).

   Разница трёх способов подключения:

   ```ruby
   module Greet
     def hello = 'hello'
   end

   class A; include Greet; end     # методы экземпляра: A.new.hello
   class B; extend  Greet; end     # методы класса:     B.hello
   class C
     def hello = 'own'
     prepend Greet                  # модуль встаёт ПЕРЕД классом
   end
   C.new.hello                      # 'hello' — из модуля, класс перекрыт
   ```

   * **`include`** — модуль встаёт в цепочку предков **после** класса: методы
     класса приоритетнее.
   * **`extend`** — методы становятся методами объекта (для класса — методами
     класса); `obj.extend(M)` работает и для отдельного объекта.
   * **`prepend`** — модуль встаёт **перед** классом, поэтому его методы
     перекрывают одноимённые методы класса и могут вызвать их через `super`. Это
     цивилизованная замена манкипатчингу с `alias_method_chain`.

   Проверить порядок всегда можно через `ancestors`. Рядом полезно знать
   `ActiveSupport::Concern` — он решает проблему зависимостей между модулями и
   даёт блок `class_methods`/`included`.

   </details>

1. Какие ORM знаешь и какие использовал? Какие плюсы и минусы можешь выделить?
   <details>
   <summary>Ответ</summary>

   В Rails-мире это прежде всего **ActiveRecord** (реализация паттерна
   ActiveRecord: объект — строка таблицы, и он же знает, как себя сохранить);
   рядом — **Sequel** (гибче и ближе к SQL) и **ROM.rb**; из не-Ruby-опыта
   уместно упомянуть Hibernate, SQLAlchemy, Doctrine, Prisma.

   **Плюсы ActiveRecord**: очень быстрое написание CRUD, миграции, скоупы,
   валидации и колбэки, ассоциации, `includes` против N + 1, поддержка
   нескольких баз, читаемый DSL.

   **Минусы**: генерируемый SQL неочевиден (N + 1, лишние `SELECT`), колбэки в
   моделях легко превращаются в неявную бизнес-логику, «толстые модели» и
   анемичные сервисы, плохо ложатся массовые операции (нужны `insert_all`,
   `upsert_all`, `update_all`), тяжёлая аналитика пишется на SQL, инстанциация
   большого числа объектов дорога по памяти (`pluck` и `find_each` вместо
   `all.map`).

   Практика: ActiveRecord для CRUD и доменной логики, `pluck`/`select` для
   больших выборок, чистый SQL или представления — для отчётов.

   </details>

1. Что такое Манкипатчинг? Применял ли?
   <details>
   <summary>Ответ</summary>

   Манкипатчинг — изменение поведения существующего класса или модуля во время
   выполнения: доопределение или переопределение методов «извне», в том числе у
   стандартной библиотеки и гемов.

   ```ruby
   # добавляем метод в String — это и есть манкипатч
   class String
     def slugify = downcase.strip.gsub(/[^a-z0-9]+/, '-')
   end
   ```

   Зачем применяют: срочно починить баг в геме, подпилить поведение библиотеки,
   добавить удобный метод, инструментировать код (APM-агенты так и работают).

   Почему это опасно: изменение видно всему процессу, конфликт двух патчей
   одного метода отлаживается тяжело, обновление гема ломает патч, а читающий
   код не понимает, откуда взялся метод.

   Как делать аккуратнее: `Module#prepend` с `super` вместо перезаписи,
   refinements (`refine`/`using`) для локальной области, отдельный
   объект-обёртка или декоратор, а в Rails — `ActiveSupport::Concern` и
   `app/lib` вместо патчей ядра. Если патч всё же нужен — держать его в одном
   файле с комментарием, зачем он и когда его можно убрать.

   </details>

### Rails

1. Ассоциации (один к одному, один ко многим, многие ко многим) — как реализовать на уровне БД и на уровне Rails-моделей?
   <details>
   <summary>Ответ</summary>

   На уровне базы всё сводится к внешним ключам и ограничениям, на уровне Rails
   — к объявлениям ассоциаций.

   ```ruby
   # один ко многим
   class User  < ApplicationRecord; has_many :posts; end
   class Post  < ApplicationRecord; belongs_to :user; end

   # один к одному
   class User    < ApplicationRecord; has_one :profile; end
   class Profile < ApplicationRecord; belongs_to :user; end

   # многие ко многим через явную модель
   class Student < ApplicationRecord
     has_many :enrollments
     has_many :courses, through: :enrollments
   end
   class Enrollment < ApplicationRecord
     belongs_to :student
     belongs_to :course
   end
   ```

   Миграция:

   ```ruby
   create_table :posts do |t|
     t.references :user, null: false, foreign_key: true   # индекс + FK
   end
   add_index :profiles, :user_id, unique: true            # для has_one
   add_index :enrollments, %i[student_id course_id], unique: true
   ```

   Что важно проговорить: `t.references` создаёт индекс, но целостность даёт
   именно `foreign_key: true`; для `has_one` и «многие ко многим» нужен
   уникальный индекс, иначе появятся дубликаты; `has_and_belongs_to_many` без
   модели-связки берут редко (нельзя добавить поля и валидации); `dependent:
   :destroy` (колбэки, медленно) против `dependent: :delete_all` и `on_delete:
   :cascade` в базе; `inverse_of` и `counter_cache` — против лишних запросов.

   </details>

### Задачки на код

1. Есть два приложения между ними шина данных(Kafka, RabbitMQ, gRPC), из одного в другой пришли кривые данные, как будешь дебажить?
   <details>
   <summary>Ответ</summary>

   Отвечать надо алгоритмом, а не догадками. Ключевая мысль: сначала
   зафиксировать факт и найти исходное сообщение, потом определить, кто его
   испортил — продюсер, транспорт или консьюмер.

   1. **Зафиксировать симптом**: что именно «кривое» — отсутствующие поля,
      неверные типы, битая кодировка, дубли, неправильный порядок, устаревшие
      данные.
   2. **Найти сообщение целиком**: по `correlation_id`/`message_id` в логах
      обоих сервисов; в Kafka — прочитать нужный offset
      (`kafka-console-consumer` с `--partition` и `--offset`), в RabbitMQ —
      посмотреть очередь или dead-letter.
   3. **Сравнить три точки**: что было в базе продюсера, что он отправил, что
      получил консьюмер. Это сразу отсекает половину гипотез.
   4. **Проверить контракт и схему**: разошлись версии, поле стало опциональным,
      поменялся сериализатор, отсутствует Schema Registry, изменилась кодировка
      или формат даты.
   5. **Проверить типовые причины**: продюсер отправляет до коммита транзакции
      (нужен outbox); нет ключа партиционирования, поэтому порядок событий
      нарушен; ретраи дали дубли и обработчик не идемпотентен; консьюмер
      обрабатывает несколько сообщений параллельно и перетирает состояние; `nil`
      вместо значения из-за ленивой ассоциации; часовые пояса.
   6. **Инструменты**: сквозной trace id (OpenTelemetry), структурированные
      логи, dead-letter очередь с исходным телом, метрики лага консьюмера.

   Что предложить дальше: валидация схемы на входе и выходе (JSON Schema, Avro,
   protobuf), контрактные тесты, отправка события через transactional outbox,
   идемпотентность по ключу, dead-letter вместо «проглотить и поехать дальше».

   </details>

2. Есть таблица `posts` и таблица `comments`, связь один ко многим, в таблице `comments` вторичный ключ `post_id` - напиши запрос который вытащит все посты у которых > 3 комментариев и дата создания поста после 20 ноября
   <details>
   <summary>Ответ</summary>

   ```sql
   select p.*
   from posts p
   join comments c on c.post_id = p.id
   where p.created_at > '2025-11-20'
   group by p.id
   having count(c.id) > 3;
   ```

   Тот же запрос на ActiveRecord:

   ```ruby
   Post.joins(:comments)
       .where('posts.created_at > ?', Date.new(2025, 11, 20))
       .group('posts.id')
       .having('count(comments.id) > 3')
   ```

   Что стоит проговорить:

   * фильтр по дате — в `WHERE` (до группировки), а условие по количеству — в
     `HAVING` (после);
   * `group by p.id` достаточно в PostgreSQL при `select p.*`, потому что `id` —
     первичный ключ (в MySQL с `ONLY_FULL_GROUP_BY` тоже работает);
   * альтернатива без группировки — подзапрос или счётчик: `where('(select
     count(*) from comments where post_id = posts.id) > 3')`, а на больших
     объёмах — `counter_cache` (колонка `comments_count`) с индексом, чтобы не
     считать каждый раз;
   * нужны индексы: `comments(post_id)` и `posts(created_at)`;
   * «дата после 20 ноября» — уточнить год и включительно ли; и помнить про
     часовой пояс (`Time.zone`), если колонка `timestamptz`.

   </details>

3. Есть новые данные вот такой структуры

    number: 'H1111',

  И им соответствуют модели

  ```ruby
  class Order < ApplicationRecord
    has_many :positions
  end

  class Position < ApplicationRecord
    belongs_to :order
  end
  ```

  Нужно в соответствии с этими данными обновить таблицу `Orders` в которой 100_000 записей
   <details>
   <summary>Ответ</summary>

   Ключевая мысль: 100 000 записей нельзя обновлять по одной в цикле — это 100
   000 `UPDATE` плюс колбэки и валидации на каждую запись. Нужны батчи и
   массовые операции.

   ```ruby
   ActiveRecord::Base.transaction do
     data.each_slice(1_000) do |batch|
       Order.upsert_all(
         batch.map { |o| { id: o[:id], number: o[:number],
                        updated_at: Time.current } },
         unique_by: :id,
       )

       positions = batch.flat_map do |o|
         o[:position].map do |p|
           { id: p[:id], order_id: o[:id], name: p[:name],
             cost: p[:cost], updated_at: Time.current }
         end
       end
       Position.upsert_all(positions, unique_by: :id) if positions.any?
     end
   end
   ```

   Что важно сказать на интервью.

   `upsert_all` и `insert_all` работают одним запросом (`ON CONFLICT DO
   UPDATE`), но **не вызывают** валидации и колбэки — значит целостность должна
   обеспечиваться базой (`NOT NULL`, `FOREIGN KEY`, уникальные индексы), а
   `created_at` и `updated_at` надо заполнять самому.

   Батчи берут по 500–5000 записей: одна огромная транзакция держит блокировки и
   раздувает WAL. Если данные приходят потоком, читать их надо лениво, а не
   разбирать весь файл в память, и всю работу выносить в фоновую задачу
   (Sidekiq, ActiveJob) с идемпотентностью и прогрессом.

   Мелочи, которые тоже спросят: `cost` — это деньги, поэтому колонка `decimal`,
   а не `float`; для чтения существующих записей — `pluck` и `find_each` вместо
   `Order.all.map`; по возможности обновлять только изменившееся (сравнение по
   хэшу или `updated_at` источника), а на очень больших объёмах — загрузка во
   временную таблицу через `COPY` и один `UPDATE ... FROM`.

   </details>

### Общие вопросы

1. Достаточно ли валидации в ORM при реализации проверки на уникальность, например, email при регистрации? Раскройте
   <details>
   <summary>Ответ</summary>

   Нет, недостаточно. `validates :email, uniqueness: true` — это `SELECT` перед
   `INSERT`, между ними есть окно: два параллельных запроса оба увидят
   «свободно» и оба вставят запись. При нескольких процессах Puma это происходит
   регулярно — двойной клик по кнопке уже воспроизводит проблему. Rails об этом
   честно пишет в документации.

   Надёжная защита — уникальный индекс в базе:

   ```ruby
   add_index :users, 'lower(email)', unique: true, name: 'index_users_on_lower_email'
   ```

   Валидацию оставляют для понятного сообщения в форме, а ошибку из базы
   перехватывают:

   ```ruby
   user.save!
   rescue ActiveRecord::RecordNotUnique
     user.errors.add(:email, :taken)
   ```

   Дополнительно: нормализация email перед сохранением (`before_validation {
   self.email = email.to_s.strip.downcase }`, в Rails 7.1+ — `normalizes`), и
   защита от повторной отправки формы.

   </details>

1. Какие последствия возможны при отправке email прямо в контроллере? Как можно решить эти проблемы?
   <details>
   <summary>Ответ</summary>

   Проблемы: запрос пользователя ждёт SMTP (медленно, таймауты), падение
   почтового сервиса роняет экшен, ретраев нет — письмо теряется, письмо может
   уйти при откате транзакции, тесты начинают ходить в сеть, скорость рассылки
   ничем не ограничена.

   Решение: контроллер только ставит задачу в очередь —
   `UserMailer.welcome(user).deliver_later` (ActiveJob + Sidekiq), а воркер
   отправляет письмо с ретраями и экспоненциальной задержкой (`retry_on`),
   dead-letter (`discard_on` + мониторинг) и идемпотентностью.

   Важные детали Rails: в задачу передавать `user` (GlobalID) или id, а не
   объект с состоянием; при `deliver_later` внутри транзакции задача может
   уехать в Sidekiq раньше коммита — Rails 7 умеет
   `enqueue_after_transaction_commit`, иначе используют `after_commit` или
   transactional outbox; в тестах — `ActiveJob::TestHelper` и
   `perform_enqueued_jobs`.

   </details>

1. Как бы вы реализовали смену email на сайте, так чтобы соблюсти баланс между сложностью и безопасностью?
   <details>
   <summary>Ответ</summary>

   Схема с подтверждением по ссылке — разумный баланс:

   1. Пользователь вводит новый адрес и **свой текущий пароль** (или проходит
      повторную аутентификацию).
   2. Меняем не email, а создаём запись «запрос на смену»: новый адрес,
      одноразовый токен (`SecureRandom`, хранится хэшем), TTL 1–24 часа. В Rails
      удобно взять `generates_token_for` (7.1+) или `signed_id(expires_in:
      2.hours)`.
   3. Письмо со ссылкой подтверждения — на **новый** адрес; уведомление о
      попытке смены со ссылкой «это не я» — на **старый**.
   4. По переходу проверяем токен и срок, меняем email, инвалидируем токен и
      остальные сессии, пишем событие в аудит-лог.

   Что учесть: rate limiting на запросы смены (`rack-attack`), уникальный индекс
   на email, письма не должны раскрывать, зарегистрирован ли адрес, сравнение
   токенов через `ActiveSupport::SecurityUtils.secure_compare`. Devise решает
   это через `reconfirmable` — можно сослаться на него как на готовый вариант.

   Чего не делать: менять email сразу по нажатию кнопки — это позволяет угнать
   аккаунт через незалоченную сессию и рассылать спам подтверждениями.

   </details>

1. Можно ли доверять email, который мы получаем по oauth от соц сетей и мержить аккаунты автоматически? Приведите примеры
   <details>
   <summary>Ответ</summary>

   Автоматически мержить нельзя. Провайдер отдаёт `email` и флаг
   `email_verified`; без подтверждённого флага адрес — просто строка, которую
   пользователь мог указать сам. Плюс бывают приватные релеи (Apple
   `@privaterelay.appleid.com`), адрес может меняться, а Gmail игнорирует точки
   и суффикс `+`.

   Примеры атак: злоумышленник регистрирует у стороннего провайдера аккаунт с
   чужим неподтверждённым email и логинится в наш сервис как жертва; или
   наоборот — регистрируется у нас на чужой адрес, а настоящий владелец позже
   приходит через OAuth и получает доступ к чужому аккаунту.

   Как правильно: мержить только при `email_verified = true` у доверенного
   провайдера, а лучше — спрашивать подтверждение у уже залогиненного
   пользователя, хранить связки в отдельной модели `Identity(provider, uid)`
   (как это делает `omniauth` + Devise) и опираться на `uid`/`sub` провайдера, а
   не на email.

   </details>

1. Как ограничить отправку email пользователю, который добавил письмо нашего проекта в спам? И почему это стоит делать (или не стоит)?
   <details>
   <summary>Ответ</summary>

   Отправку надо прекратить. Механика: провайдер (SES, SendGrid, Mailgun,
   Postmark) присылает webhook с событиями `bounce`, `complaint` (нажали
   «спам»), `unsubscribe`; по ним адрес попадает в suppression-таблицу, и перед
   каждой отправкой мейлер сверяется с ней (удобно в `before_action` мейлера или
   через `Interceptor` в ActionMailer).

   Почему это обязательно: жалобы и хардбаунсы убивают репутацию домена и IP —
   после определённого порога (у SES 0.1% жалоб) письма всех пользователей
   уходят в спам или отправку блокируют. Плюс требования CAN-SPAM, GDPR и
   152-ФЗ.

   Тонкость: разделять типы писем. Маркетинговые — блокировать полностью;
   транзакционные (сброс пароля, чек, оповещение безопасности) — при жалобе или
   хардбаунсе тоже безопаснее остановить, дав альтернативный канал в интерфейсе.

   </details>

1. Предположим что вы реализуете редакцию журнала, где редактора могут в админке править статьи. Как предотвратить ситуацию, когда два редактора могут начать одновременно редактировать одну статью и перетирать изменения друг друга?
   <details>
   <summary>Ответ</summary>

   Это задача про конкурентный доступ. Варианты по возрастанию сложности:

   **Оптимистическая блокировка** — базовое решение, в Rails встроено: если у
   модели есть колонка `lock_version`, ActiveRecord сам добавит её в `WHERE` и
   бросит `ActiveRecord::StaleObjectError`, если запись уже изменили.

   ```ruby
   add_column :articles, :lock_version, :integer, default: 0, null: false

   # в контроллере
   article.update!(article_params)
   rescue ActiveRecord::StaleObjectError
     # показать предупреждение и различия, предложить перезагрузить или слить
   ```

   **Пессимистическая блокировка** — «статью редактирует Иван»: запись с
   владельцем и TTL, продлеваемым, пока редактор активен; по истечении
   блокировка снимается, у админа есть принудительный сброс. `with_lock`
   (`SELECT ... FOR UPDATE`) годится только для короткой критической секции,
   держать его на всё время редактирования нельзя.

   **Совместное редактирование** (OT или CRDT — Yjs, Automerge) через
   ActionCable — настоящая одновременная работа, но существенно дороже.

   Практика: в админке журнала достаточно оптимистической блокировки плюс мягкий
   индикатор «сейчас редактирует другой» через heartbeat.

   </details>

1. Каких принципов разработки нужно придерживаться, для обеспечения механизма zero downtime deployment. Как это достигается?
   <details>
   <summary>Ответ</summary>

   Zero downtime достигается тем, что старая и новая версии умеют работать
   одновременно:

   * **Обратно совместимые миграции** в несколько шагов: добавить колонку и
     писать в оба места, перенести данные, переключить чтение и только в
     следующем релизе удалить старое (expand/contract). Переименование колонки
     за один деплой недопустимо; для Rails есть `strong_migrations`, который
     подсказывает опасные операции, и `ignored_columns` для безопасного
     удаления.
   * **Миграции без долгих блокировок**: `add_index algorithm: :concurrently` с
     `disable_ddl_transaction!`, добавление `NOT NULL` через `CHECK`-констрейнт
     с валидацией, обновление данных батчами в отдельной задаче, а не в
     миграции.
   * **Приложение stateless**: сессии в Redis или cookie, файлы в S3
     (ActiveStorage), кэш общий.
   * **Плавное переключение трафика**: rolling или blue-green деплой,
     health-check, чтобы балансировщик не давал трафик неготовому процессу.
   * **Graceful shutdown**: Puma по `SIGTERM` дорабатывает текущие запросы,
     Sidekiq — текущие задачи (`-t` таймаут); задачи должны быть идемпотентными,
     потому что могут быть перезапущены.
   * **Совместимость задач в очередях**: старый воркер может получить новый
     аргумент и наоборот — не удалять и не переименовывать аргументы задач одним
     релизом.
   * Плюс фичефлаги для незавершённой функциональности, прогрев кэша и план
     отката, не требующий обратной миграции данных.

   </details>

1. Что может произойти, если ваша `cron` задача, которая запускается раз в минуту, стала выполняться больше 1 минуты? Как это можно предотвратить?
   <details>
   <summary>Ответ</summary>

   Запуски начнут накладываться: появятся два и более параллельных экземпляра.
   Последствия — двойная обработка одних и тех же записей, гонки и дубликаты
   (например, повторная отправка писем), блокировки в базе, исчерпание пула
   соединений (`pool` в `database.yml`) и лимитов внешних API, лавинообразный
   рост числа процессов.

   Как предотвратить:

   * **взаимное исключение**: advisory-лок PostgreSQL (`with_advisory_lock`),
     `SET NX` с TTL в Redis, `flock`; если лок занят — просто выйти. Для Sidekiq
     есть `sidekiq-unique-jobs`, у Sidekiq Enterprise — rate limiting и
     уникальность из коробки;
   * **гарантия одного запуска на уровне платформы**: `concurrencyPolicy:
     Forbid` у Kubernetes CronJob, настройка `sidekiq-cron`/`whenever` так,
     чтобы задача ставилась в очередь, а не запускалась отдельным процессом;
   * **ограничить время работы**: обработка батчами с курсором (`find_each`),
     таймаут внутри задачи, чтобы итерация укладывалась в интервал;
   * **идемпотентность** и алерт на длительность выполнения, чтобы узнать о
     проблеме до аварии.

   </details>

1. Если вы пишите тесты, то как вы обходите проблему того, что код который вы тестируете, делает внешние вызовы? Доп условие, говорим о том, что на CI внешние вызовы запрещены (почему так правильно?)
   <details>
   <summary>Ответ</summary>

   Внешние вызовы изолируют:

   * **Подмена зависимости**: клиент передаётся в сервис снаружи, в тесте —
     фейк. Самый чистый вариант, не требует моков.
   * **Мокирование на уровне HTTP**: WebMock (`stub_request`) и VCR (записанные
     «кассеты» с реальными ответами) — стандарт в Rails; WebMock к тому же умеет
     запрещать любые сетевые вызовы (`WebMock.disable_net_connect!`), что
     превращает случайный внешний запрос в упавший тест.
   * **Контрактные тесты** (Pact) плюс отдельный редкий набор реальных
     smoke-тестов вне основного CI.
   * **Реальные зависимости в контейнерах** (PostgreSQL, Redis) — это уже
     контролируемая зависимость, а не внешний вызов.

   Почему запрет внешних вызовов в CI правильный: тесты должны быть
   детерминированными и быстрыми, иначе сборка падает из-за чужой недоступности
   и сети, а не из-за кода; у внешнего сервиса есть лимиты и цена; тесты не
   должны менять данные в чужих системах; в CI часто нет ни интернета, ни
   секретов. Обратная сторона — моки расходятся с реальностью, поэтому их
   дополняют контрактными тестами и мониторингом интеграций в проде.

   </details>

1. Предположим что в вашей системе реализована смена емейла. При этом этот емейл хранится еще и во внешней системе, например эквайринге, который шлет пользователю свои письма (но пользователь им напрямую не пользуется). Как бы вы реализовали синхронизацию емейла с внешней системой?
   <details>
   <summary>Ответ</summary>

   Смену email надо рассматривать как событие, которое нужно надёжно доставить
   во внешнюю систему.

   Схема: в той же транзакции, что и обновление email, пишем запись в `outbox`
   (transactional outbox). Отдельный воркер читает её и вызывает API эквайринга
   с ретраями и экспоненциальной задержкой, идемпотентным ключом запроса и
   переводом в dead-letter при исчерпании попыток. Статус синхронизации храним у
   себя (`pending`/`synced`/`failed`) и показываем в админке.

   Что ещё учесть: порядок событий (если email меняли дважды, во внешнюю систему
   должно попасть последнее значение — помогает `lock_version` или отправка
   текущего состояния, а не дельты), периодическая сверка (reconciliation job),
   алерт на «висящие» записи, обработка ответа «такой email уже используется».

   Чего не делать: вызывать внешний API прямо в экшене или в колбэке
   `after_save` внутри транзакции — упадёт сеть, и данные разъедутся без следа.
   `after_commit` + ActiveJob лучше, но всё равно теряет событие, если процесс
   умрёт до постановки задачи, — отсюда outbox.

   </details>

1. Как вы узнаете об ошибках, которые происходят на продакшене? От пользователей или это автоматизировано?
   <details>
   <summary>Ответ</summary>

   Автоматизировано — это ключевая часть ответа. Ошибки собирает трекер (Sentry,
   Rollbar, Bugsnag, Honeybadger): исключение уезжает со стеком, версией релиза,
   окружением и контекстом запроса и пользователя, дальше — дедупликация, алерты
   в Slack или Telegram, назначение ответственного. В Rails это подключается
   гемом и ловит и веб-запросы, и задачи ActiveJob.

   Рядом: структурированные логи (`lograge`, `semantic_logger`) с request id в
   централизованном хранилище (Loki, ELK), метрики с алертами по доле 5xx и
   времени ответа (Prometheus + Grafana), APM (Scout, Skylight, New Relic,
   Datadog), мониторинг очередей Sidekiq (размер, retries, dead set),
   health-check и внешний мониторинг доступности, алерт на бизнес-метрики.

   Про пользователей: их обращения — сигнал последней инстанции. Цель — узнавать
   об ошибке раньше, чем о ней сообщат, и иметь связь между тикетом поддержки и
   request id в логах.

   </details>

1. Как обеспечивается изоляция тестов друг от друга если они ходят в базу и меняют ее? Если в вашем фреймворке этого нет, то как вы это делаете или сделали бы?
   <details>
   <summary>Ответ</summary>

   В Rails это встроено: каждый тест выполняется в транзакции, которая
   откатывается после него (`use_transactional_tests` в Minitest,
   `use_transactional_fixtures`/`config.use_transactional_fixtures = true` в
   RSpec). База остаётся чистой, и это быстро.

   Когда транзакции не хватает:

   * **системные тесты** с реальным браузером (Capybara + Selenium) — сервер и
     тест в разных потоках; Rails решает это разделяемым соединением, но при
     проблемах используют `DatabaseCleaner` со стратегией `truncation`;
   * **код, который коммитит сам** или проверяет `after_commit` —
     `test_after_commit`-подход, `DatabaseCleaner` или явные
     `commit_transaction`;
   * **параллельный запуск**: `parallelize(workers: :number_of_processors)` в
     Rails создаёт отдельную базу на каждый воркер (`app_test-0`, `-1`, …);
   * **внешнее состояние**: Redis и кэш чистить между тестами
     (`Rails.cache.clear`, отдельная база Redis), очереди — через
     `ActiveJob::TestHelper`.

   Плюс общие правила: уникальные данные через FactoryBot и Faker вместо
   константных email, независимость от порядка тестов (в RSpec `config.order =
   :random`), фиксированное время (`travel_to`, `freeze_time`) вместо
   `Time.now`.

   </details>
