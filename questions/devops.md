1. Сталкивался ли с ревью кода? Как проходило ревью? По какому принципу бы сам проводил ревью?
   <details>
   <summary>Ответ</summary>

   Как проходило: merge request с описанием, автоматические проверки до людей
   (линтеры, `terraform validate` и `plan`, `ansible-lint`, `helm template`,
   сканеры образов), один-два ревьюера, обсуждение, правки, аппрув и мерж по
   защищённой ветке.

   Как сам бы проводил ревью инфраструктурного кода:

   * смотреть на **эффект изменения**, а не на строки: что покажет `terraform
     plan`, не пересоздаётся ли ресурс с данными, не будет ли простоя;
   * идемпотентность и повторяемость (Ansible должен быть безопасен при
     повторном запуске), отсутствие ручных шагов «руками в консоли»;
   * безопасность: нет секретов в коде, минимальные права, версии образов
     зафиксированы, не `latest`;
   * надёжность: лимиты ресурсов, probes, стратегия обновления, откат;
   * читаемость: понятные имена, переменные вместо магических значений,
     переиспользуемые модули и роли;
   * стиль не обсуждать — это работа линтера; комментарии писать вопросом и
     разделять «блокирует» и «на подумать»; ревьюить небольшими порциями.

   </details>

1. Приходилось работать с пайплайнами Gitlab Runner? Какие виды пайплайнов есть?
   <details>
   <summary>Ответ</summary>

   Пайплайн описывается в `.gitlab-ci.yml`: стадии, задания, образы, артефакты,
   кэш, правила запуска. Выполняют задания раннеры — shell, docker, kubernetes
   executor.

   Виды пайплайнов в GitLab:

   * **обычный (basic)** — стадии выполняются последовательно, внутри стадии
     задания параллельно;
   * **DAG** — зависимости через `needs`, задания стартуют, как только готовы их
     зависимости (быстрее);
   * **merge request pipeline** — запускается для MR;
   * **merged results** и **merge trains** — сборка результата слияния с целевой
     ветки, чтобы не сломать её;
   * **parent-child** — родительский пайплайн триггерит дочерние (`trigger:
     include`), удобно для монорепозиториев;
   * **multi-project** — запуск пайплайна другого проекта;
   * **scheduled** — по расписанию;
   * отдельно — matrix (`parallel: matrix`) и ручные задания (`when: manual`)
     для деплоя.

   Полезно упомянуть практику: `rules`/`only-except` для условий, `needs` для
   ускорения, кэш против артефактов (кэш — для зависимостей, артефакты — для
   результатов сборки), окружения и `environment` для деплоя, защищённые
   переменные для секретов.

   </details>

1. Набираю в командной строке curl <https://example.com/> расскажите детально что происходит дальше.
   <details>
   <summary>Ответ</summary>

   1. `curl` разбирает URL: схема, хост, порт, путь.
   2. **Разрешение имени**: `/etc/nsswitch.conf` и `/etc/hosts`, затем
      DNS-запрос к резолверам из `/etc/resolv.conf` (рекурсивный резолвер →
      корневые → TLD → авторитетный сервер), результат кэшируется по TTL.
   3. **Маршрутизация и соединение**: ядро выбирает интерфейс по таблице
      маршрутов, ARP для шлюза, TCP-рукопожатие (SYN → SYN/ACK → ACK) на порт
      443.
   4. **TLS-рукопожатие**: ClientHello с SNI, выбор версии и шифров, сертификат
      сервера и проверка цепочки по локальному хранилищу доверенных корней,
      обмен ключами, дальше трафик шифруется.
   5. **HTTP-запрос**: `GET / HTTP/1.1` (или HTTP/2 после ALPN) с заголовками
      `Host`, `User-Agent`, `Accept`.
   6. **Ответ**: код, заголовки, тело; `curl` по умолчанию печатает тело в
      stdout и **не** идёт по редиректам (для этого `-L`).
   7. Закрытие соединения (FIN) или переиспользование keep-alive.

   Полезно добавить, чем это смотреть: `curl -v` для рукопожатия и заголовков,
   `curl -w '%{time_namelookup} %{time_connect} %{time_starttransfer}'` для
   разбора по времени, `dig` для DNS, `openssl s_client` для сертификата,
   `tcpdump`/`ss` для соединений.

   </details>

1. Почему символ DevOps - бесконечность?
   <details>
   <summary>Ответ</summary>

   Знак бесконечности отражает суть подхода: разработка и эксплуатация — не две
   последовательные фазы с «передачей через стену», а непрерывный цикл, у
   которого нет конца.

   ```text
   plan -> code -> build -> test -> release -> deploy -> operate -> monitor
     ^                                                                |
     +----------------------------------------------------------------+
   ```

   Обратная связь из эксплуатации (метрики, инциденты, поведение пользователей)
   возвращается в планирование, и цикл повторяется — отсюда петля. Левая
   половина — Dev, правая — Ops, а точка пересечения — общая ответственность за
   результат.

   Смысл, который стоит озвучить: DevOps — про культуру и совместную
   ответственность («вы это написали — вы это и эксплуатируете»), про
   автоматизацию и короткие итерации, а не про набор инструментов и не про
   название должности.

   </details>

1. Что такое трассировка, для чего может использоваться?
   <details>
   <summary>Ответ</summary>

   Распределённая трассировка — способ проследить путь одного запроса через все
   сервисы. Запросу присваивается `trace_id`, каждый шаг создаёт span со
   временем начала, длительностью, родителем и атрибутами; контекст передаётся
   между сервисами через заголовки (`traceparent` в W3C Trace Context).

   ```text
   trace_id=abc
   ├─ gateway            120 мс
   │  ├─ auth-service     15 мс
   │  └─ orders-service   95 мс
   │     ├─ postgres      60 мс   <- узкое место видно сразу
   │     └─ kafka publish  5 мс
   ```

   Для чего: найти, где именно теряется время (а не «где-то в системе»); понять
   реальную топологию вызовов; связать ошибку в логах с конкретным запросом;
   отладить хвостовые задержки p99; увидеть N+1 запросы и лишние вызовы.

   Инструменты: OpenTelemetry как стандарт инструментирования, Jaeger, Tempo,
   Zipkin, Sentry, Datadog как бэкенды. Трассировка — третий столп наблюдаемости
   рядом с метриками и логами; на практике важно связывать их через общий
   `trace_id` и настраивать сэмплирование, чтобы не хранить всё.

   </details>

1. Работал ли с брокерами сообщений? Можешь рассказать, что это такое?
   <details>
   <summary>Ответ</summary>

   Брокер — посредник, через который сервисы обмениваются сообщениями
   асинхронно: издатель отправляет сообщение и не ждёт получателя, брокер хранит
   его и отдаёт подписчикам.

   ```text
   producer -> [брокер: очередь / лог] -> consumer(ы)
   ```

   Что это даёт: развязку сервисов (упал получатель — сообщения не потеряны),
   сглаживание пиков нагрузки, несколько подписчиков на одно событие, повторную
   обработку. Цена — eventual consistency, дубликаты (доставка at-least-once,
   поэтому обработчики должны быть идемпотентными), сложнее отладка и ещё одна
   система в эксплуатации.

   Основные варианты: **RabbitMQ** — очередь задач с маршрутизацией (exchange,
   routing key), подтверждениями и dead-letter; **Kafka** — распределённый лог с
   хранением истории, партициями и группами потребителей, читатель двигает свой
   offset; **NATS**, **Redis Streams**, облачные (SQS, Pub/Sub) — рядом.

   Что важно для DevOps: разворачивание и обновление кластера, репликация и
   `min.insync.replicas` в Kafka, диски и retention, мониторинг лага консьюмеров
   и глубины очередей, алерты, dead-letter очереди, ротация сертификатов и ACL.

   </details>

1. Что такое партиции (partitions) в Kafka? Как они устроены и как влияют на масштабирование и порядок сообщений?
   <details>
   <summary>Ответ</summary>

   Топик в Kafka разбит на партиции — независимые упорядоченные логи, куда
   сообщения только дописываются, а читатель двигает свой offset.

   ```text
   topic orders
     partition 0: [m0][m1][m2] ...
     partition 1: [m0][m1] ...
     partition 2: [m0][m1][m2][m3] ...
   ```

   **Масштабирование**: партиции лежат на разных брокерах, а в consumer group
   каждая партиция отдаётся одному консьюмеру. Значит параллелизм чтения
   ограничен числом партиций: три партиции — максимум три полезных консьюмера,
   четвёртый простаивает. Отказоустойчивость даёт репликация (лидер и
   follower'ы, `min.insync.replicas`).

   **Порядок**: гарантирован только внутри партиции. Партиция выбирается по
   ключу (хэш), поэтому все события одного заказа с ключом `order_id` попадут в
   одну партицию и будут прочитаны по порядку; без ключа сообщения
   раскладываются равномерно и порядок между ними не гарантирован.

   Эксплуатационные следствия: число партиций планируют заранее — увеличить
   можно (но распределение ключей изменится), уменьшить нельзя; «горячий» ключ
   даёт перекос нагрузки; за состоянием следят по лагу консьюмеров и по объёму
   на диске (retention).

   </details>

1. Работал ли с системами мониторинга и логирования?
   <details>
   <summary>Ответ</summary>

   Ответ по своему опыту, разделяя три вида телеметрии:

   * **метрики**: Prometheus (pull-модель, экспортеры `node_exporter`,
     `cadvisor`, `blackbox`), PromQL, правила записи и алертов, Alertmanager с
     маршрутизацией в Telegram и PagerDuty, Grafana как дашборды;
     VictoriaMetrics или Thanos для долгого хранения;
   * **логи**: Loki с promtail или ELK/OpenSearch с Filebeat, Vector или Fluent
     Bit как агрегатор; структурированные логи в JSON, метки сервиса и
     окружения, ротация и retention;
   * **трассировки**: OpenTelemetry, Jaeger, Tempo.

   Что полезно добавить: какие алерты настраивал и по каким принципам — алертить
   на симптомы, которые видит пользователь (доля 5xx, задержки, недоступность),
   а не на каждую метрику; SLO и error budget; борьба с шумом и «алертной
   усталостью»; дежурства и runbook к каждому алерту; Golden Signals (latency,
   traffic, errors, saturation) и USE-метод как рамка.

   </details>

### Docker

1. Приходилось самостоятельно писать Dockerfile? Чем отличается команда `ADD` от `COPY`?
   <details>
   <summary>Ответ</summary>

   Разница `ADD` и `COPY`:

   * **`COPY`** просто копирует файлы и каталоги из контекста сборки в образ.
     Предсказуемо, поэтому это выбор по умолчанию.
   * **`ADD`** умеет то же плюс два «магических» действия: автоматически
     распаковывает локальные tar-архивы и может скачивать по URL (а в новых
     версиях BuildKit — клонировать git-репозиторий).

   ```dockerfile
   COPY app/ /app/                 # обычное копирование
   ADD archive.tar.gz /opt/        # распакуется автоматически
   ```

   Почему предпочитают `COPY`: неявная распаковка приводит к сюрпризам, а
   скачивание по URL через `ADD` не даёт контроля над проверкой контрольной
   суммы и не кэшируется разумно — лучше явный `RUN curl -fsSL ... && echo
   "sha256 ..." | sha256sum -c`.

   Хороший ответ дополняют практиками: `.dockerignore`, порядок слоёв под кэш
   (сначала манифест зависимостей, потом код), multi-stage, non-root
   пользователь, фиксация версий базового образа.

   </details>

1. Для чего нужны `CMD`, `ENTRYPOINT`?
   <details>
   <summary>Ответ</summary>

   Обе инструкции задают, что выполняется при запуске контейнера, но по-разному:

   * **`ENTRYPOINT`** — сама команда, «что это за контейнер». Аргументы из
     `docker run` к ней **добавляются**.
   * **`CMD`** — аргументы или команда **по умолчанию**, которые легко
     переопределить в `docker run`.

   ```dockerfile
   ENTRYPOINT ["nginx"]
   CMD ["-g", "daemon off;"]
   # docker run image            -> nginx -g "daemon off;"
   # docker run image -t         -> nginx -t   (CMD заменён)
   ```

   Практика: использовать **exec-форму** (`["cmd", "arg"]`), а не shell-форму —
   иначе процесс запускается через `/bin/sh -c` и не получает сигналы (`SIGTERM`
   не доходит, контейнер убивается по таймауту). Типовой приём — `ENTRYPOINT` на
   скрипт-обёртку (`entrypoint.sh`), который готовит окружение и делает `exec
   "$@"`, а `CMD` задаёт саму команду. Если нужен только один из них, обычно
   достаточно `CMD`.

   </details>

1. В Docker есть понятие слоев. Что это такое?
   <details>
   <summary>Ответ</summary>

   Образ Docker — набор слоёв: каждая инструкция, меняющая файловую систему
   (`FROM`, `RUN`, `COPY`, `ADD`), создаёт новый слой с diff'ом изменений. Слои
   неизменяемы и складываются друг на друга через overlayfs; при запуске
   контейнера сверху добавляется тонкий записываемый слой.

   ```text
   [записываемый слой контейнера]
   [COPY app/]           <- слой 3
   [RUN apt-get install] <- слой 2
   [FROM debian]         <- слой 1 (базовый)
   ```

   Что это даёт: кэширование сборки (неизменившиеся слои переиспользуются),
   экономия места и трафика (общие слои скачиваются один раз и разделяются между
   образами), быстрый запуск контейнеров.

   Практические следствия: порядок инструкций важен — часто меняющееся (код)
   должно быть ниже редко меняющегося (зависимости); удаление файла в следующем
   слое **не уменьшает** образ и не удаляет данные из предыдущего слоя (секрет,
   попавший в слой, остаётся в образе); поэтому команды объединяют (`RUN a && b
   && rm -rf /var/lib/apt/lists/*`) и используют multi-stage.

   </details>

1. В слой делаем `run yum update`. Как Docker понимает, что нужно пересобирать кэш, сбросить кэш или он `yum update` один раз сделал и больше делать его не будет?
   <details>
   <summary>Ответ</summary>

   Docker кэширует слои по «ключу»: для `RUN` это **текст самой команды** (плюс
   идентификатор родительского слоя), а не результат её выполнения. То есть `RUN
   yum update -y` при неизменной строке и неизменных предыдущих слоях будет взят
   из кэша — и обновление не выполнится повторно, даже если в репозитории
   появились новые пакеты. Для `COPY`/`ADD` ключ включает контрольные суммы
   копируемых файлов, поэтому там кэш инвалидируется при изменении содержимого.

   Отсюда классическая ловушка: «почему в образе старые пакеты» — потому что
   слой закэширован месяц назад.

   Как этим управлять:

   * `docker build --no-cache` или `--no-cache-filter` для конкретной стадии;
   * инвалидация через аргумент сборки: `ARG CACHEBUST=1` перед `RUN`;
   * объединять обновление с установкой в одну команду (`RUN yum update -y &&
     yum install -y ...`), иначе установка возьмётся из кэша поверх старого
     индекса — это же известная проблема `apt-get update && apt-get install` в
     разных слоях;
   * регулярно перебирать базовый образ по тегу или digest и пересобирать образы
     по расписанию;
   * ставить конкретные версии пакетов, чтобы сборка была воспроизводимой.

   </details>

1. В Docker есть понятие multi-stage? Что это такое, зачем используется?
   <details>
   <summary>Ответ</summary>

   Да. Multi-stage build — несколько `FROM` в одном Dockerfile: в первых стадиях
   собираем артефакт со всеми инструментами, а в финальный образ копируем только
   результат.

   ```dockerfile
   FROM golang:1.23 AS build
   WORKDIR /src
   COPY go.* ./
   RUN go mod download
   COPY . .
   RUN CGO_ENABLED=0 go build -o /app ./cmd/api

   FROM gcr.io/distroless/static
   COPY --from=build /app /app
   USER nonroot
   ENTRYPOINT ["/app"]
   ```

   Зачем: итоговый образ в разы меньше (нет компилятора, исходников, кэшей),
   меньше поверхность атаки и уязвимостей в сканере, нет секретов и токенов из
   стадии сборки, при этом одна воспроизводимая сборка без внешних скриптов.
   Дополнительно: можно собрать несколько целей (`--target test`), параллелить
   независимые стадии в BuildKit, копировать файлы из чужого образа (`COPY
   --from=nginx:alpine`).

   </details>

1. Мультистейдж в Docker, для чего?
   <details>
   <summary>Ответ</summary>

   Тот же вопрос другими словами — коротко и по делу: чтобы отделить окружение
   **сборки** от окружения **запуска**.

   В образ попадает только готовый артефакт: без компилятора, менеджера пакетов,
   исходников, тестов и кэшей. Результат — образ меньше в разы (быстрее
   скачивается и стартует), меньше CVE в сканерах и нет секретов, использованных
   при сборке.

   Дополнительные применения: отдельные стадии для линтеров и тестов
   (`--target`), общая базовая стадия для нескольких образов, копирование
   готовых бинарников из официальных образов (`COPY
   --from=hashicorp/terraform`).

   </details>

1. Команда `COPY . .` Хотим все, что у нас в корне, скопировать в корень контейнера. Мы можем ограничить, что будет копироваться? В Dockerfile не меняем ничего.
   <details>
   <summary>Ответ</summary>

   Да, можно — файлом **`.dockerignore`** в корне контекста сборки. Он не
   требует изменений в Dockerfile: демон просто не отправит перечисленное в
   контекст, и `COPY . .` его не увидит.

   ```text
   .git
   node_modules
   .env
   *.log
   Dockerfile
   .dockerignore
   ```

   Зачем это нужно: контекст меньше — сборка быстрее (не гоняем сотни мегабайт в
   демон); кэш слоя не сбрасывается из-за изменений в `.git` и локальных файлах;
   в образ не утекают секреты (`.env`, ключи) и мусор (`node_modules` хоста,
   артефакты сборки).

   Синтаксис похож на `.gitignore`, поддерживаются шаблоны и исключения
   (`!important.txt`). Проверить итоговый контекст можно по строке `Sending
   build context to Docker daemon` или собрав образ и посмотрев `docker image
   history`.

   </details>

1. Как посмотреть логи работающего контейнера? Как посмотреть определённое количество строк лога?
   <details>
   <summary>Ответ</summary>

   ```sh
   docker logs <container>                 # всё, что писалось в stdout/stderr
   docker logs -f <container>              # следить в реальном времени
   docker logs --tail 100 <container>      # последние 100 строк
   docker logs --tail 50 -f --timestamps <container>
   docker logs --since 10m --until 1m <container>
   docker compose logs -f --tail=100 service
   ```

   В Kubernetes аналогично: `kubectl logs pod -c container --tail=100 -f`,
   `--previous` для упавшего экземпляра.

   Что полезно добавить: `docker logs` показывает только вывод в stdout/stderr —
   если приложение пишет в файл внутри контейнера, там ничего не будет (поэтому
   в контейнерах логи направляют в stdout); источник — драйвер логирования
   (`json-file` по умолчанию, `local`, `journald`, `fluentd`, `gelf`), и для
   некоторых драйверов `docker logs` не работает; обязательно настраивать
   ротацию (`max-size`, `max-file`), иначе логи съедят диск.

   </details>

1. Как попасть в bash работающего контейнера?
   <details>
   <summary>Ответ</summary>

   ```sh
   docker exec -it <container> bash        # если bash есть в образе
   docker exec -it <container> sh          # alpine и distroless-подобные
   docker exec -it -u root <container> sh  # войти root'ом
   ```

   `-i` держит stdin открытым, `-t` выделяет псевдотерминал. В Kubernetes —
   `kubectl exec -it pod -c container -- sh`.

   Что стоит добавить: `docker attach` подключается к основному процессу (и
   `Ctrl+C` может его убить) — это не то же самое, что `exec`; в минимальных
   образах (distroless, scratch) оболочки нет вовсе — тогда используют `docker
   debug`, отладочный сайдкар или `kubectl debug --image=busybox` с общим
   namespace; изменения, сделанные руками внутри контейнера, исчезнут при
   пересоздании — это способ диагностики, а не исправления.

   </details>

1. Развернули контейнер, как попасть внутрь? Как обеспечить доступ извне?
   <details>
   <summary>Ответ</summary>

   **Внутрь**: `docker exec -it <container> sh` (см. предыдущий вопрос).

   **Доступ извне** — публикация портов:

   ```sh
   docker run -p 8080:80 nginx          # хост:8080 -> контейнер:80
   docker run -p 127.0.0.1:8080:80 ...  # только с localhost
   docker run -P nginx                   # все EXPOSE на случайные порты
   ```

   Как это работает: Docker добавляет правила DNAT в iptables и поднимает
   проксирование на хосте; `EXPOSE` в Dockerfile — только документация, сам порт
   он не открывает.

   Что важно добавить: контейнеры в одной пользовательской сети обращаются друг
   к другу по имени сервиса и порт публиковать не нужно (`docker network
   create`, `docker compose`); наружу обычно смотрит не контейнер, а reverse
   proxy (nginx, Traefik) с TLS; публикация порта обходит `ufw`, поэтому доступ
   ограничивают привязкой к `127.0.0.1` или правилами в цепочке `DOCKER-USER`. В
   Kubernetes роль публикации играют Service (`NodePort`, `LoadBalancer`) и
   Ingress, а для отладки — `kubectl port-forward`.

   </details>

1. Приходилось работать с volume в Docker?
   <details>
   <summary>Ответ</summary>

   Volume — способ хранить данные вне записываемого слоя контейнера, чтобы они
   переживали пересоздание.

   ```sh
   docker volume create pgdata
   docker run -v pgdata:/var/lib/postgresql/data postgres     # named volume
   docker run -v /srv/app/conf:/etc/app:ro nginx              # bind mount
   docker run --mount type=tmpfs,dst=/tmp app                 # tmpfs, в памяти
   ```

   Зачем: данные баз, загруженные файлы, кэши, сокеты; в разработке —
   монтирование исходников для горячей перезагрузки. Плюс: named volume
   управляется Docker (`docker volume ls/inspect/prune`), его удобно бэкапить и
   переносить, он работает с драйверами (NFS, облачные диски).

   Что упомянуть про эксплуатацию: `docker volume prune` удаляет данные —
   осторожно; бэкап делают отдельным контейнером, монтирующим том; `:ro` для
   конфигураций; права и `uid`/`gid` внутри контейнера часто не совпадают с
   хостом; в Kubernetes аналоги — PersistentVolume, PersistentVolumeClaim,
   StorageClass, а также `emptyDir` и `configMap` как монтирования.

   </details>

1. Мы можем примонтировать директорию к контейнеру, а можем указать "используй такой-то volume". В чем разница?
   <details>
   <summary>Ответ</summary>

   Это два разных механизма:

   * **bind mount** (`-v /host/path:/container/path`) — монтируется конкретный
     путь **файловой системы хоста**. Полный контроль над расположением, видно и
     правится с хоста; но образ становится зависимым от структуры хоста, права и
     SELinux дают сюрпризы, на разных машинах путь может отличаться, а на Docker
     Desktop это ещё и медленно.
   * **named volume** (`-v pgdata:/var/lib/postgresql/data`) — Docker сам
     выделяет и хранит данные (по умолчанию в `/var/lib/docker/volumes`),
     управляет ими через API (`docker volume ls/inspect/rm`), поддерживает
     драйверы (NFS, облачные диски) и при первом монтировании **копирует** в том
     содержимое каталога из образа.

   ```text
   bind mount:   привязан к пути на хосте, для разработки и конфигов
   named volume: управляется Docker, для данных (базы, загрузки), для прода
   tmpfs:        в памяти, ничего не сохраняется
   ```

   Правило выбора: разработка и конфигурационные файлы — bind mount (желательно
   `:ro`); состояние приложения и базы — named volume; секреты и временные файлы
   — tmpfs.

   </details>

1. Зачем нужен Docker Compose?
   <details>
   <summary>Ответ</summary>

   Compose описывает **многоконтейнерное приложение** в одном YAML-файле и
   поднимает его одной командой: сервисы, сети, тома, переменные окружения,
   зависимости, health-check.

   ```yaml
   services:
     api:
       build: .
       ports: ['8080:8080']
       environment: [DATABASE_URL=postgres://app@db/app]
       depends_on:
         db: { condition: service_healthy }
     db:
       image: postgres:16
       volumes: [pgdata:/var/lib/postgresql/data]
       healthcheck:
         test: ['CMD-SHELL', 'pg_isready -U app']
   volumes:
     pgdata:
   ```

   Что даёт: `docker compose up -d` вместо десяти `docker run` с длинными
   флагами; общая сеть, где сервисы видят друг друга по имени; описание
   окружения как код в репозитории; удобство для локальной разработки, тестов и
   CI (поднять базу и брокер для интеграционных тестов); профили и несколько
   файлов (`-f compose.yml -f compose.prod.yml`) для разных окружений.

   Важная оговорка: Compose — не оркестратор. Он работает на одном хосте, без
   самовосстановления по нескольким узлам, авторазмещения и раскатов; для прода
   это Kubernetes (или Swarm/Nomad как более простые варианты).

   </details>

### Сети

1. Необходимо отследить путь от одного хоста к другому, какой командой можно это сделать?
   <details>
   <summary>Ответ</summary>

   ```sh
   traceroute example.com        # UDP по умолчанию в Linux
   traceroute -I example.com     # ICMP
   traceroute -T -p 443 host     # TCP — часто единственный, что проходит фильтры
   tracepath example.com         # без root
   mtr example.com               # traceroute + непрерывный ping, лучший вариант
   ```

   В Windows — `tracert`. Принцип: пакеты отправляются с постепенно
   увеличивающимся TTL, каждый маршрутизатор, где TTL становится нулём, отвечает
   `ICMP Time Exceeded` — так и получается список узлов.

   Что важно сказать при чтении вывода: звёздочки не обязательно означают
   проблему — многие маршрутизаторы не отвечают на ICMP или ставят ему низкий
   приоритет; путь может быть асимметричным (обратный трафик идёт иначе);
   высокая задержка на промежуточном узле сама по себе ничего не значит,
   смотреть надо на рост задержки и потери **до конца** маршрута — поэтому и
   удобнее `mtr`, который собирает статистику потерь по каждому хопу.

   </details>

1. Что такое TTL?
   <details>
   <summary>Ответ</summary>

   Аббревиатура употребляется в двух смыслах — стоит уточнить, о чём вопрос.

   **TTL в IP-пакете** (в IPv6 — hop limit) — счётчик оставшихся переходов.
   Каждый маршрутизатор уменьшает его на единицу, при нуле пакет отбрасывается и
   отправителю уходит `ICMP Time Exceeded`. Защищает сеть от бесконечной
   циркуляции пакетов в петле маршрутизации; на этом же построен `traceroute`.
   Типичные начальные значения: 64 в Linux, 128 в Windows, 255 у сетевого
   оборудования — по остатку иногда можно угадать ОС и число хопов.

   **TTL в DNS** — сколько секунд ответ можно держать в кэше резолвера. Влияет
   на скорость распространения изменений: перед миграцией TTL понижают (до
   60–300 секунд), после — возвращают.

   Рядом встречаются TTL в кэше (Redis, HTTP `max-age`) и в Kafka (retention) —
   общая идея одна: срок жизни данных.

   </details>

1. У меня есть клиент-сервер. Как замерить пропускную способность между клиентом и сервером, какой командой?
   <details>
   <summary>Ответ</summary>

   Основной инструмент — **`iperf3`**: на одной стороне сервер, на другой
   клиент.

   ```sh
   # на сервере
   iperf3 -s
   # на клиенте
   iperf3 -c 10.0.0.5              # TCP, 10 секунд
   iperf3 -c 10.0.0.5 -R           # обратное направление
   iperf3 -c 10.0.0.5 -P 8         # 8 параллельных потоков
   iperf3 -c 10.0.0.5 -u -b 100M   # UDP: проверка потерь и джиттера
   ```

   Альтернативы, если ставить нечего: `nc` + `dd` (`dd if=/dev/zero bs=1M
   count=1000 | nc host 9000`), `scp`/`rsync` большого файла с оценкой скорости,
   `curl -o /dev/null -w '%{speed_download}'` для HTTP, `speedtest-cli` до
   интернета, `qperf`, `nuttcp`.

   Что важно проговорить: измерять надо в обе стороны и несколькими потоками
   (один TCP-поток на длинном канале ограничен окном и задержкой); UDP-тест
   показывает потери и джиттер, TCP — реальную полезную полосу; результат
   зависит от MTU и фрагментации, CPU (шифрование, softirq), загруженности
   канала соседями; поэтому рядом смотрят `ping` для задержки и `mtr` для
   потерь.

   </details>

1. TCP и UDP, в чем отличия? За счёт чего и какие гарантии доставки?
   <details>
   <summary>Ответ</summary>

   **TCP** — с установлением соединения (рукопожатие SYN → SYN/ACK → ACK) и с
   гарантиями: доставка (подтверждения и повторная отправка), порядок (нумерация
   байтов), защита от перегрузки и управление потоком (congestion control,
   скользящее окно), контрольная сумма. Цена — задержка на установление,
   состояние на обеих сторонах, замедление при потерях.

   **UDP** — без соединения и без гарантий: отправил датаграмму и всё. Ни
   подтверждений, ни порядка, ни контроля перегрузки — зато минимум накладных
   расходов, поддержка multicast и broadcast, никакого состояния.

   ```text
   TCP: SYN -> SYN/ACK -> ACK -> данные (+ ACK, повторы, окно)
   UDP: датаграмма -> и никаких обещаний
   ```

   Где что: TCP — HTTP/1.1 и HTTP/2, SSH, SMTP, базы данных; UDP — DNS, DHCP,
   NTP, VoIP и видео, игры, syslog, QUIC/HTTP-3 (надёжность там реализована
   **поверх** UDP в пользовательском пространстве, чтобы обойти ограничения
   TCP).

   Единственная «гарантия» UDP — контрольная сумма целостности (и она
   опциональна в IPv4); всё остальное, если нужно, реализует приложение.

   </details>

1. Клиент что-то отправляет на сервер. Во время соединения был перезагружен роутер. Будет ли доставлен пакет после перезагрузки роутера? В течение какого времени возможна доставка?
   <details>
   <summary>Ответ</summary>

   Зависит от того, какой это роутер.

   Если это **транзитный маршрутизатор** и есть альтернативный маршрут — пакеты
   пойдут другим путём, TCP переотправит потерянное, и соединение, скорее всего,
   выживёт: пользователь заметит только задержку. Если альтернативы нет, пакеты
   теряются, а TCP продолжает повторные попытки с экспоненциально растущим
   интервалом. Живучесть определяется таймерами:

   * **RTO с экспоненциальным ростом** и лимитом попыток —
     `net.ipv4.tcp_retries2` (по умолчанию 15) даёт порядка 13–15 минут до
     разрыва соединения;
   * если данных нет вовсе, соединение молча «висит», пока не сработает
     **keepalive** (`tcp_keepalive_time` 7200 секунд по умолчанию, то есть 2
     часа) — поэтому приложения задают свои таймауты;
   * у приложения обычно свой прикладной таймаут (секунды), и он срабатывает
     раньше всего.

   Если перезагрузился **NAT-роутер** (домашний или пограничный) — его таблица
   трансляций теряется. После загрузки ответные пакеты не смогут сопоставиться с
   сессией: роутер отбросит их или пришлёт RST, и соединение порвётся, даже если
   оба хоста живы. То же с state-full файрволом.

   Итог для интервью: доставка возможна, пока не исчерпаны повторы TCP (минуты)
   и пока сохранено состояние NAT; поэтому надёжные системы не полагаются на
   живучесть соединения, а используют разумные таймауты, ретраи с
   идемпотентностью и переподключение.

   </details>

1. Отличия HTTP и HTTPS. Плюсы HTTPS помимо шифрования. За счёт чего нельзя просто подменить запрашиваемый сайт. HTTP это текстовый или бинарный протокол?
   <details>
   <summary>Ответ</summary>

   HTTPS — это HTTP внутри TLS. Помимо **шифрования** он даёт:

   * **целостность** — MAC/AEAD не позволяет незаметно изменить трафик
     (провайдер не вставит рекламу, не подменит скрипт);
   * **аутентификацию сервера** — сертификат, подписанный доверенным
     удостоверяющим центром, подтверждает, что это именно тот домен;
   * побочные, но важные вещи: доступ к современным браузерным API (Service
     Worker, геолокация, камера), HTTP/2 и HTTP/3, cookie с флагом `Secure`,
     лучше в ранжировании, защита от подмены контента в публичных Wi-Fi.

   **Почему нельзя просто подменить сайт**: у злоумышленника нет закрытого ключа
   для сертификата этого домена, а сертификат от левого центра браузер не примет
   (цепочка доверия, проверка имени, срок действия, плюс дополнительные
   механизмы — HSTS, Certificate Transparency, пиннинг). Подмена возможна только
   если удастся выпустить валидный сертификат (скомпрометировать УЦ или контроль
   над домменом) либо заставить клиента доверять своему корневому сертификату
   (так и работают корпоративные прокси).

   **HTTP — текстовый или бинарный**: HTTP/1.1 текстовый (запрос и заголовки
   читаются глазами в `tcpdump`), HTTP/2 и HTTP/3 — **бинарные**, с фреймами,
   мультиплексированием и сжатием заголовков (HPACK/QPACK). Семантика при этом
   остаётся той же.

   </details>

1. Сталкивался с REST? Какие методы есть, чем отличаются, когда используются? Основные 5. Отличия GET и POST.
   <details>
   <summary>Ответ</summary>

   Пять основных методов:

   ```text
   GET    /orders      получить список         безопасный, идемпотентный, кэшируется
   POST   /orders      создать                 не идемпотентный
   PUT    /orders/42   заменить целиком        идемпотентный
   PATCH  /orders/42   частично обновить       обычно не идемпотентный
   DELETE /orders/42   удалить                 идемпотентный
   ```

   Рядом: `HEAD` (только заголовки), `OPTIONS` (поддерживаемые методы, CORS
   preflight).

   **Отличия `GET` и `POST`**: `GET` только читает — параметры в URL, тела нет,
   ответ кэшируется, запрос попадает в логи, историю браузера и `Referer`, длина
   URL ограничена. `POST` меняет состояние — данные в теле любого размера и
   формата, по умолчанию не кэшируется, повторять его небезопасно (для этого
   вводят ключ идемпотентности).

   Для DevOps важна практическая сторона: идемпотентные методы можно безопасно
   ретраить на балансировщике и в прокси, `GET` кэшируется на CDN, а `POST` —
   нет; поэтому в конфигурации nginx повторы обычно разрешают только для
   безопасных методов (`proxy_next_upstream`).

   </details>

1. URL при использовании HTTPS зашифрован? Если взять POST, то в URL мы можем передать информацию?
   <details>
   <summary>Ответ</summary>

   Частично. TLS устанавливается **до** отправки HTTP-запроса, поэтому:

   * **не зашифровано (видно наблюдателю)**: IP-адрес, порт и имя домена — оно
     передаётся в открытом виде в расширении SNI при рукопожатии, а также
     утекает через DNS-запрос;
   * **зашифровано**: путь, query-строка, заголовки (включая `Cookie` и
     `Authorization`) и тело запроса и ответа.

   То есть провайдер видит, что вы обратились к `example.com`, но не видит
   `/admin?token=...`. (Есть Encrypted Client Hello, скрывающий и SNI, но он
   пока не повсеместен.)

   Важные оговорки: URL всё равно не место для секретов — он попадает в логи
   сервера и прокси, в историю браузера, в заголовок `Referer` и в закладки;
   TLS-терминация на балансировщике означает, что дальше по внутренней сети
   запрос может идти открытым.

   **Можно ли в `POST` передать информацию в URL** — да, конечно:
   query-параметры работают с любым методом, и `POST /search?page=2` с телом —
   обычная практика. Ограничение только смысловое (и на длину URL), а не
   техническое.

   </details>

1. Basic auth. Что это такое и как оно передаёт свои данные?
   <details>
   <summary>Ответ</summary>

   Простейшая схема HTTP-аутентификации из RFC 7617: логин и пароль склеиваются
   через двоеточие, кодируются в Base64 и отправляются в заголовке.

   ```text
   Authorization: Basic dXNlcjpwYXNzd29yZA==      # base64("user:password")
   ```

   Если заголовка нет, сервер отвечает `401 Unauthorized` с `WWW-Authenticate:
   Basic realm="..."` — браузер показывает системное окно ввода. Учётные данные
   отправляются с **каждым** запросом, состояния на сервере нет.

   Ключевая мысль: **Base64 — это кодирование, а не шифрование**, пароль
   восстанавливается тривиально. Поэтому Basic auth допустим только по HTTPS.
   Другие минусы: нет выхода из системы (браузер кэширует данные до закрытия),
   нет защиты от перебора, пароль передаётся целиком при каждом запросе.

   Где до сих пор применяется: закрытие служебных эндпоинтов на nginx
   (`auth_basic` + `htpasswd`), staging-окружения, простые внутренние интеграции
   и скрипты (`curl -u`), метрики Prometheus. Для приложений используют токены,
   OAuth или сессии.

   </details>

1. Есть URL, тело запроса. Что еще передается при запросе?
   <details>
   <summary>Ответ</summary>

   На уровне HTTP: **метод**, **версия протокола**, **заголовки** и, при
   использовании, cookie. Заголовки и составляют основную часть «остального»:

   ```text
   Host: example.com                   какой виртуальный хост
   User-Agent: curl/8.5.0              клиент
   Accept / Accept-Encoding / Accept-Language   что клиент готов принять
   Content-Type / Content-Length       формат и размер тела
   Authorization: Bearer ...           аутентификация
   Cookie: sessionid=...               состояние
   Referer, Origin                     откуда пришёл запрос
   X-Forwarded-For / X-Request-Id      добавляют прокси и балансировщики
   Connection: keep-alive
   ```

   Ниже по стеку передаётся ещё многое: IP-адреса источника и получателя, порты,
   TCP-флаги и номера последовательности, при HTTPS — SNI и согласование TLS.
   Это и есть то, что видит балансировщик и на что опираются правила
   маршрутизации.

   Полезно добавить практическую деталь: клиентский IP за прокси приложение
   узнаёт только из `X-Forwarded-For`/`X-Real-IP`, и этим заголовкам нельзя
   доверять, если их не выставил доверенный прокси (иначе легко подделать).

   </details>

1. Какие типы http-заголовков знаешь?
   <details>
   <summary>Ответ</summary>

   По назначению их делят на четыре группы:

   * **общие** (для запроса и ответа): `Date`, `Connection`, `Cache-Control`,
     `Via`, `Trailer`;
   * **запроса**: `Host`, `User-Agent`, `Accept*`, `Authorization`, `Cookie`,
     `Referer`, `Origin`, `If-None-Match`, `Range`;
   * **ответа**: `Server`, `Set-Cookie`, `Location`, `ETag`, `WWW-Authenticate`,
     `Retry-After`, `Access-Control-Allow-Origin`;
   * **сущности (представления)**: `Content-Type`, `Content-Length`,
     `Content-Encoding`, `Content-Language`, `Last-Modified`.

   Для эксплуатации важны отдельные группы: **кэширование** (`Cache-Control`,
   `ETag`, `Expires`, `Vary`), **проксирование** (`X-Forwarded-For`,
   `X-Forwarded-Proto`, `X-Real-IP`, `X-Request-Id`), **безопасность**
   (`Strict-Transport-Security`, `Content-Security-Policy`, `X-Frame-Options`,
   `X-Content-Type-Options`), **сжатие** (`Accept-Encoding`,
   `Content-Encoding`).

   Полезно добавить: заголовки с префиксом `X-` формально нестандартны, но
   де-факто закрепились; в HTTP/2 и HTTP/3 имена пишутся в нижнем регистре и
   сжимаются (HPACK/QPACK), а метод, путь и схема передаются как
   псевдо-заголовки `:method`, `:path`, `:scheme`.

   </details>

1. Что делает балансировщик нагрузки?
   <details>
   <summary>Ответ</summary>

   Распределяет входящие запросы между несколькими экземплярами приложения.
   Задачи: масштабирование (нагрузка делится), отказоустойчивость (вывод
   упавшего узла по health-check), обновления без простоя (drain соединений
   перед выключением инстанса), терминация TLS, единая точка для лимитов,
   логирования и маршрутизации.

   Уровни и алгоритмы:

   ```text
   L4 (TCP/UDP): быстрый, не видит HTTP  — HAProxy в tcp-режиме, LVS, NLB
   L7 (HTTP):    видит путь, заголовки, cookie — nginx, HAProxy, Traefik, Envoy

   алгоритмы: round-robin, weighted, least connections, IP hash /
              consistent hashing, least response time
   ```

   Что важно упомянуть про эксплуатацию: **health-check** (активные и пассивные)
   и вывод узла из ротации; **sticky sessions** для приложений с локальным
   состоянием (лучше state вынести и обойтись без них); идемпотентность при
   ретраях на другой апстрим; таймауты и `proxy_next_upstream`; передача
   клиентского IP через `X-Forwarded-For`; graceful shutdown и `SIGTERM` на
   стороне приложения. В Kubernetes роль балансировщика играют Service
   (kube-proxy), Ingress-контроллер и облачный LoadBalancer.

   </details>

### Linux

1. У нас есть какой-то диск, который хотим примонтировать в Linux. Как это можно сделать? Останется ли примонтирован диск после перезагрузки при монтировании командой `mount`. Опции монтирования `fstab` - какие есть, зачем нужны?
   <details>
   <summary>Ответ</summary>

   ```sh
   lsblk -f                                  # посмотреть диски и файловые системы
   mkfs.ext4 /dev/sdb1                       # если файловой системы нет
   blkid /dev/sdb1                           # узнать UUID
   mkdir -p /data
   mount /dev/sdb1 /data                     # монтирование вручную
   ```

   **Останется ли после перезагрузки** — нет. `mount` действует только до
   перезагрузки; чтобы монтирование было постоянным, нужна запись в `/etc/fstab`
   (или unit `.mount` в systemd):

   ```text
   UUID=1234-...  /data  ext4  defaults,noatime,nofail  0 2
   ```

   Порядок полей: источник, точка монтирования, тип ФС, опции, dump, fsck order.
   Источник лучше указывать по `UUID` или метке, а не по `/dev/sdb1` — имена
   устройств меняются при добавлении дисков.

   Полезные опции: `defaults` (rw, suid, dev, exec, auto, nouser, async),
   `noatime` (не писать время доступа — меньше износ и лишних записей), `ro`,
   `nofail` (не ронять загрузку, если диска нет — обязательно для сетевых и
   внешних дисков), `nosuid`, `nodev`, `noexec` (безопасность для
   пользовательских разделов), `discard` для SSD, `x-systemd.automount` и
   `_netdev` для сетевых ФС, `uid`/`gid` для FAT.

   После правки `fstab` проверять `mount -a` и `systemctl daemon-reload` **до**
   перезагрузки — иначе сервер может не загрузиться (как раз для этого
   `nofail`).

   </details>

1. Метрики. `I/O wait time` - что оно показывает? Как проверить загруженность диска? Как посмотреть количество свободной оперативной памяти?
   <details>
   <summary>Ответ</summary>

   `%wa` в `top` — доля времени, когда процессор **простаивал**, и при этом были
   незавершённые операции ввода-вывода. Это не «нагрузка на диск», а признак
   того, что процессам нечем заняться, пока они ждут диск или сеть. Высокий
   iowait при простое CPU — намёк на дисковое узкое место, но сам по себе он не
   доказывает проблему (например, при одном однопоточном процессе на
   многоядерной машине цифра может быть маленькой, хотя диск в полке).

   **Загруженность диска**:

   ```sh
   iostat -xz 1        # %util, await, r/s, w/s, avgqu-sz — основной инструмент
   iotop -o            # какие процессы читают и пишут
   pidstat -d 1
   dstat -d --top-io
   ```

   Смотреть на `%util` (насколько диск занят), `await` (время ожидания запроса),
   очередь и IOPS. На SSD и NVMe `%util` вводит в заблуждение (они обслуживают
   запросы параллельно) — важнее задержка.

   **Свободная оперативная память**:

   ```sh
   free -h             # смотреть колонку available, а не free
   cat /proc/meminfo
   vmstat 1            # si/so — свопинг
   ```

   </details>

1. Команда `free` - чем столбец free отличается от available. Что показывают остальные столбцы?
   <details>
   <summary>Ответ</summary>

   ```text
   total   всего физической памяти
   used    занято процессами (total - free - buff/cache, с поправкой на shared)
   free    полностью незанятая память — в Linux она стремится к нулю, и это норма
   shared  память, разделяемая процессами (tmpfs, shm)
   buff/cache  буферы и страничный кэш — ядро держит здесь данные с диска
   available   сколько реально можно выделить новому приложению без свопа
   ```

   Ключевое отличие: **`free`** — это память, которая вообще ни на что не
   используется, а **`available`** — оценка того, сколько можно получить,
   включая ту часть `buff/cache`, которую ядро отдаст без обращения к свопу (не
   отдаст только «грязные» и заблокированные страницы).

   Поэтому смотреть надо на `available`. Классическая ошибка новичка — увидеть
   `free` близко к нулю и решить, что памяти нет: Linux намеренно использует
   свободную память под кэш, потому что неиспользуемая память бесполезна.
   Реальные признаки нехватки — падение `available`, активный свопинг (`si`/`so`
   в `vmstat`) и срабатывания OOM killer в `dmesg`.

   </details>

1. Представим, что есть файл с логами. Внутри него есть сообщения типа Warning, INFO, ERROR и так далее. Как посмотреть только ошибки в файле лога? Как посмотреть саму ошибку и 10 строчек до и после неё?
   <details>
   <summary>Ответ</summary>

   ```sh
   grep ERROR app.log                      # только строки с ошибками
   grep -E 'ERROR|CRITICAL' app.log        # несколько уровней
   grep -c ERROR app.log                   # сколько всего
   grep -i error app.log                   # без учёта регистра

   grep -C 10 ERROR app.log                # ошибка + 10 строк до и после
   grep -B 10 -A 10 ERROR app.log          # то же самое явно
   grep -n -C 10 ERROR app.log             # с номерами строк
   ```

   Полезные дополнения к ответу: `tail -f app.log | grep --line-buffered ERROR`
   для наблюдения в реальном времени; `zgrep` для сжатых логов; `journalctl -p
   err -u nginx --since '1 hour ago'` для systemd; `awk '/ERROR/{print $1, $2,
   $NF}'` когда нужны отдельные поля; `grep ERROR app.log | sort | uniq -c |
   sort -rn` чтобы увидеть самые частые ошибки; `less +/ERROR` для
   интерактивного просмотра.

   И оговорка про многострочные ошибки (стектрейсы): `grep` покажет только
   строку с уровнем, поэтому либо `-A 30`, либо `awk` с диапазоном по шаблону,
   либо централизованный сбор логов, который склеивает многострочные записи.

   </details>

1. Какие механизмы ядра Linux используются для виртуализации?
   <details>
   <summary>Ответ</summary>

   Стоит разделить два случая.

   **Контейнеризация** (виртуализация на уровне ОС — Docker, LXC, Kubernetes):

   * **namespaces** — изоляция видимости: `pid`, `net`, `mnt`, `uts`, `ipc`,
     `user`, `cgroup`, `time`;
   * **cgroups (v2)** — ограничение и учёт ресурсов: CPU, память, IO, количество
     процессов;
   * **capabilities** — дробление прав root на отдельные разрешения
     (`CAP_NET_ADMIN` и так далее);
   * **seccomp** — фильтрация системных вызовов; **AppArmor** и **SELinux** —
     мандатный контроль доступа; `no_new_privs`;
   * **overlayfs** — слоистая файловая система образов; **veth**, **bridge**,
     **iptables/nftables**, **IPVS** — сеть.

   **Полная виртуализация** (KVM, QEMU): модуль ядра **KVM** плюс аппаратные
   расширения процессора (Intel VT-x, AMD-V), EPT/NPT для памяти, IOMMU и VFIO
   для передачи устройств, virtio для паравиртуализованных драйверов, vhost для
   ускорения сети и диска; управляется через libvirt.

   Ключевое отличие, которое стоит озвучить: контейнеры используют **одно общее
   ядро** и лишь изолируют процессы, а виртуальные машины запускают собственное
   ядро на гипервизоре — отсюда разница в накладных расходах и в степени
   изоляции.

   </details>

### Ansible

1. Чем плэйбук отличается от роли Ansible?
   <details>
   <summary>Ответ</summary>

   **Плейбук** — сценарий: что и на каких хостах выполнить. Это точка входа, где
   сопоставлены группы хостов (`hosts:`) с задачами и ролями.

   **Роль** — переиспользуемый, структурированный набор задач с собственными
   переменными, шаблонами, файлами и обработчиками. Она сама себя не запускает —
   её подключает плейбук.

   ```text
   site.yml                 <- плейбук
   roles/nginx/
   ├── tasks/main.yml
   ├── handlers/main.yml
   ├── templates/nginx.conf.j2
   ├── files/
   ├── vars/main.yml         <- переменные роли (высокий приоритет)
   ├── defaults/main.yml     <- значения по умолчанию (низкий приоритет)
   └── meta/main.yml         <- зависимости роли
   ```

   ```yaml
   - hosts: web
     become: true
     roles:
       - { role: nginx, nginx_port: 8080 }
   ```

   Аналогия: роль — библиотека, плейбук — программа, которая её вызывает. Роли
   делают конфигурацию переиспользуемой между проектами (в том числе через
   Ansible Galaxy) и позволяют не дублировать задачи; плейбук отвечает за
   порядок, окружение и целевые хосты. Рядом стоит упомянуть коллекции
   (collections) как современный способ распространения ролей и модулей.

   </details>

1. Какие типы переменных есть у роли Ansible?
   <details>
   <summary>Ответ</summary>

   У роли два «своих» места для переменных, и это ключевое различие:

   * **`defaults/main.yml`** — значения по умолчанию. Самый **низкий**
     приоритет, легко переопределяются извне. Здесь и должны лежать все
     настраиваемые параметры роли.
   * **`vars/main.yml`** — переменные роли. Приоритет **высокий**,
     переопределить их снаружи почти нечем (только `-e`). Здесь держат
     внутренние константы, которые менять не предполагается (например,
     соответствие имени пакета дистрибутиву).

   Дополнительно роль работает с переменными, объявленными в других местах:
   параметры при подключении роли (`roles: - { role: x, var: 1 }` — это `role
   params`, очень высокий приоритет), `include_role`/`vars:`, `set_fact` во
   время выполнения, `register` результатов, факты (`ansible_facts`), а также
   `group_vars`/`host_vars` инвентаря.

   Практика: всё настраиваемое — в `defaults`, с префиксом по имени роли
   (`nginx_port`, `nginx_workers`), чтобы не конфликтовать с другими ролями.

   </details>

1. Какой приоритет у переменных Ansible? Как переопределить переменную роли?
   <details>
   <summary>Ответ</summary>

   Ansible определяет 22 уровня; на интервью достаточно назвать порядок от
   низшего к высшему по группам:

   ```text
   1  command line values (например, -u user)
   2  role defaults  (defaults/main.yml)          <- самый низкий из "переменных"
   3  inventory file / script group_vars: all
   4  inventory group_vars: all
   5  playbook group_vars: all
   6  inventory group_vars: *
   7  playbook group_vars: *
   8  inventory file / script host_vars
   9  inventory host_vars
   10 playbook host_vars
   11 host facts / cached set_facts
   12 play vars, vars_prompt, vars_files
   13 role vars  (vars/main.yml)
   14 block vars
   15 task vars
   16 include_vars
   17 set_facts / registered vars
   18 role params и include params
   19 include_tasks / include_role params
   20 extra vars (-e)                              <- побеждает всегда
   ```

   Главное, что нужно помнить: `defaults/` — почти самый низкий приоритет,
   `vars/` — высокий, `-e` перебивает всё.

   **Как переопределить переменную роли**: если она в `defaults` — почти чем
   угодно: `group_vars`/`host_vars`, `vars:` в play, параметром при подключении
   роли (`roles: - { role: nginx, nginx_port: 8080 }`), `vars_files`,
   `set_fact`. Если она в `vars/main.yml` — только через `-e nginx_port=8080`
   (или через `include_role` с `vars:`), поэтому настраиваемые параметры туда и
   не кладут.

   </details>

1. Мы хотим собрать проект на Go. Какой порядок действий?
   <details>
   <summary>Ответ</summary>

   Локально:

   ```sh
   go mod download        # зависимости по go.mod / go.sum
   go vet ./...           # статические проверки
   go test ./... -race    # тесты
   CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
     go build -trimpath -ldflags="-s -w -X main.version=$CI_COMMIT_SHA" -o app ./cmd/api
   ```

   В контейнере — multi-stage, чтобы в образ попал только бинарник:

   ```dockerfile
   FROM golang:1.23 AS build
   WORKDIR /src
   COPY go.mod go.sum ./
   RUN go mod download                 # отдельный слой -> кэшируется
   COPY . .
   RUN CGO_ENABLED=0 go build -o /app ./cmd/api

   FROM gcr.io/distroless/static:nonroot
   COPY --from=build /app /app
   USER nonroot
   ENTRYPOINT ["/app"]
   ```

   Что важно проговорить: `CGO_ENABLED=0` даёт статический бинарник, которому не
   нужна libc — поэтому финальный образ может быть `scratch` или distroless; кэш
   модулей отдельным слоем (или `--mount=type=cache` в BuildKit) резко ускоряет
   сборку; версию и коммит прошивают через `-ldflags`; `-trimpath` для
   воспроизводимости; кросс-компиляция через `GOOS`/`GOARCH` (мультиарх —
   `docker buildx --platform`). В CI дальше: линтеры (`golangci-lint`), тесты с
   покрытием, сканирование образа (Trivy), пуш в registry с тегом по коммиту.

   </details>

1. Как поддерживали и разворачивали инфраструктуру с помощью Terraform?
   <details>
   <summary>Ответ</summary>

   Ответ по схеме «как устроен код → как устроен процесс → как решаются
   проблемы».

   **Код**: разделение на модули (сеть, кластер, база, приложение), окружения
   через отдельные каталоги или workspaces с одинаковыми модулями и разными
   `tfvars`, версии провайдеров и модулей зафиксированы (`required_version`,
   `.terraform.lock.hcl`), никаких ресурсов, созданных руками.

   **Состояние**: удалённый backend (S3 + DynamoDB, GCS, Terraform Cloud,
   Consul) с блокировкой и версионированием, шифрование, отдельный state на
   окружение, чтобы «сломать прод» из dev было невозможно.

   **Процесс**: изменения через merge request; в CI `fmt`, `validate`, `tflint`,
   `checkov`/`tfsec`, затем `plan` с публикацией в комментарий MR и ручное
   подтверждение `apply` для прода; секреты — из Vault или переменных CI, не в
   коде и не в state (state тоже содержит секреты — поэтому доступ к нему
   ограничен).

   **Эксплуатация**: `terraform import` для существующих ресурсов, `moved` блоки
   и `state mv` при рефакторинге, `-target` только как аварийная мера,
   регулярный `plan` по расписанию для отлова дрейфа, `prevent_destroy` на
   критичных ресурсах, разделение на слои, чтобы `apply` не длился полчаса.

   </details>

1. Что такое REST API?
   <details>
   <summary>Ответ</summary>

   REST — архитектурный стиль поверх HTTP: данные представлены ресурсами с URL,
   действия выражаются HTTP-методами, результат — кодом ответа и телом (обычно
   JSON).

   ```text
   GET    /servers        список         200
   GET    /servers/42     один           200 / 404
   POST   /servers        создать        201 + Location
   PUT    /servers/42     заменить       200 / 204
   DELETE /servers/42     удалить        204
   ```

   Принципы: клиент-серверность, stateless (сервер не хранит сессию между
   запросами), кэшируемость, единый интерфейс, слоистость.

   Для DevOps это в первую очередь про то, с чем работаешь ежедневно: API
   Kubernetes, GitLab, Vault, облаков — все они REST(-подобные). Отсюда
   практические вещи: аутентификация токеном в заголовке, коды ответов для
   ретраев (`429` и `5xx` — повторяем с экспоненциальной задержкой, `4xx` —
   нет), идемпотентность методов при повторах, лимиты запросов и пагинация,
   `curl` и `jq` как основной инструмент, OpenAPI-схема для генерации клиентов.

   </details>

1. У нас есть инфраструктура полностью без Ansible. Что нужно для того, чтобы начать им пользоваться?
   <details>
   <summary>Ответ</summary>

   Технически Ansible почти ничего не требует: он **agentless**. Нужны:

   1. **Управляющий хост** с Python и Ansible (либо контейнер, либо раннер CI).
   2. **Доступ по SSH** к целевым хостам (для Windows — WinRM или SSH):
      отдельный технический пользователь, ключи (не пароли), `become` через sudo
      с нужными правами, известные `known_hosts`.
   3. **Python на целевых хостах** — большинство модулей требуют интерпретатор
      (для «сырых» действий есть `raw`).
   4. **Инвентарь**: статический (`inventory.ini`/`yaml`) или динамический
      (плагины для AWS, GCP, Yandex Cloud), группы по роли и окружению,
      `group_vars`/`host_vars`.
   5. **Репозиторий с кодом**: структура (`playbooks/`, `roles/`,
      `inventories/prod|stage`), `requirements.yml` для внешних ролей и
      коллекций, `ansible.cfg`.

   Дальше — процесс: секреты в Ansible Vault или внешнем хранилище, проверка
   `ansible-lint` и `--check --diff` в CI, запуск из пайплайна, а не с ноутбука,
   тегирование задач, `serial` и `max_fail_percentage` для безопасного раската.

   Правильный порядок внедрения: начать с инвентаризации и одного безопасного
   сценария (например, сбор фактов или настройка пользователей и sshd),
   убедиться в идемпотентности, потом постепенно переносить конфигурацию
   существующих сервисов, а не пытаться описать всю инфраструктуру за один раз.
   И договориться, что ручные правки на хостах прекращаются — иначе код и
   реальность разъедутся.

   </details>

1. Как бы ты хранил чувствительные данные в Ansible плейбуках?
   <details>
   <summary>Ответ</summary>

   Базовый штатный инструмент — **Ansible Vault**: шифрование файлов и отдельных
   значений AES-256.

   ```sh
   ansible-vault create group_vars/prod/vault.yml
   ansible-vault encrypt_string 'p@ssw0rd' --name db_password
   ansible-playbook site.yml --vault-password-file .vault-pass   # в CI из переменной
   ```

   Практика: разделять переменные на открытые (`vars.yml`) и секретные
   (`vault.yml`) с одинаковыми именами через префикс (`db_password: "{{
   vault_db_password }}"`) — тогда видно, где что используется, без расшифровки;
   пароль Vault брать из переменной CI или скрипта, а не из файла в репозитории;
   `no_log: true` на задачах с секретами, чтобы они не попали в вывод и логи.

   Более зрелый вариант — **внешнее хранилище секретов**: HashiCorp Vault
   (lookup-плагин `community.hashi_vault`), AWS Secrets Manager, GCP Secret
   Manager, SOPS + age/KMS (популярно, потому что дружит с git и diff'ами),
   CyberArk. Плюсы: аудит доступа, ротация, короткоживущие динамические учётные
   данные, единый источник для всех инструментов, а не только для Ansible.

   Чего не делать: секреты в открытом виде в репозитории или в `extra-vars` в
   истории команд, в логах CI без маскирования, в переменных окружения раннера
   без ограничения области видимости, а также в `state`/артефактах. Плюс защита
   от случайного коммита — pre-commit хук с `gitleaks` или `detect-secrets`.

   </details>

### Docker

1. Из чего состоит Docker?
   <details>
   <summary>Ответ</summary>

   Docker — не один бинарник, а набор компонентов:

   ```text
   docker (CLI) --REST API--> dockerd (демон)
                                 |
                                 +-> containerd (управление жизненным циклом)
                                        +-> runc / shim (запуск по стандарту OCI)
                                               +-> namespaces, cgroups, overlayfs
   ```

   * **клиент `docker`** — командная строка, общается с демоном по сокету или
     TCP;
   * **демон `dockerd`** — API, сборка образов, сети, тома, оркестрация
     локальных контейнеров;
   * **containerd** — стандартный рантайм-менеджер (образы, снапшоты, запуск),
     сам по себе используется и Kubernetes;
   * **runc** — низкоуровневый запуск контейнера по спецификации OCI;
   * **BuildKit** — современный сборщик образов;
   * **registry** — хранилище образов (Docker Hub, Harbor, GitLab Registry);
   * **объекты**: образы, контейнеры, тома, сети, плагины.

   Полезно добавить: Kubernetes с версии 1.24 работает напрямую с containerd или
   CRI-O, без `dockerd` (dockershim удалён), но образы остаются совместимыми,
   потому что формат стандартизирован OCI.

   </details>

1. Отличие контейнеризации от виртуализации.
   <details>
   <summary>Ответ</summary>

   Виртуальная машина эмулирует железо: гипервизор (KVM, VMware, Hyper-V)
   запускает **собственное ядро** и полноценную ОС для каждой машины. Контейнер
   — это изолированный процесс на **общем ядре хоста**; изоляцию дают
   namespaces, ограничения — cgroups.

   ```text
   ВМ:         [приложение][библиотеки][гостевая ОС + ядро] -> гипервизор -> железо
   Контейнер:  [приложение][библиотеки] -> общее ядро хоста -> железо
   ```

   ```text
                     контейнер            виртуальная машина
   запуск            миллисекунды          десятки секунд
   накладные расходы почти нет             ядро + ОС на каждую ВМ
   размер образа     десятки МБ            гигабайты
   изоляция          на уровне ядра        аппаратная, сильнее
   ядро и ОС         только ОС хоста       любая гостевая ОС
   плотность         сотни на хост         десятки
   ```

   Практический вывод: контейнеры — для масштабирования приложений и одинакового
   окружения; ВМ — когда нужна другая ОС или ядро, жёсткая изоляция
   (мультитенантность, недоверенный код), специфические драйверы. На практике их
   комбинируют: Kubernetes-узлы — это ВМ, внутри которых работают контейнеры.
   Рядом стоит упомянуть «контейнеры с усиленной изоляцией» — gVisor, Kata
   Containers.

   </details>

1. Отличие `RUN`, `CMD` и `ENTRYPOINT`.
   <details>
   <summary>Ответ</summary>

   Они относятся к разным моментам жизни образа:

   * **`RUN`** выполняется **во время сборки** и создаёт новый слой: установка
     пакетов, компиляция. К запуску контейнера отношения не имеет.
   * **`ENTRYPOINT`** — команда, которая выполняется **при запуске** контейнера.
     Аргументы из `docker run` к ней добавляются.
   * **`CMD`** — команда или аргументы **по умолчанию** при запуске; легко
     переопределяются в `docker run`.

   ```dockerfile
   RUN apt-get update && apt-get install -y nginx   # сборка
   ENTRYPOINT ["nginx"]                              # запуск: сама программа
   CMD ["-g", "daemon off;"]                         # запуск: аргументы по умолчанию
   ```

   Что стоит добавить: `RUN` может быть много, а действующими остаются только
   последние `CMD` и `ENTRYPOINT`; предпочтительна exec-форма (`["cmd"]`),
   потому что shell-форма запускает процесс через `sh -c` и он не получает
   `SIGTERM`; в Kubernetes `command` соответствует `ENTRYPOINT`, а `args` —
   `CMD`.

   </details>

1. Без какой инструкции не запустится контейнер?
   <details>
   <summary>Ответ</summary>

   Формально образ обязателен только `FROM` (или `FROM scratch`) — без него
   Dockerfile не соберётся. А **запустить** контейнер нельзя без команды: если в
   образе нет ни `CMD`, ни `ENTRYPOINT` и команда не передана в `docker run`,
   получим ошибку «no command specified».

   То есть корректный ответ: нужна **исполняемая команда** — либо `ENTRYPOINT`,
   либо `CMD` в образе, либо аргумент при запуске:

   ```sh
   docker run alpine            # сработает: у образа alpine есть CMD ["/bin/sh"]
   docker run scratch-based     # ошибка, если ни CMD, ни ENTRYPOINT не заданы
   docker run scratch-based /app  # сработает: команда передана явно
   ```

   Уточнение про базовые образы: `CMD` наследуется от родителя, поэтому `FROM
   nginx` уже приносит команду запуска. И отдельная частая причина «контейнер
   сразу завершился» — не отсутствие команды, а то, что процесс не является
   долгоживущим (или ушёл в фон): контейнер живёт ровно столько, сколько живёт
   процесс с PID 1.

   </details>

1. На каких технологиях построена контейнеризация (Docker)?
   <details>
   <summary>Ответ</summary>

   Всё это механизмы ядра Linux:

   * **namespaces** — изоляция видимости: `pid` (свои процессы и PID 1), `net`
     (свой стек, интерфейсы, порты), `mnt` (своя файловая система), `uts`
     (hostname), `ipc`, `user` (маппинг uid), `cgroup`, `time`;
   * **cgroups (v2)** — ограничение и учёт ресурсов: CPU, память (и OOM-kill при
     превышении), IO, число процессов;
   * **capabilities** — дробление прав root (`CAP_NET_BIND_SERVICE` и прочие)
     вместо «всё или ничего»;
   * **seccomp** — фильтр системных вызовов; **AppArmor**/**SELinux** —
     мандатный контроль доступа; `no_new_privs`;
   * **overlayfs** — слоистая файловая система: образ (только чтение) плюс
     записываемый слой контейнера, copy-on-write;
   * **сеть**: `veth`-пары, bridge `docker0`, `iptables`/`nftables` для NAT и
     публикации портов, CNI-плагины в Kubernetes;
   * **стандарты OCI**: image spec и runtime spec, runc как эталонная
     реализация.

   Ключевая мысль: контейнер — это не «мини-виртуалка», а обычный процесс хоста,
   которому ядро ограничило видимость (namespaces) и ресурсы (cgroups). Отсюда и
   все свойства: мгновенный запуск, малые накладные расходы и более слабая
   изоляция, чем у ВМ.

   </details>

1. Как изменить настройки ядра в контейнере?
   <details>
   <summary>Ответ</summary>

   Важно понимать, что ядро **общее** с хостом: часть параметров вообще нельзя
   менять из контейнера, а часть изолирована по namespace (например, `net.*` при
   своём network namespace, `kernel.shm*`, часть `fs.*`).

   Варианты:

   ```sh
   docker run --sysctl net.core.somaxconn=1024 ...     # безопасные, изолированные
   docker run --ulimit nofile=65535:65535 ...          # лимиты процесса
   docker run --privileged ... sysctl -w vm.max_map_count=262144   # опасно
   ```

   В Kubernetes:

   ```yaml
   securityContext:
     sysctls:                       # только "безопасные" по умолчанию
       - name: net.core.somaxconn
         value: '1024'
   ```

   Небезопасные sysctl (`vm.max_map_count`, `net.ipv4.ip_forward`) нужно
   разрешить на kubelet (`--allowed-unsafe-sysctls`), иначе pod не запустится;
   альтернатива — **init-контейнер с `privileged: true`**, который выставляет
   параметр на узле, или настройка через DaemonSet и `tuned`/`sysctl.d` прямо на
   узлах.

   Правильный вывод для интервью: то, что глобально для ядра, меняют **на
   хосте** (через конфигурацию узлов, а не руками), а в контейнер отдают только
   namespaced-параметры; `--privileged` — крайняя мера, потому что это
   фактически отказ от изоляции.

   </details>

### Helm

1. Какие варианты знаешь, как развернуть Helm chart на 3 разные зоны?
   <details>
   <summary>Ответ</summary>

   Речь о том, как одним чартом обслужить несколько зон или окружений.

   * **`values` на зону**: один чарт, три файла (`values-eu.yaml`,
     `values-us.yaml`, `values-ru.yaml`) и три релиза; различия — в
     `nodeSelector`, `topologyKey`, ingress-хостах, количестве реплик. Самый
     простой и распространённый путь.
   * **Один релиз с распределением по зонам внутри**:
     `topologySpreadConstraints` с `topologyKey: topology.kubernetes.io/zone`
     (или anti-affinity) — поды сами равномерно раскладываются по трём зонам
     одного кластера. Это про отказоустойчивость, а не про отдельные релизы.
   * **Три кластера (по зоне) и GitOps**: Argo CD ApplicationSet с генератором
     по кластерам или Flux с `Kustomization` на каждый — один чарт, три
     автоматических раската, разница в overlay.
   * **Umbrella-чарт** с тремя подчартами-зонами (или чарт с `range` по списку
     зон в шаблонах) — если релиз должен быть один.
   * **helmfile / terraform helm provider** — декларативное описание набора
     релизов с общими значениями и различиями по окружениям.

   Что стоит проговорить: сначала уточнить, зоны — это availability zones одного
   кластера или разные кластеры и регионы; дальше — где живёт состояние (базы,
   PVC привязаны к зоне), как устроен трафик (global LB, GeoDNS), как
   обеспечивается версионирование релизов и откат. И общий принцип: различия
   окружений — в values, а не в форке чарта.

   </details>

1. Helm писал для проектов один общий или разные для разных проектов? Писал ли зависимости для Helm?
   <details>
   <summary>Ответ</summary>

   Оба подхода встречаются, и правильный ответ — объяснить, когда какой.

   **Общий (библиотечный) чарт**: одинаковые по структуре сервисы (десяток
   stateless-приложений на одном стеке) описываются одним чартом, а различия
   задаются через `values`. Плюсы — единые стандарты (probes, ресурсы, метки,
   HPA), правку делаешь в одном месте, новый сервис подключается за минуты.
   Минусы — чарт обрастает условиями `if` и становится сложным, а любое
   изменение затрагивает всех.

   **Отдельные чарты**: подходят для сервисов с существенно разной структурой
   (stateful, свои CRD, сложная топология). Проще читать, но появляется
   дублирование.

   **Компромисс на практике**: library chart (`type: library`) с общими
   шаблонами и helpers, который подключается как зависимость к тонким чартам
   сервисов.

   **Зависимости** — да, это `dependencies` в `Chart.yaml` (`helm dependency
   update`, `charts/`, `condition` и `tags` для включения и отключения, алиасы
   для двух экземпляров одной зависимости), а также umbrella-чарты, собирающие
   приложение с базой и брокером. Оговорка из опыта: тянуть в зависимости чарты
   баз данных удобно для dev и плохо для прода — там базу выносят в
   managed-сервис или отдельный оператор.

   </details>

1. Что такое Helm? Зачем используется?
   <details>
   <summary>Ответ</summary>

   Helm — пакетный менеджер для Kubernetes. Он превращает набор YAML-манифестов
   в **шаблонизированный пакет (чарт)** с параметрами и ведёт учёт установленных
   **релизов**.

   ```text
   chart/
   ├── Chart.yaml          метаданные и зависимости
   ├── values.yaml         параметры по умолчанию
   └── templates/          манифесты с шаблонами Go template
       ├── deployment.yaml
       └── _helpers.tpl
   ```

   ```sh
   helm upgrade --install api ./chart -f values-prod.yaml -n prod
   helm list -n prod; helm history api; helm rollback api 3
   ```

   Зачем: не копировать одинаковые манифесты между окружениями (разница — в
   `values`), версионировать поставку приложения и **откатываться** одной
   командой, ставить готовые сторонние компоненты из репозиториев
   (ingress-nginx, prometheus-stack), описывать зависимости, добавлять хуки
   (миграции перед обновлением).

   Минусы, о которых полезно сказать: шаблоны на Go template плохо читаются при
   разрастании, `helm template` обязателен для отладки, состояние релизов
   хранится в секретах кластера, а трёхсторонний merge при обновлении иногда
   даёт неожиданные результаты. Альтернативы — kustomize (наложение патчей без
   шаблонов) и операторы; в GitOps Helm часто используется как рендерер внутри
   Argo CD или Flux.

   </details>

1. Мы задеплоили Helm chart и потом в темплейте поменяли значения replicaCount подов в Deployment, и потом пишем `helm upgrade --install`. Что произойдет в Kubernetes?
   <details>
   <summary>Ответ</summary>

   При `helm upgrade --install` Helm отрендерит шаблоны заново, сравнит с
   предыдущим релизом и отправит патч в Kubernetes: в Deployment изменится поле
   `spec.replicas`. Дальше уже сам контроллер приведёт число подов к новому
   значению — добавит или удалит их. Новая ревизия релиза появится в `helm
   history`, а перезапуска существующих подов не произойдёт: `replicas` не
   входит в шаблон пода, поэтому новый ReplicaSet не создаётся.

   Важные оговорки, которые и проверяют вопросом:

   * если на Deployment настроен **HPA**, он владеет `replicas`, и Helm начнёт с
     ним конфликтовать: после апгрейда число подов сначала станет указанным в
     чарте, а потом HPA вернёт своё. Поэтому при HPA поле `replicas` в шаблоне
     обычно не задают вовсе;
   * если поды меняли руками (`kubectl scale`), Helm об этом не знает — его
     трёхсторонний merge сравнивает старый манифест, новый манифест и текущее
     состояние, и ручное изменение будет перезаписано;
   * уменьшение реплик до нуля остановит приложение, а `--atomic` и `--wait`
     заставят Helm дождаться готовности и откатиться при неудаче.

   </details>

1. Точно такой же кейс, но с ConfigMap. Что будет?
   <details>
   <summary>Ответ</summary>

   ConfigMap обновится в кластере — и на этом всё: **поды не перезапустятся**,
   потому что их спецификация не изменилась. Отсюда типичная проблема «поменяли
   конфиг, а приложение работает по старому».

   Что происходит дальше зависит от способа использования:

   * ConfigMap **смонтирован как volume** — kubelet со временем (порядка минуты,
     по своему периоду синхронизации) обновит файлы внутри контейнера. Но
     приложение подхватит их только если умеет перечитывать конфигурацию (или
     рядом есть reloader-сайдкар). Для `subPath`-монтирования файлы **не**
     обновляются вовсе;
   * ConfigMap проброшен в **переменные окружения** (`envFrom`, `env`) — внутри
     процесса они не меняются никогда, нужен рестарт пода.

   Как делают правильно:

   ```yaml
   # в шаблоне Deployment
   annotations:
     checksum/config: >-
       {{ include (print $.Template.BasePath "/configmap.yaml")
          . | sha256sum }}
   ```

   Хэш конфигурации в аннотации пода меняется вместе с ConfigMap, поэтому Helm
   создаёт новый ReplicaSet и происходит нормальный rolling restart.
   Альтернативы: `stakater/Reloader`, неизменяемые ConfigMap с именем,
   включающим хэш (тогда меняется имя ссылки), `kubectl rollout restart` после
   апгрейда.

   </details>

### Kubernetes

1. Работал с Kubernetes? Расскажи про свой опыт.
   <details>
   <summary>Ответ</summary>

   Отвечать честно, обозначая границу «пользовался кластером» и «эксплуатировал
   кластер», и говорить конкретикой.

   Что уместно перечислить: какие объекты писал и поддерживал (Deployment,
   StatefulSet, Service, Ingress, ConfigMap, Secret, CronJob, HPA, PDB), как
   устроен деплой (Helm, kustomize, Argo CD или Flux, пайплайны GitLab CI), как
   настроены probes, лимиты и реквесты, как организованы namespace и права
   (RBAC, ServiceAccount), как собираются метрики и логи (prometheus-stack,
   Loki), как решались инциденты (`kubectl describe`/`logs`/`events`, OOMKilled,
   CrashLoopBackOff, Pending из-за ресурсов, проблемы с PVC).

   Если был опыт эксплуатации самого кластера — добавить: как разворачивали
   (kubeadm, kops, managed-сервис), обновление версий, CNI и CoreDNS,
   ingress-контроллер, cert-manager, бэкап etcd (Velero), autoscaler узлов.

   Хороший ответ обязательно содержит один-два случая «было плохо — сделали так
   — стало хорошо»: например, приложение падало по OOM, разобрались по метрикам
   и `dmesg`, подняли лимит и починили утечку, добавили алерт.

   </details>

1. Из чего состоит Kubernetes (архитектура)?
   <details>
   <summary>Ответ</summary>

   ```text
   control plane                        worker node
   ├── kube-apiserver   (единая точка,   ├── kubelet     (запускает поды,
   │                     REST, авторизация)│               следит за их состоянием)
   ├── etcd             (хранилище       ├── kube-proxy  (правила сети для Service)
   │                     всего состояния)└── container runtime (containerd, CRI-O)
   ├── kube-scheduler   (выбирает узел
   │                     для пода)
   └── kube-controller-manager (контроллеры: Deployment, ReplicaSet, Node, ...)
       (+ cloud-controller-manager в облаке)
   ```

   Как это работает: клиент (`kubectl`) обращается к API-серверу, тот проверяет
   права и валидирует объект и сохраняет его в etcd; контроллеры через watch
   видят расхождение желаемого и текущего состояния и создают нужные объекты;
   scheduler назначает поду узел; kubelet на узле через CRI поднимает контейнеры
   и докладывает статус обратно. Это цикл согласования (reconciliation loop) —
   ключевая идея Kubernetes.

   Рядом стоит назвать: CoreDNS (обнаружение сервисов), CNI-плагин (Calico,
   Cilium) для сети, CSI для дисков, metrics-server для HPA, ingress-контроллер
   как точка входа трафика; etcd требует кворума, отсюда нечётное число узлов
   control plane.

   </details>

1. Что такое pod, для чего он нужен?
   <details>
   <summary>Ответ</summary>

   Pod — минимальная единица планирования в Kubernetes: один или несколько
   контейнеров, которые всегда запускаются **вместе на одном узле** и делят
   network namespace (общий IP и порты, друг друга видят по `localhost`), тома и
   жизненный цикл.

   Зачем нужна такая обёртка, а не «просто контейнер»: некоторым процессам нужно
   жить рядом и иметь общее пространство — сайдкары (прокси Envoy, сборщик
   логов, обновлятор конфигурации), init-контейнеры для подготовки (миграции,
   ожидание зависимости, права на volume), адаптеры. Плюс это абстракция от
   рантайма: Kubernetes управляет подами, а не Docker'ом.

   Что важно добавить: pod по своей природе **эфемерный** — его не
   восстанавливают и не «лечат», а пересоздают; поэтому напрямую поды почти не
   создают, за них отвечают контроллеры (Deployment, StatefulSet, DaemonSet,
   Job). У pod'а один IP на всю группу контейнеров, и он меняется при
   пересоздании — отсюда нужны Service. Обычное правило: один основной контейнер
   на pod плюс вспомогательные сайдкары, а не «все сервисы в одном поде».

   </details>

1. Namespace в Kubernetes. Для чего он?
   <details>
   <summary>Ответ</summary>

   Namespace — логическое разделение одного кластера на области видимости для
   объектов. Внутри namespace имена уникальны, между namespace — нет.

   Для чего используется:

   * **изоляция окружений и команд**: `dev`, `stage`, `prod`, `team-a` в одном
     кластере;
   * **права доступа**: RBAC чаще всего выдаётся на namespace (Role +
     RoleBinding);
   * **квоты и лимиты**: `ResourceQuota` (сколько всего CPU, памяти, объектов) и
     `LimitRange` (значения по умолчанию для контейнеров);
   * **сетевые политики**: NetworkPolicy обычно описывается в границах
     namespace;
   * **удобство**: DNS-имена вида `service.namespace.svc.cluster.local`,
     `kubectl -n`, удаление всего окружения одной командой.

   Оговорки: namespace — **не** граница безопасности сама по себе (без
   NetworkPolicy поды видят друг друга между namespace, и узлы общие);
   кластерные объекты (Node, PersistentVolume, StorageClass, ClusterRole, CRD) в
   namespace не входят; namespace `default` в проде обычно не используют, а
   `kube-system` не трогают.

   </details>

1. Чем можно разворачивать поды? Отличие Deployment, StatefulSet и ReplicaSet.
   <details>
   <summary>Ответ</summary>

   Контроллеры, создающие поды: **ReplicaSet**, **Deployment**, **StatefulSet**,
   **DaemonSet**, **Job**, **CronJob** (плюс `ReplicationController` как
   устаревший вариант и поды, созданные операторами).

   * **ReplicaSet** — держит заданное число одинаковых подов. Умеет только это:
     обновления версии образа с раскатом у него нет. Напрямую его почти не
     создают.
   * **Deployment** — управляет ReplicaSet'ами и добавляет то, что нужно на
     практике: rolling update (создаёт новый ReplicaSet и постепенно переключает
     трафик), история ревизий и `rollout undo`, `maxSurge`/`maxUnavailable`,
     пауза раската. Для stateless-приложений это выбор по умолчанию.
   * **StatefulSet** — для приложений с состоянием и идентичностью: поды
     получают **стабильные имена** (`db-0`, `db-1`) и стабильные тома
     (`volumeClaimTemplates` создаёт PVC на каждый под), запускаются и удаляются
     **по порядку**, работают с headless Service для индивидуального DNS. Нужен
     базам, Kafka, ZooKeeper, Elasticsearch.

   ```text
   Deployment  -> ReplicaSet -> поды со случайными именами, взаимозаменяемы
   StatefulSet ->               поды 0..N-1, свои PVC, порядок и идентичность
   ```

   Отдельно стоит помнить: удаление StatefulSet не удаляет PVC (данные остаются
   намеренно), а масштабирование вниз идёт с конца.

   </details>

1. Как Kubernetes-сервис находит, куда отправлять запросы?
   <details>
   <summary>Ответ</summary>

   Service — это не прокси-процесс, а правило маршрутизации. Механика:

   1. У Service есть **селектор по меткам** (`selector: app=api`).
   2. Контроллер endpoints (сейчас **EndpointSlice**) постоянно пересчитывает
      список **готовых** подов, подходящих под селектор, и хранит их IP и порты.
   3. На каждом узле **kube-proxy** (или eBPF-датапath в Cilium) читает
      EndpointSlice и настраивает правила ядра (`iptables` или `IPVS`), которые
      заворачивают трафик, идущий на ClusterIP, в один из этих подов.
   4. Клиент внутри кластера обращается по имени —
      `api.default.svc.cluster.local`, — CoreDNS отдаёт ClusterIP, а дальше
      работают правила из пункта 3.

   ```text
   pod -> DNS (CoreDNS) -> ClusterIP -> iptables/IPVS -> IP конкретного пода
   ```

   Ключевые следствия: в списке endpoints оказываются только поды, прошедшие
   **readiness probe** — именно так реализуется вывод из ротации; балансировка
   случайная (или по алгоритму IPVS), «умной» её не назвать; для
   headless-сервиса (`clusterIP: None`) DNS отдаёт сразу IP подов;
   `externalTrafficPolicy` и topology-aware routing влияют на выбор узла.

   </details>

1. kube-proxy. Расскажи подробнее.
   <details>
   <summary>Ответ</summary>

   Компонент, работающий на каждом узле (обычно как DaemonSet). Он **не
   проксирует трафик сам** (кроме устаревшего userspace-режима), а программирует
   ядро: следит через API за Service и EndpointSlice и поддерживает правила,
   которые заворачивают трафик с ClusterIP или NodePort на IP конкретных подов.

   Режимы:

   * **iptables** (по умолчанию) — правила DNAT в цепочках `KUBE-SERVICES`;
     выбор бэкенда случайный. Просто и надёжно, но при тысячах сервисов таблицы
     разрастаются и обновление правил становится медленным (`O(n)` по числу
     правил).
   * **IPVS** — балансировка средствами ядра с хэш-таблицами: масштабируется
     лучше, есть алгоритмы (`rr`, `lc`, `sh`).
   * **nftables** — современная замена iptables (бета в свежих версиях).
   * **userspace** — исторический, не используется.

   Что полезно добавить: часть CNI (Cilium в режиме `kube-proxy replacement`)
   заменяет kube-proxy на eBPF — быстрее и без iptables; kube-proxy обслуживает
   **только** Service, за сеть между подами отвечает CNI; при отладке смотрят
   `iptables-save | grep KUBE`, `ipvsadm -Ln`, логи kube-proxy и наличие подов в
   EndpointSlice.

   </details>

1. Какие есть сущности для управления подами?
   <details>
   <summary>Ответ</summary>

   ```text
   ReplicaSet   — N одинаковых подов (обычно им управляет Deployment)
   Deployment   — ReplicaSet + rolling update, история, откат (stateless)
   StatefulSet  — стабильные имена и тома, порядок запуска (базы, брокеры)
   DaemonSet    — по одному поду на каждый (подходящий) узел: агенты,
                  сборщики логов, CNI, node-exporter
   Job          — запустить до успешного завершения (миграция, разовая задача)
   CronJob      — Job по расписанию
   ```

   Рядом стоят объекты, которые управляют не созданием, а **поведением** уже
   существующих подов:

   * **HorizontalPodAutoscaler** — меняет число реплик по метрикам;
   * **VerticalPodAutoscaler** — подбирает requests и limits;
   * **PodDisruptionBudget** — не даёт вытеснить слишком много подов при
     обслуживании узлов;
   * **PriorityClass** и **preemption** — кого вытеснять при нехватке ресурсов;
   * **ResourceQuota** и **LimitRange** — границы в namespace;
   * **операторы и CRD** — собственные контроллеры для сложных систем (Postgres
     Operator, Strimzi для Kafka).

   Общий принцип: напрямую поды не создают — их всегда создаёт контроллер, чтобы
   работало самовосстановление.

   </details>

1. Отличие ReplicaSet, Deployment, StatefulSet и DaemonSet.
   <details>
   <summary>Ответ</summary>

   ```text
   ReplicaSet  держит N одинаковых подов; без раскатов и истории
   Deployment  управляет ReplicaSet'ами: rolling update, ревизии, откат
   StatefulSet стабильные имена (app-0, app-1), свои PVC на под,
               порядок запуска и удаления, headless Service
   DaemonSet   по одному поду на каждый подходящий узел; масштабируется
               вместе с числом узлов, а не параметром replicas
   ```

   Когда что:

   * **Deployment** — обычные stateless-сервисы (API, воркеры, фронтенд). 99%
     приложений;
   * **StatefulSet** — базы данных, Kafka, ZooKeeper, Elasticsearch: всё, где
     узлу нужна собственная идентичность и собственный том;
   * **DaemonSet** — инфраструктурные агенты: сборщик логов (Fluent Bit,
     promtail), `node-exporter`, CNI-плагин, CSI-драйвер, агент безопасности;
   * **ReplicaSet** — только как деталь реализации Deployment.

   Полезные детали: у DaemonSet нет `replicas`, зато есть `nodeSelector`,
   `affinity` и толерантности (чтобы попадать и на мастера); StatefulSet при
   удалении **не** удаляет PVC; у Deployment есть `maxSurge`/`maxUnavailable`, у
   StatefulSet — `podManagementPolicy` и `partition` для поэтапного обновления.

   </details>

1. Для какой абстракции не нужен Kube scheduler?
   <details>
   <summary>Ответ</summary>

   Для **DaemonSet** — исторически поды DaemonSet назначались на узлы
   контроллером напрямую (`spec.nodeName`), минуя scheduler; начиная с
   Kubernetes 1.12 их всё же планирует default scheduler, но решение «на каком
   узле» по-прежнему определяется не им, а самой сутью DaemonSet (по одному поду
   на каждый узел).

   Вторая и более точная категория — **static pods**: их kubelet читает из
   каталога на узле (`/etc/kubernetes/manifests`) и запускает сам, вообще без
   участия API-сервера и планировщика. Именно так поднимаются компоненты control
   plane при установке через kubeadm (`kube-apiserver`, `etcd`,
   `kube-controller-manager`, `kube-scheduler`) — иначе получился бы замкнутый
   круг.

   Также scheduler не участвует, если в манифесте пода **явно указан**
   `spec.nodeName`: под сразу привязан к узлу.

   Хороший ответ проговаривает разницу: DaemonSet — «планирование
   предопределено», static pod — «планировщика нет вовсе».

   </details>

1. Какие есть ограничения ресурсов в Kubernetes (QoS)?
   <details>
   <summary>Ответ</summary>

   Для контейнера задаются **requests** (сколько гарантированно нужно — по ним
   scheduler выбирает узел) и **limits** (потолок). По их соотношению Kubernetes
   присваивает поду **класс QoS**:

   ```text
   Guaranteed  requests == limits для CPU и памяти у всех контейнеров
               -> лучшая защита, вытесняется последним
   Burstable   requests заданы и меньше limits (или limits нет)
               -> может брать больше при наличии ресурсов
   BestEffort  ни requests, ни limits не заданы
               -> убивается первым при нехватке памяти
   ```

   Как это работает на практике: CPU — сжимаемый ресурс, превышение лимита
   приводит к **throttling** (процесс притормаживают через cgroups); память —
   несжимаемый, превышение лимита даёт **OOMKilled**. При нехватке памяти на
   узле kubelet вытесняет поды в порядке BestEffort → Burstable → Guaranteed,
   учитывая ещё и превышение requests.

   Рядом стоит назвать: `LimitRange` (значения по умолчанию и границы в
   namespace), `ResourceQuota` (суммарные лимиты на namespace), `PriorityClass`
   и preemption, ephemeral-storage как третий ресурс, extended resources (GPU).
   И практику: requests ставить по реальному потреблению (из метрик), лимит
   памяти — обязательно, лимит CPU — с осторожностью, потому что throttling
   часто вреднее, чем небольшое превышение.

   </details>

1. Минусы request ограничения.
   <details>
   <summary>Ответ</summary>

   `requests` — это то, что scheduler **резервирует** на узле, а не то, что
   процесс реально использует. Отсюда проблемы:

   * **недоутилизация**: зарезервировано много, потребляется мало — узлы
     выглядят «занятыми», хотя ресурсы простаивают, и кластер обходится дороже;
   * **поды не планируются** (`Pending`, `Insufficient cpu/memory`), хотя
     фактическая загрузка узлов низкая — классическая ситуация с завышенными
     requests;
   * **заниженные requests** — обратная беда: узел переподписан, поды
     конкурируют за CPU, страдают latency, а при нехватке памяти начинается
     вытеснение и OOM (BestEffort и Burstable уходят первыми);
   * **HPA считает загрузку в процентах от requests**, поэтому неверные requests
     ломают автоскейлинг: при завышенном значении HPA не сработает вовремя, при
     заниженном — начнёт масштабировать на пустом месте;
   * **cluster autoscaler** тоже опирается на requests: он добавит узлы из-за
     резервов, а не из-за реальной нагрузки;
   * **подбор вручную не масштабируется**: значения быстро устаревают после
     изменений в коде.

   Что с этим делают: считают requests по фактическим метрикам (p95
   потребления), пересматривают их регулярно, применяют VPA в режиме
   рекомендаций, разделяют профили нагрузки по нодпулам, а для «шумных» пиков
   полагаются на Burstable-класс.

   </details>

1. Варианты, как можно выкинуть приложения наружу.
   <details>
   <summary>Ответ</summary>

   ```text
   ClusterIP        только внутри кластера (по умолчанию)
   NodePort         порт 30000–32767 на каждом узле — просто, но некрасиво
   LoadBalancer     облачный балансировщик с внешним IP (в bare-metal —
                    MetalLB)
   Ingress          L7-маршрутизация по хосту и пути + TLS, один вход на
                    много сервисов (ingress-nginx, Traefik)
   Gateway API      современная замена Ingress: разделение ролей,
                    гибкая маршрутизация
   ExternalName     DNS-алиас на внешний сервис
   port-forward     kubectl port-forward — только для отладки
   hostNetwork /    под слушает порт узла напрямую — для инфраструктурных
   hostPort         агентов
   ```

   Типовая продовая схема: облачный LoadBalancer → ingress-контроллер →
   Ingress-правила → Service → поды; TLS-сертификаты выдаёт cert-manager,
   DNS-записи — external-dns.

   Что стоит добавить: `NodePort` подходит для тестов и как бэкенд для внешнего
   балансировщика; `LoadBalancer` на каждый сервис в облаке дорого — поэтому и
   ставят один ingress; для не-HTTP трафика (TCP, gRPC, TLS passthrough) нужны
   отдельные настройки контроллера или Gateway API; сервисные меши (Istio,
   Linkerd) добавляют свой ingress-gateway.

   </details>

1. Можно ли сделать так, чтобы pod всегда попадал на определенную ноду?
   <details>
   <summary>Ответ</summary>

   Да, и способов несколько — от жёстких к гибким:

   ```yaml
   # 1. nodeName — прямое указание, планировщик не участвует
   spec: { nodeName: worker-3 }

   # 2. nodeSelector — по метке узла, простой и самый частый вариант
   spec: { nodeSelector: { disktype: ssd } }

   # 3. nodeAffinity — то же, но с выражениями и "мягким" вариантом
   affinity:
     nodeAffinity:
       requiredDuringSchedulingIgnoredDuringExecution: ...    # обязательно
       preferredDuringSchedulingIgnoredDuringExecution: ...   # желательно
   ```

   Плюс дополнительные механизмы: **taints и tolerations** (узел «отталкивает»
   все поды, кроме тех, у кого есть толерантность — так выделяют узлы под GPU
   или под системные компоненты), **podAffinity и podAntiAffinity** (рядом с
   определёнными подами или, наоборот, порознь), **topologySpreadConstraints**
   для равномерного распределения по зонам, **PriorityClass**.

   Что важно проговорить: `nodeName` — плохая практика (нет отказоустойчивости:
   узел выключили — под не переедет, `Pending`); правильный способ — метки плюс
   affinity, а для выделенных узлов — комбинация taint + toleration +
   nodeSelector. И помнить, что `IgnoredDuringExecution` означает: правила
   проверяются только при планировании, уже запущенный под не будет переселён
   при изменении меток.

   </details>

1. Отличие label и selector.
   <details>
   <summary>Ответ</summary>

   **Label** — пара «ключ-значение», навешенная на объект (`app: api`, `env:
   prod`, `version: v2`). Это метаданные для группировки, они не влияют на
   поведение сами по себе.

   **Selector** — запрос по меткам: «выбери объекты, у которых такие метки». Он
   и превращает метки в механизм связывания объектов.

   ```yaml
   # Deployment: pod получит метки
   template:
     metadata:
       labels: { app: api }

   # Service: находит поды по метке
   spec:
     selector: { app: api }
   ```

   Где используются селекторы: Service → поды, ReplicaSet и Deployment → свои
   поды, NetworkPolicy, PodDisruptionBudget, `kubectl get pods -l app=api`,
   `nodeSelector` (узлы). Виды: equality-based (`app=api`, `env!=dev`) и
   set-based (`env in (prod, stage)`, `!legacy` — доступны в
   `matchExpressions`).

   Отличать от **аннотаций**: они тоже «ключ-значение», но по ним нельзя искать
   — это место для произвольных метаданных (описания, хэши конфигурации,
   настройки контроллеров). И важная практическая деталь: `selector` в
   Deployment после создания **иммутабелен**, а метки рекомендуется называть по
   стандарту `app.kubernetes.io/name`, `app.kubernetes.io/instance`.

   </details>

1. Как ты будешь реализовывать скейлинг приложений в кластере?
   <details>
   <summary>Ответ</summary>

   Три уровня, и полезно назвать все:

   * **По числу подов — HorizontalPodAutoscaler**: по CPU и памяти относительно
     `requests`, а лучше по прикладным метриками через `custom.metrics` или KEDA
     (длина очереди RabbitMQ или лаг Kafka — куда честнее CPU для воркеров).
     Настраивают `minReplicas`, `maxReplicas`, поведение (`behavior`) для
     сглаживания «дребезга».
   * **По ресурсам пода — VerticalPodAutoscaler**: подбирает requests и limits;
     обычно используют в режиме рекомендаций, потому что применение изменений
     перезапускает поды (и VPA плохо совместим с HPA по тем же метрикам).
   * **По числу узлов — Cluster Autoscaler или Karpenter**: добавляет и убирает
     узлы, когда поды не помещаются или узлы простаивают.

   Чтобы это работало, приложение должно быть готово к масштабированию: быть
   stateless (сессии и кэш вне процесса), иметь корректные probes и graceful
   shutdown, разумные requests (иначе HPA считает проценты от неверной базы),
   PodDisruptionBudget, чтобы при скейлинге вниз не остаться без кворума, и
   `topologySpreadConstraints` для распределения по зонам.

   Отдельно упомянуть: масштабировать stateful-компоненты (базы) так нельзя —
   там реплики, шардирование и операторы; и что перед автоскейлингом всегда
   полезно провести нагрузочное тестирование, чтобы знать реальный профиль.

   </details>

1. Допустим, у нас limit и request разные, и в кластере ресурсов меньше, чем в лимите, даст ли нам выложить pod в кластер?
   <details>
   <summary>Ответ</summary>

   Да, под запустится. Scheduler смотрит **только на `requests`** — он ищет
   узел, у которого свободно (по сумме requests уже размещённых подов)
   достаточно ресурсов. `limits` в планировании не участвуют вовсе, кластер
   намеренно допускает переподписку (overcommit).

   Что произойдёт дальше, зависит от ресурса:

   * **CPU** — сжимаемый: под сможет расти выше requests, пока есть свободные
     такты, но при конкуренции его прижмут (throttling) до доли,
     пропорциональной requests. Ничего не падает, только замедляется.
   * **Память** — несжимаемая: если под дорастёт до своего лимита, его убьёт
     cgroup (`OOMKilled`, рестарт по политике). Если же память на узле
     закончится раньше, kubelet начнёт **вытеснять** поды по классам QoS
     (BestEffort → Burstable → Guaranteed) и по превышению requests, а в худшем
     случае сработает OOM killer ядра и пострадать может даже «невиновный»
     процесс.

   Практический вывод: requests — это про планирование и гарантии, limits — про
   защиту узла от одного жадного пода. Сильный разрыв между ними как раз и
   создаёт риск «узел принял поды по requests, а по факту они хотят вдвое
   больше»; поэтому для критичных сервисов делают requests ближе к limits (класс
   Guaranteed), а метрики фактического потребления регулярно пересматривают.

   </details>

1. Сколько мне нужно мастер-нод для отказоустойчивого кластера?
   <details>
   <summary>Ответ</summary>

   **Три** — минимум для отказоустойчивости. Причина в etcd: он использует Raft
   и требует **кворума** (более половины узлов).

   ```text
   узлов   кворум   переживает отказ
   1       1        0   (не отказоустойчиво)
   2       2        0   (хуже, чем один: падение любого = потеря кворума)
   3       2        1
   5       3        2
   7       4        3
   ```

   Отсюда правила: число узлов должно быть **нечётным** (чётное не добавляет
   отказоустойчивости, но увеличивает задержку согласования), три узла хватает
   почти всем, пять берут для крупных или особо критичных кластеров, больше семи
   не рекомендуется — растёт стоимость записи.

   Что важно добавить: узлы control plane нужно разносить по разным зонам или
   стойкам (иначе отказ одной зоны убивает кворум) и держать etcd на быстрых
   дисках — он чувствителен к задержке fsync. При потере кворума кластер
   переходит в режим «только чтение»: работающие приложения продолжают работать,
   но изменения (деплой, автоскейлинг, самовосстановление) невозможны, пока
   кворум не восстановят из бэкапа или добавлением узла. И бэкап etcd обязателен
   независимо от числа узлов.

   </details>

1. Хочу задеплоить сервис и потом увидеть его с ноутбука. Какие минимальные ресурсы мне нужны для этого?
   <details>
   <summary>Ответ</summary>

   Минимально нужны три объекта: **Deployment** (сам под), **Service**
   (стабильная точка внутри кластера) и способ пустить трафик снаружь.

   ```yaml
   # 1) Deployment + 2) Service (ClusterIP)
   # 3) один из вариантов доступа:
   ```

   ```sh
   kubectl port-forward svc/api 8080:80     # нужен только доступ к API
   ```

   Это и есть настоящий минимум: с `port-forward` достаточно Deployment +
   Service и доступа к kube-apiserver, никакой внешней инфраструктуры.

   Если нужен «настоящий» доступ, вариантов три по возрастанию требований:

   * **NodePort** — плюс сетевая доступность узла с ноутбука и открытый порт
     30000–32767 в файрволе;
   * **LoadBalancer** — нужен облачный провайдер (или MetalLB в bare-metal) и
     внешний IP;
   * **Ingress** — нужны ingress-контроллер в кластере, внешний вход
     (LoadBalancer или NodePort), DNS-запись на этот адрес и, для https,
     сертификат (cert-manager). Зато один вход обслуживает много сервисов.

   Хороший ответ уточняет вопрос: «увидеть с ноутбука» для отладки —
   `port-forward`; для продакшена — Ingress с DNS и TLS.

   </details>

1. Набираю в командной строке `kubectl apply -f nginx.yml` расскажи детально, что происходит дальше.
   <details>
   <summary>Ответ</summary>

   1. **Клиент**: `kubectl` читает файл, определяет группу и версию API-ресурса,
      берёт кластер и учётные данные из `~/.kube/config` и отправляет
      HTTPS-запрос в kube-apiserver (`apply` — это server-side apply или
      трёхсторонний merge patch с аннотацией `last-applied-configuration`).
   2. **API-сервер**: TLS и **аутентификация** (сертификат, токен, OIDC) →
      **авторизация** RBAC (можно ли этому пользователю создавать Deployment в
      этом namespace) → **admission**: mutating вебхуки и контроллеры
      (подстановка значений по умолчанию, sidecar service mesh, `LimitRange`),
      затем **валидация** схемы и validating вебхуки (OPA, Kyverno, Pod Security
      Admission) → запись объекта в **etcd**.
   3. **Контроллеры**: Deployment-контроллер видит новый объект через watch и
      создаёт ReplicaSet; ReplicaSet-контроллер создаёт поды (пока без узла, в
      состоянии `Pending`).
   4. **Scheduler**: фильтрует узлы (ресурсы по requests, taints, nodeSelector,
      affinity, тома) и выбирает лучший по весам, записывает `nodeName` в под.
   5. **kubelet** на этом узле: через CRI просит containerd скачать образ
      (imagePullSecrets, политика pull), настраивает сеть через CNI (IP пода),
      монтирует тома через CSI, запускает init-контейнеры, затем основные,
      следит за probes и докладывает статус в API.
   6. **Сеть**: как только readiness-проба зелёная, под попадает в EndpointSlice
      сервиса, kube-proxy обновляет правила, и на под начинает идти трафик.

   Полезно закончить тем, как это наблюдать: `kubectl get events
   --sort-by=.lastTimestamp`, `kubectl describe pod`, `kubectl rollout status`,
   `-v=8` у `kubectl` для просмотра HTTP-запросов.

   </details>

1. Что такое `init` и `sidecar` контейнеры?
   <details>
   <summary>Ответ</summary>

   **init-контейнеры** выполняются **до** основных, строго по очереди, и каждый
   должен успешно завершиться. Используют для подготовки: применить миграции
   базы, дождаться доступности зависимости, скачать конфигурацию или секрет,
   выставить права на volume, склонировать репозиторий.

   **sidecar** — вспомогательный контейнер, работающий **рядом** с основным всю
   его жизнь, в том же поде (общий network namespace и тома): прокси сервисной
   сети (Envoy), сборщик логов, экспортер метрик, обновлятор конфигурации, агент
   секретов (Vault agent).

   ```yaml
   spec:
     initContainers:
       - name: migrate
         image: myapp:1.2
         command: ['./migrate']
       - name: log-shipper           # с Kubernetes 1.29 sidecar описывается
         image: fluent-bit           # как init-контейнер с restartPolicy: Always
         restartPolicy: Always
     containers:
       - name: app
         image: myapp:1.2
   ```

   Что стоит добавить: раньше sidecar был просто вторым контейнером в
   `containers`, и это давало проблемы с порядком запуска и завершения
   (приложение стартовало раньше прокси, а после завершения Job сайдкар не давал
   поду закончиться); начиная с 1.29 появились «настоящие» сайдкары —
   init-контейнеры с `restartPolicy: Always`, которые запускаются до основных и
   корректно завершаются после них.

   </details>

1. Зачем нужны `pause` контейнеры?
   <details>
   <summary>Ответ</summary>

   `pause` (infra-контейнер) — крошечный контейнер, который создаётся для
   каждого пода первым и просто спит, ничего не делая. Его роль — **держать
   namespace'ы пода**: network (IP и порты), IPC, а также быть родительским
   процессом (PID 1) для контейнеров пода, если включён общий PID namespace.

   Зачем это нужно: контейнеры пода должны разделять один сетевой стек и жить
   независимо друг от друга. Если бы namespace принадлежал «главному»
   контейнеру, то при его перезапуске под потерял бы IP и остальные контейнеры
   «осиротели». А pause живёт всё время существования пода: контейнеры можно
   перезапускать, IP при этом сохраняется.

   Дополнительно pause выполняет роль reaper'а — подбирает зомби-процессы, если
   контейнеры пода разделяют PID namespace.

   Что упомянуть: он практически не потребляет ресурсов (образ в сотни килобайт,
   процесс в паузе на сигнале), виден как
   `k8s.gcr.io/pause`/`registry.k8s.io/pause` в `docker ps` или `crictl ps -a`
   на узле, и это чисто внутренняя деталь реализации — разработчику приложений с
   ним взаимодействовать не приходится.

   </details>

1. Что такое `throttling`?
   <details>
   <summary>Ответ</summary>

   Принудительное замедление, когда потребитель превышает выделенную квоту.

   В контексте Kubernetes и контейнеров это прежде всего **CPU throttling**: CPU
   — сжимаемый ресурс, поэтому при достижении `limits.cpu` cgroup не убивает
   процесс, а не даёт ему такты. Механика CFS: квота выдаётся окнами по 100 мс,
   и если контейнер израсходовал свою долю раньше, он простаивает до начала
   следующего окна.

   ```text
   limits.cpu: 500m  ->  50 мс работы на каждые 100 мс
   приложение хочет больше -> ждёт остаток окна -> растёт latency, p99 скачет
   ```

   Как это увидеть: метрика `container_cpu_cfs_throttled_seconds_total` (и
   `throttled_periods`) в cAdvisor и Prometheus, `/sys/fs/cgroup/cpu.stat`
   внутри контейнера.

   Что важно проговорить: throttling бывает даже при низкой средней загрузке,
   если нагрузка «пиковая» (пример — многопоточная JVM или Go runtime, которые
   видят все ядра хоста и не знают о квоте — отсюда `GOMAXPROCS` и
   `-XX:ActiveProcessorCount`); лечится повышением или снятием лимита CPU,
   уменьшением параллелизма, увеличением периода CFS. Отсюда и распространённая
   практика: лимит памяти ставить обязательно, а лимит CPU — осторожно.

   Термин встречается и в других местах: rate limiting на API (`429 Too Many
   Requests`), throttling дисковых операций (`blkio`), троттлинг таймеров в
   неактивной вкладке браузера, тепловой троттлинг процессора.

   </details>

### Linux

1. Процесс и поток в Линуксе, в чем отличие?
   <details>
   <summary>Ответ</summary>

   С точки зрения ядра оба — **задачи** (`task_struct`), и создаются одним
   системным вызовом `clone()` с разными флагами. Разница в том, что
   разделяется:

   ```text
   процесс: своё адресное пространство, свои файловые дескрипторы,
            своя таблица страниц; общение — IPC, сокеты, пайпы, разделяемая память
   поток:   общее адресное пространство и дескрипторы с другими потоками
            процесса; свои стек, регистры и планировщиковый контекст
   ```

   * `fork()` создаёт процесс (copy-on-write копия памяти), `pthread_create` —
     поток (`clone` с `CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD`).
   * У процесса есть **PID**, у потока — **TID**; все потоки процесса имеют
     общий PID (он же TGID), а `ps -T` или `top -H` показывают потоки.
   * Переключение между потоками дешевле (не нужно менять таблицы страниц и
     сбрасывать TLB).
   * Изоляция: падение потока (segfault) убивает весь процесс, падение процесса
     соседей не задевает.

   Практический вывод: потоки — когда нужна общая память и быстрый обмен
   (веб-сервер, пул воркеров); процессы — когда нужна изоляция и устойчивость
   (`nginx` master + workers, Postgres backend на соединение). В Linux это
   различие тоньше, чем в других ОС, — отсюда и контейнеры, которые изолируют
   группы процессов через namespaces.

   </details>

1. Load average. Что это такое? Что делать, если высокий LA?
   <details>
   <summary>Ответ</summary>

   Load average — среднее число задач в состоянии «выполняется или ждёт» за 1, 5
   и 15 минут. Ключевая особенность Linux: в LA попадают не только готовые к
   выполнению задачи (runnable, `R`), но и **непрерываемо блокированные**
   (uninterruptible sleep, `D`) — то есть ожидание диска и сети. Поэтому высокий
   LA не обязательно означает нагрузку на процессор.

   Ориентир: LA нужно делить на число ядер. `LA 8` на 8 ядрах — это загрузка
   около 1.0, то есть «полностью занято, но без очереди»; `LA 24` на 8 ядрах —
   очередь втрое больше возможностей.

   **Что делать при высоком LA** — сначала определить причину:

   ```sh
   uptime; nproc                  # LA и число ядер
   top / htop                     # какие процессы, сколько %CPU, %wa
   vmstat 1                       # r (очередь на CPU) и b (блокированные)
   iostat -xz 1                   # диск: %util, await
   iotop -o                       # кто именно нагружает диск
   ps -eo state,pid,cmd | grep '^D'   # задачи в D-состоянии
   pidstat 1                      # по процессам
   ```

   Дальше по симптомам: очередь на CPU (`r` большое, `%us` высокий) —
   профилировать приложение, добавить ядер, ограничить параллелизм; ожидание
   диска (`%wa`, `D`-процессы, `await` высокий) — разбираться с диском,
   запросами к базе, свопом; высокий `%sy` — много системных вызовов, прерываний
   или проблемы с сетью; свопинг (`si`/`so`) — не хватает памяти. И проверить,
   не сжимает ли нас cgroup-лимит: в контейнере LA показывает хост, а не
   контейнер, поэтому смотреть надо ещё и на throttling.

   </details>

1. Как найти процесс и информацию о нем?
   <details>
   <summary>Ответ</summary>

   ```sh
   ps aux | grep nginx            # классика (осторожно: grep находит и себя)
   pgrep -a nginx                 # найти PID по имени, с командной строкой
   pidof nginx
   ps -ef --forest                # дерево процессов
   top -p <pid> / htop            # интерактивно
   ```

   Информация о конкретном процессе:

   ```sh
   ps -o pid,ppid,user,%cpu,%mem,rss,vsz,stat,etime,cmd -p <pid>
   cat /proc/<pid>/status         # состояние, память, потоки, uid
   cat /proc/<pid>/cmdline        # с какими аргументами запущен
   ls -l /proc/<pid>/cwd exe      # рабочий каталог и бинарник
   ls /proc/<pid>/fd              # открытые дескрипторы
   cat /proc/<pid>/environ        # переменные окружения
   lsof -p <pid>                  # открытые файлы и сокеты
   ss -tnp | grep <pid>           # какие порты слушает
   strace -p <pid>                # системные вызовы (отладка "залипшего")
   pstack / gdb -p <pid>          # стек
   systemctl status <unit>        # если это сервис: PID, cgroup, логи
   ```

   Полезно упомянуть, что `/proc/<pid>/` — источник истины для всех этих утилит;
   для процессов в контейнере на хосте виден их «внешний» PID, а принадлежность
   определяется по `cgroup` в `/proc/<pid>/cgroup`.

   </details>

1. Cache в Linux, что это? Почему иногда говорят его выключать?
   <details>
   <summary>Ответ</summary>

   Речь о **страничном кэше** (page cache): ядро держит в свободной оперативной
   памяти данные, прочитанные с диска и записанные на него. Повторное чтение
   идёт из памяти, а запись сначала попадает в кэш («грязные» страницы) и
   сбрасывается на диск позже. Рядом стоят buffers (метаданные блочных
   устройств), dentry- и inode-кэш.

   В `free -h` это колонка `buff/cache`. Важно понимать: такая память **не
   потеряна** — ядро отдаст её приложению по первому требованию, поэтому
   смотреть надо на `available`, а не на `free`.

   «Выключить кэш» в общем смысле нельзя и не нужно. Что действительно имеют в
   виду, когда советуют «сбросить кэш»:

   ```sh
   sync; echo 3 > /proc/sys/vm/drop_caches   # только для замеров, не в проде
   ```

   Это делают **при бенчмарках**, чтобы измерить честное чтение с диска. В
   остальных случаях сброс лишь замедлит систему — данные придётся читать
   заново.

   Отдельные обоснованные случаи: базы данных (PostgreSQL, Oracle) используют
   собственный кэш и прямой ввод-вывод (`O_DIRECT`), чтобы не кэшировать одно и
   то же дважды; для них настраивают `dirty_ratio`, `dirty_background_ratio`,
   `swappiness`, `vm.dirty_expire_centisecs`, чтобы избежать резких «залпов»
   записи и роста latency.

   </details>

1. RAID в Linux, что это?
   <details>
   <summary>Ответ</summary>

   RAID — объединение нескольких дисков в один логический массив для надёжности,
   производительности или того и другого. В Linux бывает аппаратный
   (контроллер), «фейковый» (BIOS) и **программный** — `mdadm` (устройства
   `/dev/mdX`), а также встроенные средства ZFS, Btrfs и LVM RAID.

   ```text
   RAID 0   страйп: скорость, ёмкость N дисков, отказ любого = потеря всего
   RAID 1   зеркало: ёмкость одного диска, переживает отказ любого
   RAID 5   N-1 ёмкость, чётность, переживает 1 отказ; долгий rebuild
   RAID 6   N-2 ёмкость, переживает 2 отказа; предпочтителен на больших дисках
   RAID 10  зеркало + страйп: лучший компромисс скорости и надёжности
   ```

   ```sh
   mdadm --create /dev/md0 --level=1 --raid-devices=2 /dev/sdb /dev/sdc
   cat /proc/mdstat                  # состояние массива и синхронизации
   mdadm --detail /dev/md0
   mdadm /dev/md0 --fail /dev/sdb --remove /dev/sdb   # замена диска
   ```

   Что важно проговорить: **RAID — не бэкап**. Он защищает от отказа диска, но
   не от удаления файлов, шифровальщика, ошибки администратора и сбоя
   контроллера. Плюс практические вещи: мониторинг деградации (`mdadm
   --monitor`, алерт на `/proc/mdstat`), горячий резерв (spare), «дыра записи» и
   опасность длительного rebuild на RAID 5 с большими дисками, влияние на
   производительность записи из-за расчёта чётности.

   </details>

1. Сможешь описать полный процесс загрузки OS Linux?.
   <details>
   <summary>Ответ</summary>

   ```text
   1. UEFI/BIOS: POST, инициализация железа, выбор загрузочного устройства
   2. Загрузчик: UEFI читает EFI-раздел -> GRUB (или systemd-boot);
      GRUB загружает ядро (vmlinuz) и initramfs, передаёт параметры
      (root=, ro, quiet)
   3. Ядро: распаковывается, инициализирует память, планировщик и драйверы,
      монтирует initramfs как временный корень
   4. initramfs: подгружает модули для доступа к настоящему корню
      (RAID, LVM, LUKS, сетевые ФС), находит и монтирует его, делает
      switch_root
   5. PID 1 (systemd): читает default.target (обычно multi-user или
      graphical), разворачивает граф зависимостей юнитов, монтирует по
      fstab, поднимает сеть, запускает сервисы параллельно
   6. getty / display manager -> приглашение на вход
   ```

   Что полезно добавить: разница UEFI и legacy BIOS (EFI-раздел и efibootmgr
   против MBR и загрузки по секторам); зачем нужен initramfs (ядро не знает, как
   добраться до корня на LVM или зашифрованном разделе); где смотреть проблемы —
   `dmesg`, `journalctl -b`, `systemd-analyze blame` и `critical-chain` для
   времени загрузки, `systemctl list-units --failed`; как вмешаться — параметры
   ядра в GRUB (`single`, `init=/bin/bash`, `systemd.unit=rescue.target`).

   </details>

1. Userspace и systemspace. Отличия, зачем они нужны?
   <details>
   <summary>Ответ</summary>

   Речь о двух режимах работы процессора и двух областях памяти: **пространство
   ядра** (kernel space) и **пространство пользователя** (user space).

   ```text
   kernel space: ring 0, полный доступ к железу и всей памяти,
                 единое адресное пространство ядра, драйверы, планировщик
   user space:   ring 3, доступ только к своей виртуальной памяти,
                 к железу — только через системные вызовы
   ```

   Зачем разделение: **защита и стабильность**. Процесс не может испортить чужую
   память или напрямую обратиться к устройству; ошибка в приложении роняет
   процесс, а не систему. Ядро выступает арбитром ресурсов (CPU, память, диск,
   сеть) и точкой контроля прав.

   Переход между режимами происходит через **системные вызовы** (`syscall`,
   раньше `int 0x80`), прерывания и исключения; каждый переход стоит времени
   (смена контекста, сброс кэшей), поэтому производительные системы стараются их
   сокращать (`io_uring`, `mmap`, батчинг, eBPF, DPDK и вынос обработки в user
   space).

   Практические следствия: сегфолт — попытка выйти за границы своей памяти;
   `kernel panic` — фатальная ошибка в ядре; `%us` против `%sy` в `top`
   показывает, где именно тратится процессор; драйвер в ядре быстрее, но опаснее
   (FUSE как компромисс — файловая система в user space).

   </details>

1. Почему некоторые сетевые службы запускаются в kernelspace, а не в виде демона?
   <details>
   <summary>Ответ</summary>

   Главная причина — **производительность**: обработка пакетов в ядре избавляет
   от копирования данных между ядром и пользовательским процессом и от
   переключений контекста на каждый запрос. Для сервисов, которые работают на
   скорости линка, это решающий фактор.

   Типичные примеры: NFS-сервер (`nfsd`), сетевой стек TCP/IP и маршрутизация,
   `iptables`/`nftables` и conntrack, IPVS (балансировка в Kubernetes),
   in-kernel iSCSI target, KTLS, kernel-модуль WireGuard, eBPF-программы
   (Cilium).

   Вторая причина — **доступ к внутренним структурам ядра**: буферам пакетов
   (`sk_buff`), таблицам маршрутизации, файловому кэшу; из user space к ним
   попасть можно только через системные вызовы, то есть медленно.

   Что важно сказать про цену: код в ядре работает без изоляции — ошибка
   означает panic всей машины, а уязвимость даёт максимальные привилегии;
   отладка сложнее, обновление требует перезагрузки или перезагрузки модуля.
   Поэтому современная тенденция — компромиссы: eBPF (безопасный верифицируемый
   код в ядре), FUSE и `io_uring`, а также вынос обработки в user space с
   обходом ядра (DPDK) там, где нужна максимальная скорость.

   </details>

1. Вывод команды `top`. Что означают колонки памяти у процесса?
   <details>
   <summary>Ответ</summary>

   ```text
   VIRT  виртуальная память: всё адресное пространство процесса — код,
         данные, стек, отображённые файлы, разделяемые библиотеки,
         зарезервированное и ещё не занятое. Может быть огромной и почти
         ничего не значит
   RES   resident set size: сколько физической памяти реально занято
         сейчас (включая разделяемые страницы) — главный ориентир
   SHR   часть RES, разделяемая с другими процессами (библиотеки, tmpfs,
         shared memory)
   %MEM  RES относительно всей физической памяти
   SWAP  (в некоторых версиях/по нажатию f) выгружено в своп
   CODE/DATA  размер сегментов кода и данных
   ```

   Что важно проговорить: сумма `RES` по всем процессам **больше** реального
   потребления, потому что разделяемые страницы считаются многократно — поэтому
   для честной оценки берут `PSS` из `/proc/<pid>/smaps_rollup` или `smem`.
   Высокий `VIRT` при низком `RES` — норма (например, JVM или Go резервируют
   адресное пространство). Для процессов в контейнере смотреть надо на лимит
   cgroup (`memory.current`, `memory.max`), а не на общую память хоста, потому
   что убивает под именно cgroup.

   </details>

1. Как вывести список домашних директорий для пользователей с непустым паролем?
   <details>
   <summary>Ответ</summary>

   Пароли лежат в `/etc/shadow` (второе поле), домашние каталоги — в
   `/etc/passwd` (шестое поле). «Непустой пароль» — это поле, которое не пустое
   и не является блокировкой (`!`, `*`, `!!`, `!*`).

   ```sh
   sudo awk -F: '$2 !~ /^[!*]|^$/ {print $1}' /etc/shadow > /tmp/withpass

   awk -F: 'NR==FNR {u[$1]; next} $1 in u {print $6}' /tmp/withpass /etc/passwd
   ```

   Или одной командой:

   ```sh
   sudo awk -F: '$2 !~ /^[!*]|^$/ {print $1}' /etc/shadow \
     | while read -r u; do getent passwd "$u" | cut -d: -f6; done
   ```

   Вариант через `join`:

   ```sh
   join -t: -o 2.6 \
     <(sudo awk -F: '$2 !~ /^[!*]|^$/ {print $1}' /etc/shadow | sort) \
     <(sort -t: -k1,1 /etc/passwd)
   ```

   Что стоит проговорить: нужен root, потому что `/etc/shadow` закрыт; хэш вида
   `!` или `*` означает, что вход по паролю запрещён (но вход по ключу
   возможен); правильнее использовать `getent`, а не читать `/etc/passwd`
   напрямую — тогда учтутся LDAP и SSSD; удобно рядом показать `passwd -S
   <user>` для проверки статуса пароля.

   </details>

1. Что такое namespaces, cgroups, capabilities в Linux?
   <details>
   <summary>Ответ</summary>

   Три независимых механизма ядра, на которых держится контейнеризация.

   **namespaces — изоляция видимости**: процесс видит только свой срез системы.

   ```text
   pid    свои процессы, свой PID 1
   net    свои интерфейсы, адреса, порты, таблицы маршрутов
   mnt    своё дерево монтирования
   uts    свой hostname
   ipc    своя разделяемая память и очереди
   user   маппинг uid/gid (root в контейнере != root на хосте)
   cgroup, time
   ```

   **cgroups (v2) — ограничение и учёт ресурсов**: сколько CPU, памяти, IO и
   процессов доступно группе. Именно cgroup убивает контейнер по `memory.max`
   (OOMKilled) и притормаживает его по `cpu.max` (throttling); она же даёт
   метрики потребления.

   **capabilities — дробление прав root**: вместо «всё или ничего» привилегии
   разбиты на отдельные разрешения — `CAP_NET_ADMIN` (настройка сети),
   `CAP_NET_BIND_SERVICE` (порты ниже 1024), `CAP_SYS_ADMIN`, `CAP_CHOWN`.
   Контейнер обычно запускают с минимальным набором (`--cap-drop=ALL
   --cap-add=NET_BIND_SERVICE`).

   ```yaml
   securityContext:                    # так это выглядит в Kubernetes
     runAsNonRoot: true
     capabilities: { drop: ['ALL'] }
     allowPrivilegeEscalation: false
   ```

   Итого: namespaces отвечают на вопрос «что процесс видит», cgroups — «сколько
   он может потребить», capabilities — «что ему позволено делать». Рядом стоят
   seccomp (фильтр системных вызовов) и SELinux/AppArmor (мандатный доступ).

   </details>
